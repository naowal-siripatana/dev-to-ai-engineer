2 · Hook 2 min

Your embeddings live in a Python list. The server restarts, and your assistant forgets all 20 documents until you embed them again. A second service would like to use the same vectors. What is missing?

Guess first, then open

A place to keep them that outlives the program and that other programs can reach: a database. You already have a good one in your plan: PostgreSQL. With the pgvector extension it can store vectors and answer “which rows are nearest to this vector?” with plain SQL. Today you start it and store your first vector.

3 · The idea, in three small pieces 8 min

Piece 1: a database in a container

Docker runs programs in containers: ready-made boxes with everything inside. An image is the recipe (here: PostgreSQL with pgvector already installed), a container is one running copy. A compose file (compose.yaml) describes the container in a few lines, so anyone starts the same database with one command. A volume keeps the data when the container is stopped or recreated. A port mapping connects a port on your computer to one inside the container.

Piece 2: pgvector adds a vector type and distance operators

After CREATE EXTENSION vector a column can have the type vector(3): three numbers (your embeddings will have 384). Three operators measure the distance between two vectors: <-> (straight-line distance), <=> (cosine distance) and <#> (negative inner product). A smaller distance means closer. Cosine similarity, which you know from Day 37, is 1 - (a <=> b).

Piece 3: nearest-neighbour search is one SQL query

You sort by distance and take the first rows: SELECT ... ORDER BY embedding <=> query LIMIT 3. The length of the vector must match the column: a vector with the wrong number of dimensions is an error, which protects you from mixing two embedding models (Day 37).

If you know another typed language (C# as the example): Docker Compose plays the role of the Docker Compose or Testcontainers setup that you may use for SQL Server in an ASP.NET Core project, and the vector column is a custom column type, like a spatial type in SQL Server with its own distance functions. With a .NET client you would use Npgsql with the pgvector package.
Capstone: this database replaces the in-memory index of the assistant. It also stays on after a restart, and later it holds the chunks, their metadata and the vectors in one place, in the same Postgres that the other parts of the system use.

4 · Worked example 5 min

Read it first. The whole database is two small files. compose.yaml:

services:
  db:
    image: pgvector/pgvector:pg17
    container_name: assistant-db
    environment:
      POSTGRES_USER: assistant
      POSTGRES_PASSWORD: assistant
      POSTGRES_DB: assistant
    ports:
      - "5433:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U assistant -d assistant"]
      interval: 3s
      timeout: 3s
      retries: 10

volumes:
  pgdata:

The second file runs once, when the database is created for the first time, and turns the extension on. db/init.sql:

CREATE EXTENSION IF NOT EXISTS vector;

The user and the password assistant are for a throwaway database on your own computer. Never use them for anything real. The host port is 5433, not the usual 5432, so that it does not clash with a Postgres that may already run on your machine.

6 · Stuck? anytime

  • “Cannot connect to the Docker daemon”: Docker is not running. Start Docker Desktop (or your container engine), wait until it says it is running, and try again.
  • “port is already allocated” or “address already in use”: another program uses the port. Change the left number in ports (for example to 5434:5432) and use the new port in your connection.
  • The container is not healthy: look at the logs with docker compose logs db. Often the first start is just slow.
  • “password authentication failed” from Python: the user, the password or the port differs from compose.yaml. The database also keeps its first password in the volume: if you changed it later, run docker compose down -v to start fresh.
  • The extension is missing in a database you created: init.sql only runs for the first database. In another database run CREATE EXTENSION vector;.

The distance is smaller for closer items. Cosine similarity (1 - (a <=> b)) is bigger for closer items. Use the one that matches how you think, and always ORDER BY the distance (ascending).

A wrong password or a wrong port gives errors like these:

You should see

You should see
connection to server at "127.0.0.1", port 5999 failed: ... Connection refused

docker compose down removes the container but keeps the volume, so after up -d your table is still there. docker compose down -v removes the volume too:

You should see
ERROR: relation "items" does not exist
LINE 1: SELECT count(*) FROM items;

After down -v the database is new and empty, and init.sql runs again (the extension is back, your table is gone). Use -v only when you want a fresh start.

7 · Check yourself 5 min

  1. What do the image, the container and the volume each do?
  2. Which pgvector operator would you use to sort by cosine closeness, and which way do you sort?
  3. What is the difference between docker compose down and docker compose down -v?
Answers
  1. The image is the recipe (Postgres with pgvector installed). The container is one running copy of it. The volume keeps the data outside the container so it survives a restart.
  2. <=>, the cosine distance, sorted ascending: ORDER BY embedding <=> query LIMIT 3, because a smaller distance means closer.
  3. down removes the container and keeps the data in the volume. down -v removes the volume as well, so you lose the data and start fresh.
