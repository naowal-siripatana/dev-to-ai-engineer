Self-test: coding agents

1.5 hhands-onfree
Today you will be able to explain coding agents, instructions files and code review in your own words, and plan week 17.

1 · Self-test 25 min

Close your notes. Answer each question in your own words, and write a confidence number next to it: 1 = guessing, 2 = fairly sure, 3 = certain. Then open the answers and mark each one right, partly right or wrong.

  1. What is the difference between a coding assistant and a coding agent? (Day 107)
  2. What do you look for in an agent’s steps? (Day 107)
  3. Which limits do you set before an agent works? (Day 107)
  4. What goes into an instructions file, and what stays out? Why must it be tested? (Day 109)
  5. What are the four parts of a good prompt for an agent? (Day 110)
  6. Name three questions of the review checklist. (Day 110)
  7. Why is “the tests pass” not enough? Give an example from your runs. (Day 110, 112)
  8. Why commit the agent’s first version alone? (Day 112)
  9. What belongs in a PR description besides what changed? (Day 112)
Answers
  1. An assistant suggests text and you apply it. An agent reads and edits files and runs commands itself, in a loop (think, act, observe).
  2. Did it read before it edited? Did it run something to check its own work? Did it touch files outside the task, or decide something the task did not ask for?
  3. A git branch, a small clear task, which commands it may run without asking, no secrets in reach, and tests and a type check that it can run. Afterwards you read the whole diff.
  4. In: commands, layout, rules newcomers get wrong, what done means, what needs a human decision. Out: what the code says, history, vague style advice, secrets. A wrong file is worse than none, because the agent trusts it, so every command must be run.
  5. The goal, the files to look at (and the instructions file), the rules (what not to touch or add), and what it must show when done.
  6. For example: does it do what I asked? What happens with a wrong, empty or odd input? Can it fail silently? What does it overwrite, delete, send or log? Do tests cover the new behaviour? Is every change needed? Secrets or privacy? Did I see the tests, types and score table pass?
  7. Tests only check what someone thought of. In the runs: the --only option ran zero questions with exit code 0 on a typo while tests were green, and the question log’s tests wrote user questions into the repository.
  8. So that the review is a real diff, and your fixes are a second commit: you can show what the agent wrote and what you changed.
  9. Why, how it was tested, what was not tested, and the risks.

Read your numbers. If you were sure (3) and wrong, that is the most valuable thing you found. Circle those.

2 · Your review log 15 min

Keep one line for every feature an agent builds for you. It is the evidence that you review, and the data that tells you what your agent gets wrong:

date | feature | agent | findings (observed / read) | fixed? | tests added | golden table: before -> after
...  | question log | ...   | ...                          | ...    | ...         | 11/18 -> 11/18

After a few features, look at the “findings” column. If the same kind of finding repeats (missing tests, silent failure, a file written outside the task), put a line in AGENTS.md about it. That is how the file stays useful.
