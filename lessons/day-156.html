Guess first, then open

Yes: open-weight models publish their trained numbers (the weights) so that anyone can download and run them. How big it is you can calculate: the number of weights times the bytes each one takes. Today you measure it on your own machine.

3 · The idea, in three small pieces 8 min

Piece 1: open-weight, and where to find them

An open-weight model is one whose weights you can download. That is not the same as open source: the training data and code may not be shared, and the license may limit use (read it on the model page; licenses differ between models, even in one family). Hugging Face is the website and library where most of them live: a model page (the model card) says what it is, its size, its license and how to use it. A model is a folder of files: weights, a tokenizer and a small config.

Piece 2: size is arithmetic, memory is the limit

A model with 1.5 billion weights, each stored in 2 bytes, is about 3 GB. The weights must sit in fast memory while the model writes: VRAM (the memory of a graphics card) on a PC, or the unified memory shared by the CPU and the GPU on an Apple laptop like the one used for this lesson. If the weights do not fit, the model does not run (or runs very slowly from disk). On top of the weights come the program and the context (the text it reads and writes), so leave some room.

Piece 3: quantization makes them smaller

Quantization stores each weight with fewer bits (for example 4 instead of 16). The model gets about 3.5 times smaller and usually faster, because less data moves through memory for each word. The price is a small loss of precision, which can make answers a little worse. How much worse depends on the model and the task, so you test it (Day 161) and do not assume.

If you know another typed language (C# as the example): quantization is like storing a double as a float or a short where you can live with less precision: smaller and faster, with a rounding error you must check. VRAM is the heap that the GPU can use: if the object does not fit, it does not run.

4 · Worked example 5 min

Read it first. What was run: on an Apple-silicon laptop with 16 GB of shared memory, with the mlx-lm library and models of the Qwen2.5 Instruct family from Hugging Face in two forms, 16-bit (bf16) and 4-bit. A model is not hosted by this course; names below are exactly what was downloaded. A small script reads the header of the weights file (no model needs to load) and sums up the values:

"""Read the size of a model from the files on disk: the number of weights, the bytes per weight, and the data types. Usage: python model_size.py <folder with model.safetensors>"""
import json
import math
import struct
import sys
from collections import Counter
from pathlib import Path

folder = Path(sys.argv[1])
file = folder / "model.safetensors"
with open(file, "rb") as f:
    header_size = struct.unpack("<Q", f.read(8))[0]   # the first 8 bytes say how long the JSON header is
    header = json.loads(f.read(header_size))
header.pop("__metadata__", None)

by_dtype: Counter[str] = Counter()
numbers: Counter[str] = Counter()
for tensor in header.values():
    by_dtype[tensor["dtype"]] += math.prod(tensor["shape"]) * {"BF16": 2, "F16": 2, "F32": 4, "U32": 4}.get(tensor["dtype"], 1)
    numbers[tensor["dtype"]] += math.prod(tensor["shape"])

size = file.stat().st_size
print(f"{folder.parent.parent.name.split('--')[-1]}")
print(f"  file size       {size / 1e6:8.1f} MB")
for dtype, n in numbers.items():
    print(f"  {dtype:<6} values   {n / 1e6:8.1f} million   ({by_dtype[dtype] / 1e6:.1f} MB)")
config = json.loads((folder / "config.json").read_text())
print(f"  layers {config['num_hidden_layers']}, hidden size {config['hidden_size']}, quantization {config.get('quantization', 'none')}")

The 0.5 billion model is 494 million values of 2 bytes each, so 988 MB: the arithmetic is exact. The 4-bit file is 3.6 times smaller, not 4 times, and the reason is in the numbers:

278.1 MB x 8 / 494 million values = 4.5 bits per value, not 4.0
(every group of 64 values also stores a scale and a bias, and the embeddings are kept in 16 bits)

Now load each model and measure the memory and the speed while it writes 120 tokens (a token is about three quarters of a word). Loading took long because the files were on an external drive:

"""Load a model on this machine and measure: the memory its weights take, the peak while it writes, and the speed. Usage: python measure_memory.py <model name> [...]"""
import sys
import time

import mlx.core as mx
from mlx_lm import load, stream_generate

PROMPT = "Explain in three sentences why the order of lines in a Dockerfile matters."

for name in sys.argv[1:]:
    mx.clear_cache()
    mx.reset_peak_memory()
    started = time.perf_counter()
    model, tokenizer = load(name)
    mx.eval(model.parameters())
    load_s = time.perf_counter() - started
    weights_gb = mx.get_active_memory() / 1e9
    messages = [{"role": "user", "content": PROMPT}]
    prompt = tokenizer.apply_chat_template(messages, add_generation_prompt=True)
    last = None
    for last in stream_generate(model, tokenizer, prompt, max_tokens=120):
        pass
    assert last is not None
    print(f"{name.split('/')[-1]:<32} load {load_s:5.1f} s   weights {weights_gb:5.2f} GB   peak {mx.get_peak_memory() / 1e9:5.2f} GB   speed {last.generation_tps:6.1f} tokens/s")
    del model
    mx.clear_cache()

The weights take what the file size says, the peak is a little more, and the 4-bit versions are 2 to 3 times faster here, because there is less to move. Your numbers will differ with the machine. Bigger models, by arithmetic, not measured:

You should see
parameters     bf16 (2 bytes each)     4-bit (about 4.5 bits each, see below)
0.5 billion       1.0 GB                  0.3 GB          <- measured: 0.99 GB and 0.28 GB
1.5 billion       3.1 GB                  0.8 GB          <- measured: 3.09 GB and 0.87 GB

70 billion      140.0 GB                 39.4 GB          (arithmetic)
formula: parameters x bits per weight / 8 = bytes of weights.  Add room for the context and the program (the peak above was about 5 to 20 percent more).

So a 7 billion model in 16 bits (14 GB) does not fit in 16 GB with the system around it, but in 4 bits (about 4 GB) it does. A 70 billion model needs a server-class machine even in 4 bits.

6 · Stuck? anytime

  • The download is huge or slow: start with the smallest model (0.5 billion). A 4-bit 1.5 billion model is under 1 GB.
  • The model page does not say how much memory it needs: calculate it from the number of parameters and the bits, as in the table.
  • You run out of memory: close other programs, use a smaller or more quantized model, or a shorter context.
  • The model answers strangely: tiny models are weak. Day 161 shows how a 0.5 billion model fails the rules of your assistant.
Hint: Step 2

1.5 billion x 4.5 / 8 = 0.84 billion bytes, so about 840 MB. The real file was 869 MB: a few embeddings and other tensors are kept in more bits.

Solution: Step 3

In 16 bits on 16 GB: the 7, 13 and 70 billion models do not fit (14 GB leaves nothing for the system). In 4 bits the 7 billion (about 4 GB) fits and the 13 billion (7 GB) fits with room; the 70 billion (39 GB) does not. Options when it does not fit: a smaller model, a more compressed one, a shorter context, or a bigger machine.

  2. How do you work out how much memory a model’s weights need?
  3. What does quantization trade?
Answers
  1. You can download the weights. It does not mean open source: the data and code may be closed and the license may limit use.
  2. Number of parameters times bits per weight divided by 8, plus room for the context and the program.
  3. Precision for size and speed: smaller and faster, with a small possible loss of quality that you must test.
