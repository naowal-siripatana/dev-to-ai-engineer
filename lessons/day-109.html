DAY 109 · LEVEL 9: CODING AGENTS

AGENTS.md / CLAUDE.md and context for code

60-70 minhands-onfree
Today you will be able to write an instructions file that a new agent session can use, with every command tested.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Name two things to look at in the steps of a coding agent.
  2. Why is a git branch the first limit you set?
Answers
  1. Did it read before it edited, and did it run something to check its own work (also: did it touch files outside the task).
  2. Any change can be thrown away, and the diff against the main branch shows exactly what the agent did.

2 · Hook 2 min

You start a new agent session in your repository. It knows nothing about your project: not that tests need no model, not that every search must take the user’s role, not that the answers in the demos come from a stand-in. How does it find out, and who has to write that down?

Guess first, then open

A coding agent has no memory of your project between sessions. It learns what it can from the files it reads, and from one file that is loaded at the start: an instructions file (AGENTS.md, or CLAUDE.md for Claude Code). You write it, once, and it works for every session after. It is documentation that is read, every time.

3 · The idea, in three small pieces 8 min

Piece 1: write what the agent cannot guess

The agent can read your code, so do not repeat it. Write what it cannot see: the exact commands (and in which order), where the important things live, the rules that a newcomer gets wrong in the first week, what “done” means, and which decisions need a human. The best test of every line: “would a good new colleague do the wrong thing without it?”

Piece 2: keep it short, true and tested

A long file is read less well, and a wrong file is worse than none: the agent will trust it. So keep it to a page, run every command in it yourself (one by one, on a clean checkout if you can), and update it in the same pull request that changes the thing it describes. Never put a secret in it: it goes into Git, and into the agent’s context.

Piece 3: different tools, one file

Tools look for different file names. AGENTS.md is a common convention that several tools read; Claude Code reads CLAUDE.md. You do not need two copies: keep the real content in AGENTS.md, and make CLAUDE.md a one-line file that imports it with @AGENTS.md. A file that is loaded for the whole session also costs context tokens every time (Day 58), which is one more reason to keep it short.

If you know another typed language (C# as the example): it is the README for a very fast colleague who forgets everything every night, mixed with an .editorconfig and a contributing guide. The commands section is what you would put in the build instructions of any solution, and “ask first” is your list of changes that need a design review.
Capstone: the Module 9 checkpoint needs an AGENTS.md in the ai-knowledge-assistant repository describing its stack, conventions and test commands. You write it today, and use it on Saturday.

4 · Worked example 5 min

The six parts of a good file:

what this is        two or three sentences: the stack and the purpose
commands            the exact commands to install, run, test, type-check, evaluate
layout              where things live, in a few lines (not a copy of the file tree)
rules               the things a newcomer would get wrong: roles, secrets, naming of stand-ins
done means          what to run and show before saying 'done'
ask first           the changes that need a human decision

The real file for my-ai-project (39 lines). The commands are the ones used in the earlier lessons (pytest, mypy and run_golden.py were run again for this file), and every rule comes from something that went wrong, or nearly went wrong, in an earlier lesson (the role filter from Day 79, the stand-ins from Day 91, the golden table from Day 105):

# AGENTS.md: my-ai-project (the PumpGuard assistant)

## What this is
A Python service (FastAPI) that answers questions about a fictional pump monitor from a small knowledge base (`data/kb`):
hybrid search (pgvector and keywords), cited answers, user roles, and a tool loop. A .NET gateway and a React page sit in
front of it (other folders). The product is fictional; there is no real customer data.

## Commands
    uv sync
    docker compose up -d            # Postgres with pgvector on port 5433 (throwaway credentials)
    uv run python ingest.py         # chunk, embed and store the knowledge base
    uv run pytest -q                # needs no model and no key; database tests skip when the database is down
    uv run mypy src tests           # must stay clean
    uv run python run_golden.py     # the score table (18 questions); compare it with the baseline I saved
    uv run uvicorn my_ai_project.api:app --port 8000

## Layout
- `src/my_ai_project/`: `api.py` routes, `deps.py` dependencies, `store.py` SQL, `hybrid.py` search, `rag.py` pipeline,
  `grounding.py` prompt and citations, `tool_design.py` / `agent.py` / `tool_loop.py` tools, `golden.py` / `scoring.py` evaluation.
- `tests/`: one file per module, with fakes for the model, the embedder and the store.
- `data/kb/` the pages, `data/golden.jsonl` the golden questions.

## Rules
- Every search and every tool takes the user's role (`allowed_kinds`). Never add a path that skips it.
- A tool's error is a result (`is_error`), not an exception. A tool that changes data needs a person's approval first.
- A stdio MCP server never prints to standard output; use `logging`.
- Models in tests and demos are stand-ins (`Pretend...`, `Simulated...`). Keep them named as such, and never present
  their answers as a real model's.
- No secrets in Git: keys come from environment variables, and `.env` is ignored.
- Type hints everywhere. Small functions. No new dependency without asking.

## Before you say you are done
1. Run `pytest` and `mypy`, and show the results.
2. If you touched retrieval, prompts, thresholds or chunking: run `run_golden.py` before and after and show both tables.
   Do not accept a change that makes a question fail that passed before.
3. Show the diff, and list what you did not test.

## Ask first
Changing a prompt in `grounding.py`, the minimum similarity, the chunk size, the database schema, or anything about deployment.

And CLAUDE.md, one line:

# CLAUDE.md
@AGENTS.md

Notice what is not in the file: the history of the project, a description of every function, style advice such as “write clean code”, and any key. Compare it with a bad one:

# Notes for the AI
Please write clean, high-quality, well-tested code. Follow best practices. Be careful.
This project uses AI and is very important. (and 300 more lines of history of the project...)
To run the tests use pytest_run_all.sh     <- the file was deleted two months ago

5 · Try it 30 min

Work in my-ai-project, on a branch if you like (git switch -c docs/agents-md).

Step 1 Write it

Write AGENTS.md for your repository, using the six parts. Start from the one above, and change it to match your project. Write CLAUDE.md with the one line.

Step 2 Test every command

Run each command in the file, one by one. Fix the file (or the project) when one fails. Predict first: how many of your commands will fail on the first try?

Step 3 Cut it

Read it as a new colleague. For every line, ask: “would they do the wrong thing without it?” Delete the lines where the answer is no. Aim for under 60 lines.

Step 4 Try it on an agent

Start a new agent session and give it a small task that touches a rule of your file (for example: “add a search function”, which must take the role). Did it follow the rule? Did it run the commands of “done means”? Write down what it did, and what it missed. If it missed something, was the line in the file unclear, or missing?

Commit: git add AGENTS.md CLAUDE.md and git commit -m "Add AGENTS.md and CLAUDE.md".

6 · Stuck? anytime

  • The agent ignores the file: check the file name and the folder (the repository root), and that you started a new session after you created it.
  • The file grows every week: move long explanations into docs/ and link to them in one line. Keep only the rules.
  • You are not sure a rule is needed: if it has never gone wrong, leave it out; add it the first time it does.
  • Two tools, two files: keep one real file and import it, as shown.
Solution: Step 2 (what to expect)

Most people find that at least one command in their first draft fails: a missing step (start the database first), a wrong folder, or a command that only works on their machine. Each failure you fix is a mistake the agent will no longer make. That is the main value of Step 2.

Solution: Step 4 (how to judge)

Do not count the file as a success because the agent read it. Check what it did: the role in the new function, the tests it ran, whether it showed the diff and said what it did not test. If it missed a rule, make the line shorter and more concrete (“every search takes allowed_kinds” works better than “respect permissions”) and try again.

7 · Check yourself 5 min

  1. What should an instructions file contain, and what should it leave out?
  2. Why is a wrong file worse than no file?
  3. How do you serve two tools that look for different file names?
Answers
  1. What the agent cannot guess: commands, layout, rules newcomers get wrong, what done means, what needs a human decision. It leaves out what the code already says, history, vague style advice and secrets.
  2. The agent trusts it, so a wrong command or a stale rule sends it the wrong way with confidence.
  3. Keep the content in one file (AGENTS.md) and make the other (CLAUDE.md) a one-line file that imports it.
