DAY 86 · LEVEL 7: TOOLS

Tool design: schemas, permissions, errors

60-70 minhands-onfree
Today you will be able to design a tool with a clear description, a strict schema, a structured error and a permission check that runs first.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Why does a tool error go back to the model as a result?
  2. Who runs the function when a model “calls” it?
Answers
  1. The model can read it and recover, or explain it to the user. An exception ends the loop and nobody learns why.
  2. Your code. The model only sends a request that names the tool and the input.

2 · Hook 2 min

Two tools do the same lookup. One is called error with the description “errors”. The other has a clear name, a clear description and a strict schema. Which one will the model use correctly, and why?

Guess first, then open

The second. A tool’s name, description and schema are the only things the model knows about it. They are a prompt. A vague tool gets called at the wrong time, with the wrong input, or never.

3 · The idea, in three small pieces 8 min

Piece 1: the description is a prompt

Write it for the model. Say what the tool does, when to use it, and when not to. Put the format of the input in the schema (a pattern, an enum, a short description on each field), because a schema can be checked by code and a sentence cannot.

Piece 2: the error is part of the design

A good tool error has three parts: a stable code (invalid_input, unknown_error_code, permission_denied) that your code and your tests can match, a plain message, and a hint for what to do next (the format to use, the list of valid codes). The model can then fix its own mistake or explain it. Keep hints useful but safe: a refused caller must not learn what exists.

Piece 3: the tool acts for the user, not for the model

The model is not a user and has no rights of its own. A tool must run with the role of the person who asked and check it before doing anything. The role comes from your code (their login), never from the model’s input. This is the permission filter of Day 79, now applied to tools. A tool that only reads is easy; a tool that writes or deletes needs extra care, and you will meet that on Wednesday next week.

If you know another typed language (C# as the example): a tool is a public API method with an OpenAPI description, and the model is a client that has read only the documentation. You would not ship an endpoint called error with the summary “errors”. The error codes are like ProblemDetails with a type, and the role check is an [Authorize] that runs before the action.
Capstone: the Module 7 checkpoint is one real tool. Today you design it properly, so that on Saturday the loop around it is simple.

4 · Worked example 5 min

A checklist for any tool you write:

1. One job.            The tool does one thing. Two jobs are two tools.
2. A verb_noun name.   lookup_error, not error or handle.
3. A description for the model: what it does, when to use it, and when NOT to.
4. A strict schema:    required fields, patterns, enums, short descriptions.
5. A small answer:     only the fields the model needs, never a whole table.
6. A readable error:   a stable code, a plain message, and a hint for the next step.
7. The user's rights:  the tool runs with the permissions of the person asking, not of the model.
8. Read or write?      A tool that changes things needs more care (a confirmation, a log, a limit).

A bad tool, for contrast:

{"name": "error", "description": "errors", "input_schema": {"type": "object"}}   # what is it for? what does it take?

The good one, in src/my_ai_project/tool_design.py. It replaces the executor of Day 82: the same input check, plus the user’s role, structured errors with hints, and a better description:

import json
from dataclasses import asdict
from typing import Any

from pydantic import BaseModel, Field, ValidationError

from my_ai_project.access import allowed_kinds
from my_ai_project.incident import UnknownErrorCode, load_incidents, lookup_error


class LookupInput(BaseModel):
    code: str = Field(pattern=r"^[Ee]\d{3}$", description="The error code: the letter E and three digits, like E104")


LOOKUP_TOOL: dict[str, Any] = {
    "name": "lookup_error",
    "description": "Look up ONE PumpGuard error code (the letter E and three digits, like E104) in the incident database. "
    "Returns its name, severity and the recommended action. "
    "Use it when the user asks what an error code means or what to do about it. "
    "Do not use it for general questions: it only knows error codes.",
    "input_schema": LookupInput.model_json_schema(),
}


def tool_error(tool_use_id: str, code: str, message: str, **hints: Any) -> dict[str, Any]:
    """An error result the model can act on: a stable code, a plain message, and a hint for what to do next."""
    body = {"error": {"code": code, "message": message, **hints}}
    return {"type": "tool_result", "tool_use_id": tool_use_id, "content": json.dumps(body), "is_error": True}


def execute(tool_use_id: str, name: str, tool_input: dict[str, Any], role: str = "customer") -> dict[str, Any]:
    """Run a tool on behalf of a user with this role. Always returns a tool_result block; never raises."""
    if name != "lookup_error":
        return tool_error(tool_use_id, "unknown_tool", f"there is no tool named {name!r}", available=["lookup_error"])
    try:
        permitted = "error" in allowed_kinds(role)
    except ValueError:
        permitted = False   # an unknown role fails closed
    if not permitted:
        # Checked before the input, so a refused caller learns nothing about which codes exist.
        return tool_error(tool_use_id, "permission_denied", "this user may not read error records", hint="tell the user to ask support staff")
    try:
        args = LookupInput.model_validate(tool_input)
        incident = lookup_error(args.code)
    except ValidationError as err:
        first = err.errors()[0]
        return tool_error(tool_use_id, "invalid_input", f"invalid {'.'.join(str(p) for p in first['loc'])}: {first['msg']}", hint="use the letter E and three digits, like E104")
    except UnknownErrorCode:
        return tool_error(tool_use_id, "unknown_error_code", f"no error with code {tool_input.get('code')!r}", known_codes=sorted(load_incidents()))
    return {"type": "tool_result", "tool_use_id": tool_use_id, "content": json.dumps(asdict(incident))}

6 · Stuck? anytime

  • “ModuleNotFoundError: access”: access.py comes from Day 79. Add it, or copy it from the lesson.
  • Staff get permission_denied: the role string must be exactly staff, lower case.
  • A test fails on the message text: match the stable code, not the sentence. The message may change; the code is the contract.
Solution: Step 2

The customer would see unknown_error_code with the full list of known codes, so a person with no rights learns exactly which codes exist. The order of the checks is part of the security: rights first, then input, then lookup.

Solution: Step 3

Every record has a name, a severity and a long action text. Seven records are already several times longer than one, and a real database would have thousands. The model has to read all of it on every call: it is slower, it costs more, and it can lose the one fact that matters (context rot, Day 58). Return what was asked for, and nothing else.

Solution: Step 4 (close_incident)

Different points: it writes, so it needs a confirmation before it runs (a human says yes), a log line with who and when, a permission that only staff have, an error for “already closed”, and a description that says “only after the user has confirmed”. It must be safe to call twice (idempotent).

Template: tests
import json

import pytest

from my_ai_project.tool_design import LOOKUP_TOOL, execute


def body(result: dict[str, object]) -> dict[str, object]:
    return json.loads(str(result["content"]))


def test_staff_get_the_record() -> None:
    result = execute("t1", "lookup_error", {"code": "E104"}, "staff")
    assert "is_error" not in result
    assert body(result)["name"] == "Disk full"


@pytest.mark.parametrize("role", ["customer", "admin", ""])
def test_everyone_else_is_refused_and_learns_nothing(role: str) -> None:
    result = execute("t1", "lookup_error", {"code": "E999"}, role)
    assert result["is_error"] is True
    error = body(result)["error"]
    assert error["code"] == "permission_denied"   # type: ignore[index]
    assert "known_codes" not in error             # type: ignore[operator]


def test_a_bad_format_says_how_to_fix_it() -> None:
    error = body(execute("t1", "lookup_error", {"code": "104"}, "staff"))["error"]
    assert error["code"] == "invalid_input"        # type: ignore[index]
    assert "E104" in error["hint"]                 # type: ignore[index]


def test_an_unknown_code_lists_the_known_ones() -> None:
    error = body(execute("t1", "lookup_error", {"code": "E999"}, "staff"))["error"]
    assert error["code"] == "unknown_error_code"   # type: ignore[index]
    assert "E104" in error["known_codes"]          # type: ignore[index, operator]


def test_an_unknown_tool_lists_the_available_ones() -> None:
    error = body(execute("t1", "delete_everything", {}, "staff"))["error"]
    assert error["available"] == ["lookup_error"]  # type: ignore[index]


def test_the_description_says_when_not_to_use_it() -> None:
    assert "Do not use it" in LOOKUP_TOOL["description"]

7 · Check yourself 5 min

  1. Why is a tool description a prompt?
  2. What three parts does a good tool error have?
  3. Why is the permission checked before the input?
Answers
  1. It is the only thing the model knows about the tool, and it decides when and how the model calls it.
  2. A stable code, a plain message, and a hint for the next step.
  3. So that a refused caller learns nothing about the data: no list of valid codes, no hint that a record exists.
