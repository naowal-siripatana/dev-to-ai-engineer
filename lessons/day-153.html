Teach-back: why secrets stay out of Git

30 minhands-onfree
Today you will be able to explain in 5 sentences why a secret never goes into Git, what to do instead and what to do after a leak.

1 · Warm-up: write down what you know 5 min

Close your notes. A teammate says: “The repository is private and I deleted the password in the next commit. Why are you worried?” Write what you would answer in two lines. Then write who can read a private repository, over its whole life.

Do not look anything up. Your guess is the most useful line you will write today.

2 · Explain it 10 min

Your task: explain why secrets stay out of Git in 5 sentences or a 60-second voice note.

  • Who you are talking to: the teammate above.
  • Use these words: history, environment variable, rotate, .gitignore, secret store.
  • Rules: no notes, and say what you do after a leak, not only how to avoid one.

Write it or record it now. A rough first try is exactly right.

Stuck? Sentence starters

Use these if you freeze:

1. A secret is ..., for example ...
2. Git keeps ..., so when I commit a password ...
3. Removing it in the next commit ... but ...
4. What I do instead is ..., and what I commit is ...
5. If it already leaked, I first ..., because ...

3 · Check it against the key points 8 min

Read the six key points and tick each one that your explanation said clearly. Be strict.

  1. Git keeps everything: every commit is stored, so a value committed once is in the history, in every clone and every fork, even after a later commit removes it.
  2. Private is not secret: a private repository is read by many people, tools and services over the years, and may become public by a mistake or a change of settings.
  3. Where secrets go instead: the environment, filled from a .env file that is ignored by Git, or from the secret store of the place where the code runs. An .env.example with fake values is committed.
  4. Catch it early: a finder or scanner in CI, and a look at git status and git diff --staged before every commit; adding files by name, not git add ..
  5. After a leak: treat the secret as public. Replace it at its source first (a new key, a new password, and revoke the old one), then clean the history if you want to, and look at the logs of the service for use of the old one. Cleaning the history alone is not enough: copies may exist.
  6. Limit the damage: use keys with the least power and a spending limit, one per place, so that a leaked key can do little.
A model answer in 5 sentences

A secret is a key or a password, for example a database address with a password in it. Git keeps every commit, so when I commit a password it stays in the history and in every copy, even if the next commit removes it. A private repository is still read by many people and tools, and can become public by mistake. What I do instead is read secrets from the environment, filled from a .env file that Git ignores or from the secret store of the host, and I commit only an example file with fake values. If it already leaked, I first replace it at its source and revoke the old one, because cleaning the history does not take back copies that exist.

Count your ticks. 6: very clear. 3 to 5: good, you found your gaps. 0 to 2: also fine, the next step fills them in.

4 · Look at the evidence 5 min

Do not trust the argument. Look at a leak. In a throwaway repository a file with a fake password inside an address was committed, then removed in the next commit. A small finder checks the files that Git tracks. Predict first: will the finder be green after the removal, and will the password still be findable?

You should see
after the commit that adds the password:
  settings.env:1  password inside an address
  1 suspicious line(s) in 2 tracked files          (exit code 1)

after the commit that removes it:
  0 suspicious line(s) in 2 tracked files          (exit code 0)

git log --oneline
  1026194 remove the password
  ce05f5c add settings

git log -p -S S3cretValue9 --oneline
  1026194 remove the password
  -DATABASE_URL=postgresql://admin:S3cretValue9@db.example.com:5432/app
  ce05f5c add settings
  +DATABASE_URL=postgresql://admin:S3cretValue9@db.example.com:5432/app

The finder is green once the file is clean, but git log -p -S finds the password in both commits. The finder looks at the present; the history is the past, and anyone with a clone can read it. (The fake password is made up for this lesson. Never test this with a real one.)

5 · Fix the biggest gap 3 min

Look at the key points you did not tick. Pick the one that matters most and write a better sentence for it. Did you say what to do after a leak? Add what is missing, and save your five sentences next to your earlier teach-backs.
