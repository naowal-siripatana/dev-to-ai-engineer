DAY 168 · LEVEL 13: SHOW YOUR WORK · PROJECT LAB

Project Lab 24: freeze, polish, record, CV and LinkedIn

2.5 hhands-onfree
Today you will be able to freeze your project, polish it until a stranger can run it from the README, record your demo, and describe it on your CV and LinkedIn with claims you can show.

1 · Warm-up 5 min

Answer from memory, then open the answers.

  1. What are the beats of a three-minute demo?
  2. What kind of gap does a fresh clone find that tests do not?
  3. Which claims of your pitch have no real run behind them?
Answers
  1. Who you are and the problem; how it fits; two or three things working; what is not real; what next.
  2. Gaps between what you know and what you wrote down: missing setup, silent skips, examples that fail by default, features you cannot see, leftover templates.
  3. Your own list: the things you set up but never ran (images, a pipeline, a hosted model).

2 · The goal 5 min

Done looks like: a stranger, with only your link and a timer, gets your project running by following the README; a three-minute recording of your demo is linked at the top of it; and your CV and LinkedIn describe the project with claims that you can show. From now until the workshop no new features: only fixes.

Be clear about what was run. For the capstone repository of this course the following were run for real: the diagram check, the secret finder (before and after), a fresh clone followed from the README (without Docker), and the test commands. Not done by the author: recording a video, editing any CV or LinkedIn page, the Docker path, the GitHub pipeline. The CV text below is an example built from real numbers of this course: write yours from your own runs.

3 · Plan the work 10 min

Four jobs: (1) freeze, (2) polish, (3) record, (4) CV and LinkedIn. Put them in that order: you cannot record a demo of a thing that is still changing, and you cannot write about it before it is stable. Give yourself a rule for the day: if a new idea appears, it goes on the ticket list, not into the code.

4 · Build 90 min

Job 1: freeze

Write what is in, what is out, and the known limits. Tag the code: git tag v1-freeze. If you break something later, you can always go back to it.

FREEZE: from now on no new features until the workshop. Only: fix a bug, fix the README, fix the demo.
IN  (frozen):   the page (two modes), the gateway, the Python service, the ingest, Compose, the settings, the tests, the README
OUT (not now):  a real login, a bigger knowledge base, a streaming page, deploying it somewhere
KNOWN LIMITS (also in the README):  the role is a header; the cache can be stale; the keyword index is built at start
ticket list:    one line per idea you are NOT building, so that you do not forget it, and do not build it either

Job 2: polish

Polish is not new code: it is the small things that make a stranger trust the rest. Run each check, and fix what it finds. The run on the capstone repository:

You should see
polish check                                    result (run for real, on the capstone repository)
the diagram and compose.yaml agree               the diagram and compose.yaml agree
docker compose config -q                         (no output, exit code 0)
the secret finder, from the top of the repo      before: 3 suspicious lines (CI password twice, the README placeholder)  ->  after: 0 suspicious line(s) in 213 tracked files
.env.example documents every setting             yes (below)
a fresh clone runs from the README               yes, without Docker, after 5 fixes (Day 166)
the tests                                        pytest 224 passed (with a database), mypy clean; dotnet test 21 passed; npm run build ok
NOT checked:  the Docker images, the Compose stack running, the GitHub Actions workflow, the hosted model

Two of those checks found something. The secret finder, run on the whole repository, flagged the throwaway CI password and a placeholder in the README (fakes on purpose: now allowed by name), and showed that it had only looked at the folder it was started in:

# find_secrets.py: two changes, both found by running it on the whole repository
ALLOWED = (..., "ci-only-password", "USER:PASSWORD@", "secret-scan: allow")   # fakes that the project uses on purpose
os.chdir(<top of the repository>)    # git ls-files lists only the folder you are in: go to the top first

The example settings file now documents every setting, so that a stranger knows what to uncomment (it was missing the settings of the model providers):

Other polish to look for in your repository: leftover files from the tool that made the project, scripts at the top level that belong in a folder of examples, a licence file (decide on one), a clear first line in the README, no TODO you would be ashamed of, commit messages that read well.

Job 3: record the demo

You have the script of Wednesday and the clean start of Thursday. Record it. (This was not done by the author: there is no screen recording here. Follow the list.)

BEFORE YOU RECORD
  start from a clean state: stop everything, start it from the README, warm it up (ask one throwaway question)
  close what is not needed: notifications off, other tabs closed, a plain desktop, browser zoom at 125 percent so it reads on a phone
  open: the README with the diagram, the page, a terminal with the test command ready
  write your script on a second screen or on paper, not on the screen you record
RECORD
  a screen recorder you already have (QuickTime on a Mac, OBS, the one in your system); microphone check first (10 seconds, listen back)
  do two full takes without stopping, even if you stumble; keep the better one
  3 minutes: if it is 4, cut a beat, do not talk faster
AFTER
  trim the start and the end only; add captions if you can; upload as unlisted; put the link at the top of the README
  watch it once with the sound off: can you follow the story from the screen alone?

Job 4: CV and LinkedIn

Write three bullets and a short project text. First the rules, then an example built from the real numbers of this course (write yours, from your own runs):

RULES FOR EVERY LINE
1. Start with a verb for what YOU did, then the thing, then a number or a fact you can show.
2. Every claim has a command, a file or a screen behind it. If you cannot show it, cut it or say "set up, never run".
3. Say stand-in where it is a stand-in. A reader who finds it later will doubt everything else.
4. Do not write "AI engineer with ..." for what you built in your free time: write what you built.
5. Do not list a tool you only read about (Kubernetes, vLLM...). Write "read about", or leave it out.
6. Put the link first. A recruiter clicks before reading.
PROJECT (CV, 3 bullets)
- Built a question-and-answer assistant in React, ASP.NET Core, FastAPI and PostgreSQL with vector search: it answers only from its own pages, cites them, and refuses when they hold no answer.
- Measured three writers on 18 golden questions (a stand-in 11, small local models 5 to 17 by size and precision) and reported how small the sample was.
- Followed my own README from a fresh clone, found and fixed five setup gaps, and added a test for the first one.

LINKEDIN (Featured / Projects, about 60 words)
PumpGuard assistant: a grounded Q&A assistant for a made-up product. React, .NET gateway, Python service, PostgreSQL with pgvector. Answers from its own pages with citations, refuses otherwise, limits what each role can see. The default writer is a stand-in; I also compared small local models. Code, diagram and a 3-minute demo in the README.
(link to the repository and to the demo)

5 · The final test 20 min

Give a stranger the link and a timer, say nothing, and watch (or ask a friend to do it and report). If you cannot find anyone today, do the fresh clone yourself again from the top, with a timer, and note how long it takes. Fix what you find, then run it once more.

THE FINAL TEST: a stranger (a friend, a family member who codes, a classmate)
  give them ONLY the link to the repository, and a timer
  they follow the README and say out loud what they do and where they are stuck; you say nothing
  note: minutes to a running page ...   steps where they stopped ...   words they did not understand ...
  fix what they hit, and run it again with the fresh clone yourself

Check the top of the README one last time: is the demo link there, does the first paragraph say what it is, and does “what has not been run” list what is true today?

6 · Stuck? anytime

  • You keep finding things to add: put each on the ticket list and read the freeze rule aloud. A finished small project beats an endless big one.
  • The demo only works some of the time: add the warm-up step, find what is random (a model loading, a cache, a port in use) and remove it, and keep a recorded clip as the fallback.
  • You have no one to test with: use a fresh clone on another machine or another user account of your own, and speak aloud what you do.
  • The CV bullet feels thin: add the number or the file that shows it. If there is none, the bullet is not ready.
Hint: the CV

For each bullet, ask: “what would I show if the interviewer said show me?” If the answer is a command, a file or a screen, keep it. If it is “well...”, cut it or mark it as not run.

7 · Finish and ship 15 min

Commit by name (the README, the example settings, the finder, the docs), check git status for anything you do not want public, and push. Then the 10-minute reflection: what you cut, what you are proud of, what a stranger taught you. Tag the checkpoint: git tag m15-checkpoint.

8 · Check yourself 5 min

  1. Why freeze before you polish, and polish before you record?
  2. What makes a CV line believable?
  3. What did the stranger (or your fresh clone) find that you did not?
Answers
  1. You cannot record a thing that is still changing, and a polished README of an unstable project goes stale at once.
  2. A verb for what you did, and a number, a command or a file that shows it, with stand-ins named as stand-ins.
  3. Your own list: always something you knew so well that you never wrote it down.
