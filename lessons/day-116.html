DAY 116 · LEVEL 10: DESIGN

When NOT to use AI, and decision frameworks

60-70 minhands-onfree
Today you will be able to choose between a rule, one model call, RAG, an agent and a person for a use case, and defend the simplest choice with evidence.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. What makes a requirement testable?
  2. Why write “where you are today” next to a success criterion?
Answers
  1. It says one thing and comes with a check: a yes or no, or a number, and the script that gives it.
  2. The gap between the two is the plan, and it keeps the criterion honest.

2 · Hook 2 min

A teammate says: “Let’s use AI for the error code lookup too.” Your vector search failed to find the E104 page for the question about E104. What is a better tool for that job?

Guess first, then open

A dictionary: the code is the key, the answer is the value. It is exact, instant, free and always right. The best use of AI is knowing where not to use it: when a rule gives the exact answer, a model can only be slower and less sure.

3 · The idea, in three small pieces 8 min

Piece 1: a ladder, and you start at the top

There are five ways to solve a problem, from the simplest to the most complex: a rule, one model call, RAG, an agent, or a person. Each step down costs more, is slower, is less predictable and is harder to test. So you start at the top, and you move down only when the step above cannot do the job. Most beginners start at the bottom, because it is more exciting.

Piece 2: five questions decide it

Ask them in order, and the first “yes” decides: Is there an exact rule? Is a wrong answer costly, with no rule? Does the next step depend on the last result? Must the answer come from your documents? If none fits, one model call is enough. Cost of failure comes early in the list: if a mistake is expensive, no clever design replaces a person.

Piece 3: “do not use it” is a design decision

Not using AI is not a failure of ambition. It is a decision to write down. A rule is cheaper to run, to test and to explain. A small knowledge base may fit in the prompt. A fixed process is a workflow, not an agent. Keep AI for the part that is really about language, and write down the other parts as rules around it.

If you know another typed language (C# as the example): it is the same instinct as “do not reach for a distributed system when a method call will do”. You already know to pick the simplest thing that meets the requirement, and to be able to explain why you did not pick the fancy one.
Capstone: your assistant already uses three rungs: a lookup tool for error codes, RAG for the manuals, and a person (the approval step) for risky actions. On Saturday you write down why.

4 · Worked example 5 min

The ladder:

1. RULES / A LOOKUP     exact, free, instant, testable.                      'What does error E104 mean?'
2. ONE MODEL CALL      understands and writes free text; knows nothing of yours.   'Translate this reply into Thai.'
3. RAG                 a model call + your documents, found at question time.      'Answer from the manuals.'
4. AN AGENT            a loop: the next step depends on the last result.           'Check these incidents and rank them.'
5. A PERSON            when a wrong answer is costly and no rule exists.           'Approve this refund.'
Move DOWN the ladder only when the step above cannot do the job. Each step costs more, is slower, and is harder to test.

The five questions, as a decision order:

1  Could a rule, a lookup or a formula give the exact answer?         yes -> rules (unless it must read or write free text)
2  Is a wrong answer costly (money, safety, trust) and there is no rule?  yes -> a person decides; the model prepares
3  Does the next step depend on what the last one found?                  yes -> an agent (or a workflow, if you can write the steps down)
4  Must the answer come from YOUR documents?                              yes -> RAG (or put them all in the prompt, if they are tiny)
5  Otherwise                                                              one model call, checked by a golden set

Two real measurements make the point. First, the error code lookup done with a rule, against a vector search for the same question. rule_vs_rag.py:

import os
import statistics
import time

from my_ai_project.access import allowed_kinds
from my_ai_project.embedder import FastEmbedder
from my_ai_project.incident import lookup_error
from my_ai_project.store import ChunkStore

question = "What does error E104 mean?"
timings = []
for _ in range(2000):
    start = time.perf_counter()
    lookup_error("E104")
    timings.append((time.perf_counter() - start) * 1_000_000)
print(f"rule: lookup_error('E104') = {lookup_error('E104').name}, {statistics.median(timings):.1f} microseconds (median of 2000)")

store = ChunkStore(os.environ.get("DATABASE_URL", "postgresql://assistant:assistant@localhost:5433/assistant"))
embedder = FastEmbedder()
vector = embedder.embed([question])[0]
rag = []
for _ in range(20):
    start = time.perf_counter()
    found = store.search(embedder.embed([question])[0], top_k=3, allowed_kinds=allowed_kinds("staff"))
    rag.append((time.perf_counter() - start) * 1000)
print(f"vector search alone: {statistics.median(rag):.1f} ms (median of 20), top 3 = {[f.doc_id for f in found]}")
print("the E104 page is in the top 3:", any(f.doc_id == "error-e104" for f in found))
You should see
rule: lookup_error('E104') = Disk full, 0.1 microseconds (median of 2000)
vector search alone: 6.5 ms (median of 20), top 3 = ['error-e101', 'error-e102', 'error-e101']
the E104 page is in the top 3: False

The rule is exact and tens of thousands of times faster (a dictionary lookup against an embedding and a database query), and the vector search alone did not even have the right page in its top 3. For this job, a model is the wrong tool. (Your pipeline still gets E104 right, because the keyword search of Day 74 brings the page back: that is extra machinery to make AI do what a dictionary does.)

Second, how big is the knowledge base? Count the tokens of all 20 pages:

You should see
20 pages, 862 tokens in all

All 20 pages together are 862 tokens: less than one page of text. You could put every page in every prompt, with no vector database at all. RAG earns its place when the knowledge base is too big, too costly or too noisy to send whole, or when you need to filter it per user. At this size it is not needed for the sake of fitting; keep that in mind for Saturday.

5 · Try it 30 min

This is a paper exercise, with two measurements. Work in your notebook or in docs/design-notes.md.

Step 1 Choose for five use cases

Write five use cases for your project (or take the five of the example, and replace two). For each, choose rules, one model call, RAG, an agent or a person, using the five questions in order. Write one line of why.

Step 2 Defend the boring one

For the use case where you chose rules or a person, write what you would answer to a teammate who says “but AI can do this”. Use a number if you have one.

Step 3 Measure two things

Run rule_vs_rag.py on your project (or time a lookup against a retrieval of your own). And count the tokens of all your knowledge base pages with your count_tokens. Predict first: will your knowledge base fit in one prompt?

Step 4 Break the framework

Find a use case where the five questions give an answer that you disagree with. Which question is missing? Write it down: your framework is a draft, and tomorrow you encode it in code.

Commit if you wrote a file: git add docs/design-notes.md and git commit -m "Choose an approach for five use cases".

6 · Stuck? anytime

  • Every use case looks like “RAG”: ask question 1 again, honestly. Many “questions about documents” are really lookups in a table.
  • You cannot decide between a workflow and an agent: can you write the steps down in advance? If yes, a workflow.
  • A use case has several parts: split it. Most real features are a rule plus a model call plus a person.
Solution: Step 3 (your numbers)

For a small knowledge base, the whole text is often under a few thousand tokens, and the honest answer to “do I need RAG?” is “not yet”. That does not mean the design is wrong; it means you must write the reason for RAG down (growth, per-user filtering, citations), and not “because it is the standard”.

Solution: Step 4 (a missing question)

A common missing question is volume and cost: a task that is done a million times a day needs a different answer from one that is done ten times. Another is latency: a decision that must come in 50 ms cannot wait for a model. Add what you find to the list.

7 · Check yourself 5 min

  1. Name the five rungs of the ladder, from the simplest.
  2. Why does “a wrong answer is costly” come before “needs an agent”?
  3. Why might RAG be the wrong choice for a knowledge base of 862 tokens?
Answers
  1. A rule or lookup, one model call, RAG, an agent, a person.
  2. If a mistake is expensive, no loop or clever design replaces a person: the model may prepare, and a person decides.
  3. It fits in a prompt, so you could send every page, with no vector database. RAG is justified by growth, per-user filtering or citations, and that reason should be written down.
