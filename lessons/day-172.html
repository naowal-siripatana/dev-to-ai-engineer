DAY 172 · LEVEL 13: SHOW YOUR WORK

Practice the demo

60-70 minhands-onfree
Today you will be able to check your demo path with a script, rehearse the demo twice without stopping, and say what you will do when it breaks.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. How do you rank bugs when you can fix only three?
  2. What is the difference between /health and /ready?
Answers
  1. By who is hurt, how likely it is, and the size of the fix: the worst small ones first.
  2. Liveness (the process runs) against readiness (it can do its job, so it asks what it depends on).

2 · Hook 2 min

You have read your script twenty times and it is perfect in your head. Then you stand up, the first question takes ten seconds, and you forget your first sentence. What would have saved you?

Guess first, then open

Doing it for real, twice, without stopping. A demo is a performance with a machine on stage: the machine and your memory both fail in ways you cannot predict from your desk. The first full run teaches you, the second without stopping builds the habit of carrying on.

3 · The idea, in three small pieces 8 min

Piece 1: make the demo a test you can run

Your demo is six beats, and each beat has an expected result. Write them as a demo check: a script that runs every beat against the running system and says which one is wrong. Run it before every rehearsal, and the morning of the workshop. If it passes, the system is ready; the rest is you.

Piece 2: rehearse twice, and the second time do not stop

Run the whole demo aloud with a timer. The first run you may stop and fix. The second run you carry on whatever happens, and you say your fallback line when something breaks. What you practise is not the words: it is recovering without panic.

Piece 3: drill the failures, and remove the surprises

Switch off the service on purpose and see what the audience would see. Write one calm sentence for each failure (service down, slow first question, no network). And remove what you can: start everything before the audience, warm it up with a throwaway question, and keep the models and files on the laptop, not on the internet.

If you know another typed language (C# as the example): the demo check is a smoke test run after a deployment: the minimum that must work before anyone is let in. The failure drill is a game day, the way a team switches a dependency off on purpose to see what happens.
Capstone: today you turn your demo script into a check, and you run the full demo twice. Tomorrow a friend watches the second run.

The demo check. Each beat of the script has a function that asks the running system and checks what comes back (scripts/demo_check.py):

The demo check
"""The demo, as a test: run every beat of the demo script against the running system and check what comes back.
Usage: python scripts/demo_check.py [base_url]     Exit code 1 if any beat is wrong. Run it before every demo, and before every friend sees it."""
import json
import sys
import time
import urllib.error
import urllib.request

BASE = sys.argv[1] if len(sys.argv) > 1 else "http://localhost:5100"


def call(method: str, path: str, role: str | None = None, question: str | None = None) -> tuple[int, dict[str, object]]:
    headers = {"content-type": "application/json", **({"x-demo-role": role} if role else {})}
    data = json.dumps({"question": question}).encode() if question is not None else None
    request = urllib.request.Request(BASE + path, data=data, method=method, headers=headers)
    try:
        with urllib.request.urlopen(request, timeout=60) as response:
            return response.status, json.loads(response.read())
    except urllib.error.HTTPError as err:
        return err.code, {}


def ask(role: str, question: str) -> dict[str, object]:
    status, body = call("POST", "/api/ask", role, question)
    assert status == 200, f"HTTP {status}"
    return body


def beat_calibration() -> None:
    body = ask("customer", "How often should I calibrate the sensor?")
    assert "once a month" in str(body["answer"]) and "[manual-calibration#0]" in str(body["answer"]), body["answer"]


def beat_refusal() -> None:
    body = ask("customer", "Where can I buy a coffee?")
    assert body["refused"] is True and body["sources"] == [], body["answer"]


def beat_customer_cannot_read_errors() -> None:
    assert ask("customer", "What does error E104 mean?")["refused"] is True


def beat_staff_can() -> None:
    body = ask("staff", "What does error E104 mean?")
    assert "[error-e104#0]" in str(body["answer"]), body["answer"]


def beat_stats_are_for_staff() -> None:
    assert call("GET", "/api/stats", "customer")[0] == 403
    status, body = call("GET", "/api/stats", "staff")
    assert status == 200 and int(str(body["questions"])) >= 1, body


def beat_ready() -> None:
    assert call("GET", "/ready")[0] == 200, "the gateway cannot reach the AI service"


BEATS = [beat_ready, beat_calibration, beat_refusal, beat_customer_cannot_read_errors, beat_staff_can, beat_stats_are_for_staff]
failed = 0
for beat in BEATS:
    started = time.perf_counter()
    try:
        beat()
        verdict = "ok"
    except (AssertionError, KeyError, urllib.error.URLError) as err:
        verdict, failed = f"FAILED: {err}", failed + 1
    print(f"{beat.__name__.removeprefix('beat_'):<34} {verdict:<8} {(time.perf_counter() - started) * 1000:6.0f} ms")
print("the demo path works" if failed == 0 else f"{failed} beat(s) failed: fix them before the demo")
sys.exit(1 if failed else 0)

The order to do things in before you go on, and the sentences for when it breaks:

BEFORE YOU GO ON (do it in this order, every time)
1. start everything from the README, from nothing running
2. python scripts/demo_check.py   -> "the demo path works"
3. ask one throwaway question in the page (this warms it up: a model, a cache, the first request)
4. open: the README with the diagram, the page, the terminal with the test command typed but not run
5. notifications off; battery full and the charger in; the recorded demo ready to play
WHAT I SAY WHEN IT BREAKS (write your own, one line each; say it calmly, then move on)
the service is down:       "It cannot reach the AI service, so it says so and does not guess. Here is the recording of the same run."
a question is slow:        "The first call loads things; the next ones are quick. While it works, here is the part of the diagram it is in."
the page does not load:    "I will show it with the terminal instead." (curl a question, show the JSON, say what each field is)
the network is down:       "Everything runs on this laptop. The model files are already here."
I forget my words:         look at the diagram: one box, one line

5 · Try it 30 min

Work on your own capstone. Start your whole system from the README, from nothing running, and time how long each part takes to be ready.

Step 1 Copy and run

Write your demo check: one function per beat of your script, each asking your running system and checking the result, with a pass or fail for each and a non-zero exit code if any fails (use the worked example as a shape). Run it. Fix what fails: the demo or the check, whichever is wrong.

Step 2 Change one thing

Run your full demo aloud with a timer and the rehearsal sheet below. Predict the time before you start. Which beat took longest, and which words did you stumble on?

Step 3 Break it on purpose

Switch off one dependency (the service behind your front door, or your database) and run the check, then try a real beat in the page. What does the audience see? Write your calm sentence for it, and say it aloud once. Then check your offline story: where does your system keep its model files, and what happens after a restart with no network?

Step 4 Your turn

Run the demo twice more: the first run you may stop, the second you do not stop, whatever happens. Fill in the sheet. Change the one thing that hurt most (a word, a step, an order), and commit your check: git add scripts/demo_check.py and git commit -m "Add a demo check".

6 · Stuck? anytime

  • The demo check passes but the demo goes wrong: the check tests the system, not the page, the screen share or you. Rehearse with the real screen.
  • The first question is slow: warm the system up with a throwaway question before you start. If a model has to load, that can take tens of seconds.
  • You always stop at the same place: the script is too long there, or the step is awkward. Cut a sentence or move the step.
  • You are nervous aloud: record yourself once. It is uncomfortable and it works. Practise the first two sentences until you do not think about them.
Hint: Step 3

The three things most likely to go wrong in a room: the network, a service that did not start, and the first slow call. Each has a fix you can do before the audience arrives.

7 · Check yourself 5 min

  1. What does the demo check prove, and what does it not prove?
  2. Why is the second rehearsal the one you do not stop in?
  3. Name two surprises you can remove before the audience arrives.
Answers
  1. That every beat works on the running system. Not that the page, the screen share or you will go well.
  2. Because on stage you cannot stop. You practise carrying on and saying your fallback line.
  3. Start everything and warm it up first; keep the model and files on the laptop in a folder that survives a restart; have a recording ready; notifications off.
