Project Lab 22: GitHub Actions for the whole system

2.5 hhands-onfree
Today you will be able to run tests and build the images on every push, with a badge and an honest README.

1 · Warm-up 5 min

Answer from memory, then open the answers.

  1. Why does CI use the fake writer and a throwaway database password?
  2. What does || true do to a failing test step?
  3. Where do real secrets live, if a job ever needs one?
Answers
  1. CI must not need a real key; a leak or a mistake would cost money or touch real data.
  2. It turns the failure into a pass (exit code 0), so nothing is blocked.
  3. In the secret settings of the repository or of the host, never in the workflow file or in Git.

2 · The goal 5 min

Done looks like: you push to GitHub, four jobs run (Python, gateway, page, images), they turn green, and a green badge sits at the top of your README. A red test makes the build job grey. The README says what CI checks, and what it does not. This is the checkpoint of the deployment weeks: your whole system starts with one command, and a machine checks it on every push.

Be clear about what was run. The workflow was never run on GitHub, and no image was ever built (the author’s Docker engine did not respond). So this lab has no green screenshot to show. What was checked for real: the file with a workflow linter, and every command of the Python, gateway and page jobs by hand with the same settings. The image job could only be checked as far as docker compose config. The images job is the most likely place of your first red run: it is the first time the three Dockerfiles of Day 142 and 147 are built from a clean checkout. If it fails, that is the lesson: read the log, fix the Dockerfile, push again.

3 · Plan the work 10 min

Four jobs, one workflow. Draw them: python, gateway, web side by side, and images after them with needs. Then list what each job needs from the outside: a database (a service container with a throwaway password), a .NET SDK, Node, the POSTGRES_PASSWORD that compose.yaml insists on. None of them needs a real secret. Three jobs of work: (1) the workflow file, (2) the first push and the first read of a log, (3) the badge and the README.

4 · Build 90 min

Job 1: the workflow

Create .github/workflows/ci.yml in the repository root. Read it top to bottom before you copy it: the trigger, the least permission, the cancel of old runs, then the four jobs. Things to notice: the database is a service container and the tests read TEST_DATABASE_URL; the embedding model is cached between runs; the secret finder is a step of the Python job; and the images job has needs on the other three.

name: CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read   # the least a job needs: it can read the code and nothing else

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true   # a newer push replaces the run of an older one

jobs:
  python:
    runs-on: ubuntu-24.04
    timeout-minutes: 20
    defaults:
      run:
        working-directory: python-service
    services:
      db:
        image: pgvector/pgvector:pg17
        env:
          POSTGRES_USER: assistant
          POSTGRES_PASSWORD: ci-only-password   # a throwaway database that lives for this job only
          POSTGRES_DB: assistant
        ports: ["5433:5432"]
        options: >-
          --health-cmd "pg_isready -U assistant -d assistant"
          --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      TEST_DATABASE_URL: postgresql://assistant:ci-only-password@localhost:5433/assistant
      DATABASE_URL: postgresql://assistant:ci-only-password@localhost:5433/assistant
      LLM_MODE: fake   # no real model, no key: CI never needs a secret
      FASTEMBED_CACHE_PATH: ${{ github.workspace }}/.fastembed
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10
      - uses: actions/cache@v6
        with:
          path: .fastembed
          key: fastembed-bge-small-en-v1.5
      - run: uv sync --frozen
      - run: uv run mypy src tests
      - run: uv run pytest -q
      - run: uv run python find_secrets.py

  gateway:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    defaults:
      run:
        working-directory: gateway
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: 10.0.x
      - run: dotnet test AskGateway.Tests

  web:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    defaults:
      run:
        working-directory: web/chat-ui
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm ci
      - run: npm run build

  images:
    needs: [python, gateway, web]   # only when all three test jobs are green
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    env:
      POSTGRES_PASSWORD: ci-only-password   # compose.yaml refuses to run without it
    steps:
      - uses: actions/checkout@v7
      - run: docker compose config -q
      - run: docker compose build

Check it before you push (run for real, with actionlint 1.7.12), and then run the commands of each job by hand, in its folder (run for real on a laptop with the same settings):

Job 2: the first push

Push to a branch, open a pull request, and open the Actions tab. Read the log of the slowest job from the top. When a job fails, open the failing step, read the first error (not the last line), fix it on your machine in the same way as in the log, and push again. Expect at least one red run; a clean first run is rare.

Job 3: the badge and the README

The badge is a picture that GitHub makes from the last run of the workflow named in the address. Add it to the top of the README, with a section for what CI checks and what it does not (the honest part), using your own owner and repository names:

# pumpguard

[![CI](https://github.com/OWNER/REPO/actions/workflows/ci.yml/badge.svg)](https://github.com/OWNER/REPO/actions/workflows/ci.yml)

(replace OWNER and REPO with yours)

## What CI checks on every push

- types and tests of the Python service (against a throwaway PostgreSQL with pgvector, with the fake writer: no model, no key)
- the .NET gateway tests
- the page builds
- no obvious secret in the files Git tracks
- the three images build (only when the tests are green)

## What CI does not do

- it does not call a real model, and it does not push the images anywhere
- it does not deploy
- it has not checked quality of answers (that is the golden set, run by hand)

## Run everything

    cp .env.example .env      # then set your own POSTGRES_PASSWORD
    docker compose up -d --build

5 · Run it, and read what you ran 20 min

Make a red run on purpose, then a green one. On a branch, change one expected value in a test, push, and look at the red mark: which jobs ran, which is grey? Fix the test, push, and look at the green. Then merge the pull request and watch the badge on the main page of the repository.

Check the secrets. Run git grep -n -i password in the repository root and read every line: only fakes and variable names should be there. Look at the log of one run: no real value should appear. (The settings object prints stars, remember Day 149.)

Optionally in the settings of the repository, find the rule that requires a check to pass before a merge (a branch protection rule or a ruleset), and require python, gateway and web. It is a setting on GitHub, not a line in the file; this lab did not set or test it.

Write down in your notes what you actually saw: how long each job took on the first run and on the second, and which one failed first.

6 · Stuck? anytime

  • The images job fails in a Dockerfile: read the first error. The usual ones: a file the COPY expects is not in the repository (ignored by Git, or by .dockerignore), a wrong folder in build:, or a base image name that is wrong. Reproduce it with docker compose build on your laptop if you can.
  • The Python job fails on the database: check that the port in TEST_DATABASE_URL is the left side of ports, and the password matches.
  • The .NET job cannot find the SDK: the version in dotnet-version must exist. Use the one your project targets.
  • The badge is grey or says “no status”: the workflow has not run on the branch the badge points at, or the owner or repository name in the address is wrong.
  • Everything is green but you are not sure it tests anything: make one test fail on purpose (step 5 above). A check that cannot fail tells you nothing.
Hint: reading a log

Start at the red step, scroll up to the first line that says error, and read from there. The last lines often only say that the step failed.

7 · Finish and ship 15 min

Merge the pull request when it is green. In the README, check that every claim is true and that the “does not do” list is honest. Then the 10-minute reflection: what worked, what broke, what you would change. Tag the checkpoint: git tag m13-checkpoint, and look at it with git log --oneline --decorate.

8 · Check yourself 5 min

  1. Why do the three test jobs run in parallel, and the image job after them?
  2. What does the badge show, and what does it not show?
  3. What did you actually run, and what did you only read?
Answers
  1. The test jobs do not depend on each other, so parallel is faster. Building images from code that fails its tests is waste, so needs keeps it behind them.
  2. The result of the last run of the workflow on the branch. It does not show the quality of the answers, nor that the system works in production.
  3. Your own list. If you cannot name it, the README is not honest yet.
