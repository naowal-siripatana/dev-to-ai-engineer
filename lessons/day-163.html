1 · Warm-up 3 min

  2. What does a cost of 0 per token not mean?

2 · Hook 2 min

A recruiter opens your repository for 90 seconds. They do not run anything. What do they see first, and can they tell what you built, how it fits together, and what is real?

Guess first, then open

They see the README, and often only the top of it. If the first screen says what it is, shows one picture of how the parts fit, and says honestly what is a stand-in, they will keep reading. If it is the empty template that the tool made, they close the tab.

3 · The idea, in three small pieces 8 min

Piece 1: write the README for a stranger, in the order they ask

A reader asks the same questions in the same order: what is this, how does it fit together, how do I run it, what can I change, how do I know it works, and what should I not trust. Give each one a heading, in that order. Put the honest part (what is real and what is not) near the top: it makes every later claim believable.

Piece 2: one diagram, boxes that are real

An architecture diagram shows the parts that run (boxes) and who calls whom (arrows, with the protocol or port). One diagram, about six boxes, readable in ten seconds. Use Mermaid: a diagram written as text in the README, which GitHub draws. Because it is text, a program can check it: the boxes must be the services of your compose.yaml, or the picture is lying.

Piece 3: explain each box in one line

After the picture, a table: the name of the box, and one line on what it does. If you cannot say it in one line, the box does too much, or you do not know it yet. That table is also your script for the demo.

If you know another typed language (C# as the example): the check is a unit test for documentation: the same way a test fails when a method is renamed, this script fails when the diagram and the compose file drift apart. A README is the XML doc comment of the whole solution.
Capstone: your repository gets its real README today. Thursday a fresh clone tests it, and Saturday you polish it for the workshop.

The boxes web, gateway, ai, db and ingest are the five services of compose.yaml. user (a person) and model (the writer is chosen by settings) are not services, and the check knows that. A small script, with only the standard library, compares the names (scripts/check_diagram.py):

"""Check that the boxes of the architecture diagram in README.md are the services of compose.yaml (and nothing else).
Only the standard library: it reads the node names of the first mermaid block and the keys under 'services:'. Exit 1 on a difference."""
import re
import sys
from pathlib import Path

root = Path(__file__).resolve().parent.parent
readme = (root / "README.md").read_text(encoding="utf-8")
block = re.search(r"```mermaid\n(.*?)```", readme, re.S)
if block is None:
    sys.exit("README.md has no mermaid block")
# a node is written like  name[text]  name([text])  name[(text)]  name{{text}}, at the start of a line or after an arrow
drawn = set(re.findall(r"(?:^|[\s|])([a-z]\w*)(?:\[\(|\(\[|\{\{|\[)", block.group(1), re.M))
drawn -= {"flowchart", "graph", "subgraph", "end"}

services: set[str] = set()
inside = False
for line in (root / "compose.yaml").read_text(encoding="utf-8").splitlines():
    if re.match(r"^services:\s*$", line):
        inside = True
    elif inside and re.match(r"^\S", line):
        inside = False
    elif inside and (match := re.match(r"^  ([a-z]\w*):", line)):
        services.add(match.group(1))

optional = {"model", "user"}   # boxes that are not services: the person, and the writer (it is chosen by settings)
missing = services - drawn
extra = drawn - services - optional
print(f"compose services: {sorted(services)}")
print(f"diagram boxes:    {sorted(drawn)}")
if missing or extra:
    print(f"NOT in the diagram: {sorted(missing)}   NOT in compose.yaml: {sorted(extra)}")
    sys.exit(1)
print("the diagram and compose.yaml agree")
You should see
compose services: ['ai', 'db', 'gateway', 'ingest', 'web']
diagram boxes:    ['ai', 'db', 'gateway', 'ingest', 'model', 'user', 'web']
the diagram and compose.yaml agree

The whole README of the capstone, as it was written today. Read how it opens (what it is, then what is real), how each section answers one question, and how the table of settings and the list “What has not been run” keep it honest:

The README
# PumpGuard assistant

A small question-and-answer assistant for a **fictional** product (the PumpGuard pump monitor). It finds the right pages of a knowledge base, asks a writer to answer **only from those pages**, adds citations, and says "I could not find that in the knowledge base." when the pages do not hold the answer. A page, a gateway and an AI service work together; a dashboard shows how it is doing.

[![CI](https://github.com/OWNER/REPO/actions/workflows/ci.yml/badge.svg)](https://github.com/OWNER/REPO/actions/workflows/ci.yml)

(replace OWNER and REPO with yours)

## Read this first: what is real and what is not

- The default writer is a **stand-in** (`LLM_MODE=fake`): a small program, **not a model**, so that everything runs and is tested with no key and no cost.
- A real writer is a switch away: a hosted model (`LLM_MODE=real`, needs a key) or a model on your own machine (`LLM_PROVIDER=openai_compatible`). The local path was run once, with a small open-weight model; the hosted path is tested only with a fake HTTP server, never against the real service.
- The knowledge base is made up (26 chunks from 10 pages). The numbers on the dashboard come from a rehearsal, not from users.
- The Docker images and the CI workflow in this repository were **checked as far as possible but never built or run** by the author (see "What has not been run").

## Architecture

```mermaid
flowchart LR
  user([Browser]) -->|HTTP 8080| web[web: nginx and the React page]
  web -->|/api| gateway[gateway: ASP.NET Core]
  gateway -->|HTTP 8000| ai[ai: FastAPI service]
  ai -->|SQL| db[(db: PostgreSQL with pgvector)]
  ingest[ingest: one-off job] -->|fills the table| db
  ai -.->|chat API| model{{writer: stand-in, local model or hosted model}}
```

| Box | What it does, in one line |
|-----|---------------------------|
| web | Serves the React chat page and forwards `/api/` to the gateway. The only box with a public port (8080). |
| gateway | The .NET front door: checks the input, gives each request an id, forwards to the AI service, turns failures into clean errors. |
| ai | The Python service: hybrid search (meaning plus keywords), role filter, grounded answer with citations, guardrails, audit log, metrics. |
| db | PostgreSQL with the pgvector extension: the chunks and their vectors, and the table of requests. |
| ingest | Runs once at start: reads the pages, cuts them into chunks, embeds them, stores them. |
| model | Not a service of this repository: the writer is chosen by settings. |

## Run it with Docker

```bash
cp .env.example .env          # then set your own POSTGRES_PASSWORD in .env
docker compose up -d --build
# then open http://localhost:8080 in your browser
docker compose down           # add -v to delete the database volume
```

## Run it without Docker

You need: Python 3.12 with [uv](https://docs.astral.sh/uv/), .NET 10 SDK, Node 22, and a PostgreSQL 16 or newer **with the pgvector extension** that you can reach with a connection string.

```bash
# 1. the AI service (port 8000)
cd python-service
export DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DBNAME
uv sync
uv run python ingest.py
uv run uvicorn my_ai_project.api:app --port 8000

# 2. the gateway (port 5100), in a second terminal
cd gateway
dotnet run --project AskGateway --urls http://localhost:5100

# 3. the page (port 5173), in a third terminal
cd web/chat-ui
npm ci
npm run dev                   # then open http://localhost:5173
```

In the page, "customer" can ask about the manuals and the FAQ; choose "staff member" to ask about error codes and to see the dashboard.

## Settings

| Variable | Default | Meaning |
|----------|---------|---------|
| `DATABASE_URL` | a local test address | PostgreSQL connection string (it holds a password: keep it out of Git) |
| `LLM_MODE` | `fake` | `fake` = the stand-in writer; `real` = a model |
| `LLM_PROVIDER` | `anthropic` | with `LLM_MODE=real`: `anthropic` or `openai_compatible` |
| `ANTHROPIC_API_KEY` | none | needed for `anthropic` |
| `LLM_BASE_URL`, `LLM_MODEL` | none | needed for `openai_compatible` (for example a local server) |
| `AUDIT_LOG` | `logs/audit.jsonl` | where the audit log is written |

Wrong or missing settings stop the service at the start with a message that names the setting.

## Tests

```bash
cd python-service && uv run pytest -q && uv run mypy src tests
cd gateway && dotnet test AskGateway.Tests
cd web/chat-ui && npm run build
```

The tests that need a database are **skipped** (you will see `skipped` in the summary) unless `TEST_DATABASE_URL` points at a PostgreSQL with pgvector; set it to the same address as `DATABASE_URL` to run them.

CI (`.github/workflows/ci.yml`) runs the same on every push, and builds the images only when the tests are green.

## What has not been run

- The three Docker images were never built, and the Compose stack was never started (checked with `docker compose config` only).
- The GitHub Actions workflow was never run on GitHub (checked with a linter, and every command run by hand).
- `nginx.conf` was never run.
- The hosted model was never called. Ollama and vLLM were never run.

## Known limits

- The role (`staff` or `customer`) comes from a header. It is a demo: a caller can write any role. A real service reads it from a login.
- The answer cache can serve an answer up to its time to live after a page changes.
- The keyword index is built when the service starts: run `ingest.py` and restart after a change.

## Layout

```
python-service/   FastAPI service, ingest, tests, golden questions
gateway/          ASP.NET Core gateway and its tests
web/chat-ui/      React page (Vite) and its nginx file
compose.yaml      the whole system with one command
scripts/          small checks (the diagram check)
```

5 · Try it 30 min

Work in the root of your capstone repository, on a branch: git switch -c readme.

Step 1 Copy and run

Create README.md in the root (if you have one, rewrite it) with the six sections in the order of the stranger’s questions. Copy the shape, not the words: use your project name, your boxes and your commands.

Step 2 Change one thing

Draw the Mermaid diagram of your system with six boxes at most, and a label on every arrow (protocol or port). Predict: which of your boxes is not a service in your Compose file? (A person, a model, a database that is outside.) Then add scripts/check_diagram.py and run it.

Step 3 Break it on purpose

Misspell one box in the diagram and run the check: read the message. Then fix it. Now rename a service in compose.yaml (not the diagram) and run it again. Which side did the script say was wrong? Put both back.

Step 4 Your turn

Write the table: one line for each box. If a line needs “and” twice, split the box or learn what it really does. Add the part everybody skips: what is real and what is not (stand-ins, estimates, things never run), and known limits. Commit: git add README.md scripts/check_diagram.py and git commit -m "Add a README and an architecture diagram".

6 · Stuck? anytime

  • The diagram shows as text on GitHub: the code block must start with three backticks and the word mermaid, nothing else on that line.
  • The check says a box is missing but you drew it: it reads names written like name[text], name([text]), name[(text)] or name{{text}}. A box written another way is not seen.
  • The README is long: put the quick start first and move detail to other files in docs/. The first screen decides.
  • You are not sure what is a stand-in: list everything that was never run against the real thing (a model, a service, a deploy). That list is the section “what has not been run”.
Hint: Step 2

The person using the page and the writer (model) are drawn but are not services. The check lets you list such names as optional.

Solution: Step 3

Answers
