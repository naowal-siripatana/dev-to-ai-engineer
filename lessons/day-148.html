1 · Self-test 25 min

A note on this week. The Docker engine on the author’s laptop did not respond, so the lessons of Day 142 to 147 were checked as far as possible without it: the Compose file with docker compose config, each build step by hand, and the error messages. No image was built and no container was started. Your run is the real one, and section 3 asks you to write down exactly what you ran.

Close your notes. Answer each question in your own words, and write a confidence number next to it: 1 = guessing, 2 = fairly sure, 3 = certain. Then open the answers and mark each one right, partly right or wrong.

  1. What is the difference between an image and a container? (Day 142, 146)
  2. Why do the packages come before the code in a Dockerfile? (Day 142)
  3. What does a multi-stage build give you, and what was the editable-install problem? (Day 142)
  4. Why 0.0.0.0 inside a container, and why a non-root user? (Day 142)
  5. How does one Compose service find another, and which port do you use? (Day 144)
  6. Where does the database password live, and what goes in Git instead? (Day 144)
  7. What do service_started, service_healthy and service_completed_successfully wait for? (Day 145)
  8. Why does only one service publish a port? (Day 147)
  9. What does down keep, what does down -v remove? (Day 144)
Answers
  1. An image is a read-only package; a container is one running copy. Many containers from one image; removing a container leaves the image.
  2. Layers are reused until a line changes. Packages change rarely and code often, so this order keeps the slow layer cached.
  3. The final image only holds what runs, not the tools that built it. An editable install points at the source folder, which the last stage does not have; --no-editable copies the package into the environment.
  4. Inside a container 127.0.0.1 is only that container, so a published port cannot reach it. A plain user limits what a bug or an attacker can do.
  5. By its service name on the Compose network, with the port inside the container (for example db:5432).
  6. In a .env file that Git ignores; an .env.example with a fake value is committed.
  7. Started: the container is running. Healthy: its health check passes. Completed successfully: it ran and exited with 0.
  8. Everything else is reached by name on the private network. Fewer open doors, fewer ways in.
  9. down removes containers and the network and keeps named volumes. down -v removes the volumes too, so the data is gone.

Read your numbers. If you were sure (3) and wrong, that is the most valuable thing you found. Circle those.
