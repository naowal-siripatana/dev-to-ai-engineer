2 · Hook 2 min

Your model provider has an outage at 2 a.m. for ten minutes. What does your assistant do, and what does the user see: an error, a spinner, or an answer?

Guess first, then open

It depends on what you built before the outage. A system that has a timeout (so that it does not wait for ever), a fallback (a second model to try), and a clear message when everything fails, gives an answer or an honest “try again in a minute”. One that has none of these hangs, or shows a stack trace.

3 · The idea, in three small pieces 8 min

Piece 1: a timeout, so that you stop waiting

A model call can hang. Without a limit, your request hangs too, and so does your user. A timeout says “if there is no answer in N seconds, give up”. Choose N from what a good call needs plus some room. One honest limit: in Python you cannot kill a thread, so the slow call keeps running in the background, and its answer is simply ignored.

Piece 2: a fallback, and honesty about which one answered

When the first model fails or is too slow, try a second model. It may be cheaper, weaker or from another provider. Do not hide it: record which model answered in the metrics, so that you can see how often you fall back, and what it costs you in quality. Only fall back on expected failures (a provider error, a timeout). A bug in your own code must still be seen, not hidden by a fallback. And when everything fails, give a clear 503 with a message, not a crash.

Piece 3: a cache trades freshness for speed and cost

If the same question comes again, you can serve the last answer and skip the model: faster and free. But a cache can serve a wrong answer if its key is not complete, and an old one if the knowledge changed. So the key must contain everything that changes the answer, above all the role (an answer made for staff must never be served to a customer), and the limit (the time to live) must be written down.

If you know another typed language (C# as the example): the timeout is a CancellationToken with a deadline (or Polly’s timeout policy), the fallback is Polly’s fallback policy, and the cache is IMemoryCache with an absolute expiration. The same warning applies to the cache key: it is the one place where a missing part becomes a security bug.
Capstone: a real service is judged by what it does when something is wrong. This week you add exactly these, and on Saturday the dashboard shows how often they were needed.

4 · Worked example 5 min

What can go wrong, and what to do about each:

what can go wrong with a model call           what you do                                        what it costs you
it fails (an error, a 503)                    retry (Day 51), then fall back to a second model   a second model to pay for and test
it is slow                                    a TIMEOUT: stop waiting after N seconds             a few answers lost, and a thread you cannot kill
it is down for a while                        fall back, and say so in the metrics                the fallback may be weaker or different
you ask the same thing again and again        a CACHE with a time to live                         an answer may be as old as the TTL
everything fails                               a clear 503 message, not a crash or a blank page    the user waits, and knows why
The models here are stand-ins. We have no key, so the “first model” and the “second model” are small classes: one that works, one that always fails (a 503) and one that sleeps too long. They are not real models. They let you test the system around a model, which is the only part that is the same for every provider.

The module, in src/my_ai_project/reliability.py: with_timeout, FallbackWriter (which remembers which model answered in used), and the AnswerCache with its key. The cache is for Thursday; read the first two now:

import concurrent.futures
import logging
import re
import time
from collections.abc import Callable
from dataclasses import dataclass

from my_ai_project.grounding import Writer
from my_ai_project.llm import LlmError

logger = logging.getLogger("reliability")


class Unavailable(Exception):
    """Every way of getting an answer failed. The caller shows a clear message; it does not crash."""


def with_timeout(call: Callable[[], str], seconds: float) -> str:
    """Give up waiting after some seconds. The slow call keeps running in its thread (Python cannot kill a thread): the answer is simply ignored."""
    pool = concurrent.futures.ThreadPoolExecutor(max_workers=1)
    future = pool.submit(call)
    try:
        return future.result(timeout=seconds)
    except concurrent.futures.TimeoutError as err:
        raise TimeoutError(f"no answer after {seconds} seconds") from err
    finally:
        pool.shutdown(wait=False)


class FallbackWriter:
    """Try the first model; if it fails or is too slow, try the second. `used` says which one answered, for the metrics."""

    def __init__(self, primary: Writer, secondary: Writer | None, timeout: float = 20.0, names: tuple[str, str] = ("primary", "fallback")) -> None:
        self.primary, self.secondary, self.timeout, self.names = primary, secondary, timeout, names
        self.used = names[0]

    def complete(self, prompt: str, system: str | None = None) -> str:
        try:
            return with_timeout(lambda: self.primary.complete(prompt, system), self.timeout)
        except (LlmError, TimeoutError) as err:
            logger.warning("the first model failed (%s: %s)", type(err).__name__, err)
            if self.secondary is None:
                raise Unavailable("the model did not answer and there is no fallback") from err
        secondary = self.secondary
        try:
            self.used = self.names[1]
            return with_timeout(lambda: secondary.complete(prompt, system), self.timeout)
        except (LlmError, TimeoutError) as err:
            logger.error("the fallback model failed too (%s: %s)", type(err).__name__, err)
            raise Unavailable("neither model answered") from err


def normalize(question: str) -> str:
    return re.sub(r"\s+", " ", question.strip().lower())


def cache_key(role: str, question: str, top_k: int) -> str:
    """The role is part of the key: an answer made for staff must never be served to a customer."""
    return f"{role}|{top_k}|{normalize(question)}"


@dataclass
class Entry:
    value: object
    expires_at: float


class AnswerCache:
    """A small in-memory cache with a time to live. It trades freshness for speed and cost, so its limit is written down: an answer can be this old."""

    def __init__(self, ttl_seconds: float = 300.0, max_entries: int = 500, clock: Callable[[], float] = time.monotonic) -> None:
        self.ttl, self.max_entries, self.clock = ttl_seconds, max_entries, clock
        self.entries: dict[str, Entry] = {}
        self.hits = 0
        self.misses = 0

    def get(self, key: str) -> object | None:
        entry = self.entries.get(key)
        if entry is None or entry.expires_at <= self.clock():
            self.entries.pop(key, None)
            self.misses += 1
            return None
        self.hits += 1
        return entry.value

    def put(self, key: str, value: object) -> None:
        if len(self.entries) >= self.max_entries:
            self.entries.pop(next(iter(self.entries)))   # the oldest one goes
        self.entries[key] = Entry(value, self.clock() + self.ttl)

    def clear(self) -> None:
        self.entries.clear()

Five scenarios on the real pipeline (real retrieval, the real question about the alarm), with a timeout of half a second. fallback_demo.py:

import os
import time

from my_ai_project.access import allowed_kinds
from my_ai_project.embedder import FastEmbedder
from my_ai_project.hybrid import KeywordIndex
from my_ai_project.llm import LlmError
from my_ai_project.rag import answer_question
from my_ai_project.reliability import FallbackWriter, Unavailable
from my_ai_project.simulated import SimulatedWriter
from my_ai_project.store import ChunkStore


class Down:
    """A stand-in for a model that is down. NOT a real model."""

    def complete(self, prompt: str, system: str | None = None) -> str:
        raise LlmError("the provider answered 503")


class Slow:
    """A stand-in for a model that takes too long. NOT a real model."""

    def complete(self, prompt: str, system: str | None = None) -> str:
        time.sleep(2.0)
        return "an answer that comes too late"


store = ChunkStore(os.environ.get("DATABASE_URL", "postgresql://assistant:assistant@localhost:5433/assistant"))
embedder, keywords = FastEmbedder(), KeywordIndex(store.all_chunks())
question = "How do I silence the alarm?"
backup = SimulatedWriter()   # the second 'model' is also a stand-in

SCENARIOS = [
    ("1 the first model works", FallbackWriter(SimulatedWriter(), backup, timeout=0.5)),
    ("2 the first model is down", FallbackWriter(Down(), backup, timeout=0.5)),
    ("3 the first model is too slow (timeout 0.5 s)", FallbackWriter(Slow(), backup, timeout=0.5)),
    ("4 both models are down", FallbackWriter(Down(), Down(), timeout=0.5)),
    ("5 the first model is down and there is no fallback", FallbackWriter(Down(), None, timeout=0.5)),
]
for label, writer in SCENARIOS:
    started = time.perf_counter()
    try:
        result = answer_question(question, embedder, store, keywords, writer, allowed_kinds=allowed_kinds("staff"))
        outcome = f"answered by '{writer.used}': {result.text}"
    except Unavailable as err:
        outcome = f"Unavailable: {err}"
    print(f"{label:<52}{(time.perf_counter() - started) * 1000:>6.0f} ms   {outcome}")
You should see
1 the first model works                                 37 ms   answered by 'primary': Open Settings, choose Sound, and set the alarm to Silent [faq-alarm-sound#0].
2 the first model is down                                7 ms   answered by 'fallback': Open Settings, choose Sound, and set the alarm to Silent [faq-alarm-sound#0].
3 the first model is too slow (timeout 0.5 s)          519 ms   answered by 'fallback': Open Settings, choose Sound, and set the alarm to Silent [faq-alarm-sound#0].
4 both models are down                                  22 ms   Unavailable: neither model answered
5 the first model is down and there is no fallback      11 ms   Unavailable: the model did not answer and there is no fallback

(and in the log, one line per failure:)
the first model failed (LlmError: the provider answered 503)
the first model failed (TimeoutError: no answer after 0.5 seconds)
the fallback model failed too (LlmError: the provider answered 503)

Read it. In 2 the failure costs almost nothing (7 ms): the second model answers at once. In 3 the user waits the whole timeout (519 ms) before the second model is tried: a timeout is the price of a slow failure, so choose it with care. In 4 and 5 the answer is a clear Unavailable, which the API turns into a 503. And every failure left a line in the log.

The rules of a safe cache, for Thursday:

a cache is only safe if its KEY contains everything that changes the answer
  the question (normalised: trim, lower case, one space)
  the ROLE      (Day 79: an answer made for staff must never be served to a customer)
  top_k and anything else that changes what is retrieved
and its LIMIT is written down: an answer can be as old as the time to live. After the pages change, the cache can still serve the old answer
until the TTL ends (or until you clear it, or restart).

6 · Stuck? anytime

  • The test for the slow model takes a long time: the slow stand-in sleeps. Keep its sleep short (1 s) and the timeout shorter (0.1 s).
  • Everything is slow after a timeout: the slow thread is still running. That is the limit of threads in Python; a real HTTP client has its own timeout, which you should set as well (timeout=30 in the SDK).
  • The fallback hides a real bug: catch only LlmError and TimeoutError, not Exception.
  • mypy: the type of the writer: both models implement the Writer protocol (complete(prompt, system)).
Solution: Step 2

With 0.1 s the user waits about 0.1 s and the fallback answers; with 3 s the slow model answers after 2 s (it is not too slow any more), so the user waits 2 s and the first model answers. The timeout decides who answers, and how long the user waits.

Solution: Step 3

It must not hide it: a ValueError is a bug, not a provider failure, and falling back would only make the bug harder to see. The test “a bug is not hidden by the fallback” keeps it that way. Fall back on failures you expect, and let the rest crash loudly (in a test, or in a log you read).

  1. What does a timeout cost you?
  2. Why record which model answered?
  3. Why catch only some errors in the fallback?
Answers
  1. A slow failure costs the user the whole timeout before the second try, and the slow call may keep running in the background.
  2. To see how often you fall back and what it does to quality and cost.
  3. A provider error is expected and recoverable; a bug in your own code should not be hidden by a second model.
