2 · Hook 2 min

Your manager asks: “How much does the assistant cost per question, and how fast is it?” You have a log full of text. Can you answer in a minute? What would you need to have stored?

Guess first, then open

One row per request with numbers: latency, input tokens, output tokens, cost, and how it ended. Then the answer is a SQL query. A log is for reading one request; a table is for answering questions about all of them.

3 · The idea, in three small pieces 8 min

Piece 1: three numbers per request

For every request, store latency (how long it took), tokens (input and output) and cost (from tokens and a price), together with how it ended: answered, refused, or error. Put them in a table in PostgreSQL, one row per request, with the request id. Now you can count, average, find the slow ones, and add up the cost.

Piece 2: be exact about what a number means

A missing number is not zero. NULL means “not measured” (a failed request, a tool loop that does not report tokens yet). 0 means “measured, and it was zero” (a question refused before the model was called costs nothing). Mixing them gives averages that lie. Also say where each number comes from: an estimate with a tokenizer is not the billed number, and a price in a config file is an example until you check it.

Piece 3: recording must never break the request

Writing a metrics row happens at the end of every request. If the database is down, the row is lost, and that is acceptable; failing the user’s request is not. So the writer catches database errors and logs a warning, like the audit log. Note the irony: when the database is down, your metrics table is down too, so the log lines are what you have left.

If you know another typed language (C# as the example): it is the same as request-duration and request-count metrics that you would export from ASP.NET Core (for example with OpenTelemetry), only stored in a SQL table you can query. The percentile (percentile_cont) is what you would otherwise read off a histogram.
Capstone: next week the five numbers of the dashboard (question count, success rate, average time, total cost, failed queries) come straight from this table.

4 · Worked example 5 min

The formula, and the difference between “not measured” and “zero”:

cost = (input_tokens x price_in + output_tokens x price_out) / 1,000,000
e.g. 240 in, 14 out at 1.00 and 5.00 per million:  (240 x 1.00 + 14 x 5.00) / 1,000,000 = 0.000310 USD

NULL   = not measured     (the request failed, or the tool loop does not report tokens yet)
0      = measured, and zero  (the model was never called)
These are different facts. Never store a missing number as 0.
What is real, and what is not. No real model was called, so there are no billed tokens and no model latency. The tokens are estimates made with tiktoken, and the prices are example values (1 and 5 US dollars per million tokens). The numbers show how the system works; replace the price and the token source with real ones when you have them.
tokens        ESTIMATED with tiktoken (the o200k_base tokenizer). A model counts with its own tokenizer, so the billed number will differ.
              With a real model, store the 'usage' that the API returns, and keep the estimate only as a fallback.
prices        EXAMPLE values in a config. Check your provider's price list, and note the date. Prices change.
latency       here: without a model call. A real call adds hundreds of milliseconds to seconds, and it will dominate.
cost          a model call is only part of the cost: the database, the servers and your time are not in this table.

The metrics module, in src/my_ai_project/metrics.py: the cost function, the table, and a store that writes one row and never raises:

import logging
import os
from dataclasses import dataclass
from typing import Protocol

import psycopg

logger = logging.getLogger("metrics")

# EXAMPLE prices in US dollars per million tokens. They are placeholders: put the real prices of YOUR model here, from its price list.
PRICES_PER_MILLION = {"input": 1.00, "output": 5.00}


def cost_usd(input_tokens: int | None, output_tokens: int | None, prices: dict[str, float] | None = None) -> float | None:
    """None means 'not measured'. 0.0 means 'measured, and it was free' (for example: no model was called)."""
    if input_tokens is None or output_tokens is None:
        return None
    price = prices or PRICES_PER_MILLION
    return (input_tokens * price["input"] + output_tokens * price["output"]) / 1_000_000


@dataclass
class RequestMetrics:
    request_id: str
    route: str
    role: str
    status_code: int
    latency_ms: float
    outcome: str                 # answered, refused, error
    model: str
    input_tokens: int | None     # None = not measured
    output_tokens: int | None


class Metrics(Protocol):
    def record(self, row: RequestMetrics) -> None: ...


SCHEMA = """
CREATE TABLE IF NOT EXISTS requests (
    id bigserial PRIMARY KEY,
    time timestamptz NOT NULL DEFAULT now(),
    request_id text NOT NULL,
    route text NOT NULL,
    role text NOT NULL,
    status_code int NOT NULL,
    latency_ms real NOT NULL,
    outcome text NOT NULL,
    model text NOT NULL,
    input_tokens int,
    output_tokens int,
    cost_usd numeric(12, 6)
);
CREATE INDEX IF NOT EXISTS requests_time_idx ON requests (time);
CREATE INDEX IF NOT EXISTS requests_request_id_idx ON requests (request_id);
"""


class MetricsStore:
    """One row per request in PostgreSQL: how long it took, what it cost, how it ended."""

    def __init__(self, dsn: str) -> None:
        self.dsn = dsn
        self.ready = False

    def record(self, row: RequestMetrics) -> None:
        """Never raises: if the database is down, the metrics are lost, but the user's request must not be."""
        try:
            with psycopg.connect(self.dsn) as conn:
                if not self.ready:
                    conn.execute(SCHEMA)
                    self.ready = True
                conn.execute(
                    "INSERT INTO requests (request_id, route, role, status_code, latency_ms, outcome, model, input_tokens, output_tokens, cost_usd) "
                    "VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s, %s)",
                    (row.request_id, row.route, row.role, row.status_code, row.latency_ms, row.outcome, row.model,
                     row.input_tokens, row.output_tokens, cost_usd(row.input_tokens, row.output_tokens)),
                )
        except psycopg.Error as err:
            logger.warning("could not store the metrics of %s: %s", row.request_id, err)


def default_store() -> MetricsStore:
    """The metrics go to the same database, unless METRICS_DATABASE_URL says otherwise."""
    return MetricsStore(os.environ.get("METRICS_DATABASE_URL") or os.environ.get("DATABASE_URL", "postgresql://assistant:assistant@localhost:5433/assistant"))

Look at three things. The first request took 3584 ms and the rest a median of 8 ms: a cold start, which an average (187 ms) hides, so always look at the median and the worst case. Refused questions cost nothing. And the whole run cost under half a cent at the example prices, with a stand-in writer: with a real model, the cost and the latency will be very different, and you will want this table to tell you by how much.

6 · Stuck? anytime

  • No rows appear: check the database address, and the warning in the log (the store never raises, so a failure is only a warning). Check that the route starts with /api/.
  • Every refused row has tokens: only a refusal after the writer was called has tokens; one before it has 0.
  • The average is far from the median: one very slow request (usually the first). Look at the median and the maximum.
  • The cost is 0 everywhere: the tokens are 0 (no model call) or NULL (not measured). Cost needs both tokens and a price.
Solution: Step 2

A refused question that never reached the writer uses 0 tokens and costs 0.000000: the gate saved the call. The first request after a start is much slower than the rest (here 3584 ms against 8 ms), because the Python service loads its model and builds its keyword index when the first request arrives.

Solution: Step 3

Yes: the user gets the answer, because the store catches the error. The row is lost, and the only trace is a warning line in the application log (“could not store the metrics of ...”) with the request id. If you must not lose rows, write them to a local file as well, and load them later: a decision for when the numbers become important.

Solution: Step 4 (the query)
SELECT request_id, route, round(latency_ms::numeric) AS ms, outcome
FROM requests
ORDER BY latency_ms DESC
LIMIT 5;

7 · Check yourself 5 min

  1. Which three numbers do you store for every request, and what else?
  2. What is the difference between NULL and 0 for the tokens?
  3. Why must storing the metrics never raise an error?
Answers
  1. Latency, tokens (input and output) and cost, plus how the request ended (answered, refused, error) and its request id.
  2. NULL means not measured; 0 means measured and zero (for example no model call). Mixing them makes the averages lie.
  3. The metrics are a by-product; if the database is down the row is lost, but the user’s request must not fail because of it.
