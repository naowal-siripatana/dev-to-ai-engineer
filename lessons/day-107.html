DAY 107 · LEVEL 9: CODING AGENTS

AI coding assistants versus agents

60-70 minhands-onfree
Today you will be able to give a coding agent one small task, read its steps, and judge how it worked.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. What goes into a golden item?
  2. Why is a change checked against the whole table and not only the fixed question?
Answers
  1. An id, the question, the expected sources, optional phrases for the answer, and whether it should be refused.
  2. A change that fixes one question often breaks another.

2 · Hook 2 min

You ask a chat assistant to “add a --top-k option to my script”. It writes a snippet. You paste it in, run the script, find a problem, and go back. Now imagine that it could read your files, make the edit, run the script, see the problem and fix it, all on its own. What changes for you?

Guess first, then open

The loop you were doing by hand (read, edit, run, look) moves inside the tool: that is an agent. It is the loop of Day 93 with tools for files and commands. You do less typing and more checking, because the changes arrive fast, in several places, and some of them you did not ask for.

3 · The idea, in three small pieces 8 min

Piece 1: an assistant suggests, an agent acts

An AI coding assistant (a chat window, or completion in your editor) gives you text, and you decide what to do with it. A coding agent runs in your repository with tools: it searches and reads files, edits them, and runs commands (tests, scripts, git). It repeats think, act and observe until it believes the task is done. The table below shows the difference.

Piece 2: its steps are visible, and you should read them

A good agent shows what it did: which files it read, what it changed, which commands it ran and what came back. Reading the steps tells you whether it understood the code (did it look before it edited?) and whether it checked its own work (did it run something?). An agent that edits without reading, or says “done” without running anything, is one to watch.

Piece 3: you set the limits

You decide the branch it works on, the size of the task, which commands it may run without asking, and what it must never touch. These limits do the same job as the step limit and the approval of Week 14, only now the agent writes the code that goes into your repository. The most important limit comes after the work: you read the diff, like a pull request.

If you know another typed language (C# as the example): compare it to IDE refactoring tools. A refactoring does one well-defined change that you can trust. An agent does a loosely defined change in several files, so it is closer to a new colleague who sends you a pull request: useful, fast, sometimes wrong, and your name is on the merge.
Capstone: Module 9 ends with a feature of ai-knowledge-assistant built by a coding agent and reviewed by you, with an instructions file in the repository.

5 · Try it 30 min

Use any coding agent you have: Claude Code, an agent mode in your editor, or another tool. Work in my-ai-project.

Step 1 Prepare

Commit what you have, and make a branch: git switch -c feature/top-k. Check that uv run pytest and uv run mypy src tests pass, and save your run_golden.py table as the baseline.

Step 2 Give it the same small task

Give the agent the task text above (or a close one). Let it work, and watch its steps. Do not help.

Step 3 Write down its steps

Fill in a table like the one in the worked example: the step, the tool, what it did, what it learned. (If your agent runs several commands in one step, list them separately.) Mark the steps where it read before it edited, and the steps where it ran something to check.

Step 4 Judge it

Answer in your notebook: Did it read before it edited? Did it check its own work? Did it touch a file you did not expect? Did it make a decision that the task did not ask for? Then read git diff, line by line, before you read its own summary.

Commit if you are happy: git add . and git commit -m "Add --top-k to run_golden.py".

6 · Stuck? anytime

  • The agent asks for permission to run commands: that is good. Allow the test and the script commands, and read any other command before you allow it.
  • The agent changed more files than you expected: do not merge. Ask why, or throw the branch away (git switch main, git branch -D feature/top-k) and give a smaller task.
  • You have no coding agent: do the task yourself with a chat assistant, and write the table as if you were the agent. You will see which steps were really yours.
  • Its answer differs from the diff: believe the diff. The summary is what the agent says; the diff is what it did.
Rules before you start
Before you let an agent work:
 - a git branch (so every change can be thrown away)
 - a small, clear task (one feature, one fix)
 - permission to read and edit files, but ask before commands that delete, install or reach the network
 - no secrets in reach (.env, keys, production data)
 - tests and a type check that it can run
After it works:
 - read the whole diff before you read the explanation
What to look for in the steps

Good signs: it searched or read before it edited, it ran the script or the tests after, it looked at the output, and it fixed something it saw. Warning signs: it edited a file it never read, it said “done” without running anything, it ran a command you did not expect, or it changed files outside the task.

7 · Check yourself 5 min

  1. What is the difference between a coding assistant and a coding agent?
  2. Why read the steps, and not only the result?
  3. Why work on a branch?
Answers
  1. An assistant suggests text and you apply it. An agent reads and edits files and runs commands itself, in a loop.
  2. The steps show whether it understood the code (it read first) and checked its work (it ran something). The result alone does not.
  3. So that any change can be thrown away, and the diff against the main branch shows exactly what the agent did.
