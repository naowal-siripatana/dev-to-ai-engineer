Project Lab 9: chunks in Postgres

2.5 hhands-onfree
Today you will be able to store chunks with their metadata in Postgres, and return the nearest 3 with one SQL query, with tests that skip when the database is down.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Why do you write an upsert and not a plain insert when you fill the database?
  2. What does an HNSW index trade for speed?
Answers
  1. So the script can run twice without a duplicate key error or doubled data.
  2. Exactness: it finds almost the same nearest rows, not always exactly the same (the recall is below 100 percent), and it takes time and memory to build.

2 · Hook 2 min

On Day 35 you cut documents into chunks of at most 40 tokens, in memory. Tomorrow someone asks: “Which chunk came from which document, and where in it?” What does a chunk need to carry with it to answer that?

Guess first, then open

At least the document id and the position of the chunk in it. That is called metadata: facts about the text. Without them an answer cannot say where it came from. Today every chunk is stored with its document id, its index and its token count, next to the vector.

3 · The idea, in three small pieces 8 min

Piece 1: one row per chunk

The table chunks has one row for each chunk: the doc_id, the chunk_index (its position in the document), the text, its number of tokens and its embedding. A unique constraint on (doc_id, chunk_index) says that one position of one document can only exist once, which is what makes the upsert possible.

Piece 2: a small class owns the SQL

A class ChunkStore hides the SQL from the rest of the code: init_schema, add_chunks, count and search. The rest of your app asks for chunks and does not know the table. Two safety rules: values always go in as parameters (never glued into the SQL text), and a table name, which cannot be a parameter, is checked against a strict pattern first.

Piece 3: test the database part without losing your data

Tests that need a database are slower and need Docker. Use a separate table name for the tests, drop it before and after, and skip the tests (do not fail them) when the database is not running. That way a friend who has no Docker can still run the other tests.

If you know another typed language (C# as the example): ChunkStore is a repository class over Npgsql or Dapper, sql.Identifier is like quoting an identifier safely instead of building SQL strings, and skipping a test when the database is down is like marking an integration test with a category that CI runs only when a container is available.
Capstone: this is the real storage of ai-knowledge-assistant. Next week you add more metadata (language, product, type) and a search endpoint that returns cited chunks.

import re
from dataclasses import dataclass

import numpy as np
import psycopg
from pgvector.psycopg import register_vector
from psycopg import sql

from my_ai_project.chunking import Chunk

TABLE_NAME = re.compile(r"^[a-z_][a-z0-9_]*$")


@dataclass
class Found:
    doc_id: str
    chunk_index: int
    text: str
    similarity: float


class ChunkStore:
    def __init__(self, dsn: str, table: str = "chunks", dims: int = 384) -> None:
        if not TABLE_NAME.match(table):
            raise ValueError(f"not a safe table name: {table!r}")
        self.dsn = dsn
        self.table = sql.Identifier(table)
        self.index = sql.Identifier(f"{table}_embedding_idx")
        self.dims = dims

    def connect(self) -> psycopg.Connection:
        conn = psycopg.connect(self.dsn)
        register_vector(conn)
        return conn

    def init_schema(self) -> None:
        with self.connect() as conn:
            conn.execute(
                sql.SQL(
                    "CREATE TABLE IF NOT EXISTS {table} ("
                    "id bigserial PRIMARY KEY, doc_id text NOT NULL, chunk_index int NOT NULL, "
                    "text text NOT NULL, tokens int NOT NULL, embedding vector({dims}) NOT NULL, "
                    "UNIQUE (doc_id, chunk_index))"
                ).format(table=self.table, dims=sql.Literal(self.dims))
            )
            conn.execute(
                sql.SQL("CREATE INDEX IF NOT EXISTS {index} ON {table} USING hnsw (embedding vector_cosine_ops)").format(
                    index=self.index, table=self.table
                )
            )

    def add_chunks(self, chunks: list[Chunk], vectors: np.ndarray) -> int:
        query = sql.SQL(
            "INSERT INTO {table} (doc_id, chunk_index, text, tokens, embedding) VALUES (%s, %s, %s, %s, %s) "
            "ON CONFLICT (doc_id, chunk_index) DO UPDATE SET "
            "text = EXCLUDED.text, tokens = EXCLUDED.tokens, embedding = EXCLUDED.embedding"
        ).format(table=self.table)
        with self.connect() as conn:
            for chunk, vector in zip(chunks, vectors):
                conn.execute(query, (chunk.doc_id, chunk.index, chunk.text, chunk.tokens, vector))
        return len(chunks)

    def count(self) -> int:
        with self.connect() as conn:
            row = conn.execute(sql.SQL("SELECT count(*) FROM {table}").format(table=self.table)).fetchone()
        return int(row[0]) if row else 0

    def search(self, query_vector: np.ndarray, top_k: int = 3) -> list[Found]:
        query = sql.SQL(
            "SELECT doc_id, chunk_index, text, 1 - (embedding <=> %s) AS similarity "
            "FROM {table} ORDER BY embedding <=> %s LIMIT %s"
        ).format(table=self.table)
        with self.connect() as conn:
            rows = conn.execute(query, (query_vector, query_vector, top_k)).fetchall()
        return [Found(doc_id, chunk_index, text, round(float(similarity), 2)) for doc_id, chunk_index, text, similarity in rows]

    def drop(self) -> None:
        with self.connect() as conn:
            conn.execute(sql.SQL("DROP TABLE IF EXISTS {table}").format(table=self.table))

A script that chunks the knowledge base with your splitter from Day 35, embeds the chunks, and stores them. ingest.py:

from pathlib import Path

from my_ai_project.chunking import chunk_documents
from my_ai_project.embedder import FastEmbedder
from my_ai_project.knowledge_base import load_knowledge_base
from my_ai_project.store import ChunkStore

DSN = "postgresql://assistant:assistant@localhost:5433/assistant"

documents = load_knowledge_base(Path("data/kb"))
chunks = chunk_documents(documents, max_tokens=40)
vectors = FastEmbedder().embed([f"{chunk.text}" for chunk in chunks])

store = ChunkStore(DSN)
store.init_schema()
store.add_chunks(chunks, vectors)
print(f"stored {len(chunks)} chunks from {len(documents)} documents; rows in the table: {store.count()}")

And the query that the lab is about: one SQL query that returns the nearest 3 chunks. Here the question is the first chunk of error-e101 itself, so you can see it come out first with a similarity of 1.00. nearest.sql:

SELECT doc_id, chunk_index, left(text, 40) AS start_of_text,
       round((1 - (embedding <=> (SELECT embedding FROM chunks WHERE doc_id = 'error-e101' AND chunk_index = 0)))::numeric, 2) AS similarity
FROM chunks
ORDER BY embedding <=> (SELECT embedding FROM chunks WHERE doc_id = 'error-e101' AND chunk_index = 0)
LIMIT 3;

6 · Stuck? anytime

  • “type vector does not exist”: the extension is not on in that database. Run CREATE EXTENSION vector;, or reset with docker compose down -v and up -d.
  • “expected 384 dimensions, not 64”: a table was created with another size. The tests use chunks_test with 64 dimensions, and the app uses chunks with 384. Do not mix the tables.
  • Ingest says 26 rows the first time and 52 the second: the upsert is missing, or the unique constraint is not on (doc_id, chunk_index).
  • The tests are skipped: the database is not running, or the connection string differs. Check docker compose ps.
  • Your first results differ from the lesson: your chunk size or your documents differ. Compare the number of chunks first.
Hint: Part C

Use psycopg.sql to build statements: sql.Identifier(table) for the name and sql.Literal(dims) for the size, and %s parameters for the values. The upsert is INSERT ... ON CONFLICT (doc_id, chunk_index) DO UPDATE SET .... For the search use the same vector twice: in the similarity column and in ORDER BY embedding <=> %s LIMIT %s.

Solution: Part G (tests)
import os
from collections.abc import Iterator

import psycopg
import pytest

from my_ai_project.chunking import Chunk
from my_ai_project.embedder import FakeEmbedder
from my_ai_project.store import ChunkStore

DSN = os.environ.get("TEST_DATABASE_URL", "postgresql://assistant:assistant@localhost:5433/assistant")

CHUNKS = [
    Chunk(doc_id="error-e101", index=0, text="Check the sensor cable and restart the monitor.", tokens=9),
    Chunk(doc_id="faq-battery", index=0, text="The battery lasts about eight hours.", tokens=7),
    Chunk(doc_id="faq-wifi", index=0, text="Only 2.4 GHz networks are supported.", tokens=8),
]


@pytest.fixture
def store() -> Iterator[ChunkStore]:
    chunk_store = ChunkStore(DSN, table="chunks_test", dims=64)
    try:
        chunk_store.drop()
    except psycopg.OperationalError:
        pytest.skip("the database is not running: start it with docker compose up -d")
    chunk_store.init_schema()
    yield chunk_store
    chunk_store.drop()


def test_the_nearest_chunk_comes_first(store: ChunkStore) -> None:
    embedder = FakeEmbedder()
    store.add_chunks(CHUNKS, embedder.embed([c.text for c in CHUNKS]))
    found = store.search(embedder.embed(["sensor cable restart"])[0], top_k=2)
    assert [f.doc_id for f in found][0] == "error-e101"
    assert len(found) == 2


def test_adding_the_same_chunks_twice_does_not_duplicate_them(store: ChunkStore) -> None:
    vectors = FakeEmbedder().embed([c.text for c in CHUNKS])
    store.add_chunks(CHUNKS, vectors)
    store.add_chunks(CHUNKS, vectors)
    assert store.count() == 3


def test_an_unsafe_table_name_is_rejected() -> None:
    with pytest.raises(ValueError, match="not a safe table name"):
        ChunkStore(DSN, table="chunks; DROP TABLE chunks")

7 · Check yourself 5 min

  1. Why does the table have a unique constraint on (doc_id, chunk_index)?
  2. Why is the table name checked, and the values passed as parameters?
  3. Why do the database tests skip themselves when the database is not running?
Answers
  1. One position of one document can exist only once, so you can upsert: the same chunk written twice updates the row instead of adding a copy.
  2. Values go in as parameters so that text from a document or a user can never become SQL. A table name cannot be a parameter, so it is checked against a strict pattern before it is used.
  3. So that people without Docker, or with the database stopped, can still run the other tests and see a clean result. A skipped test says “not run”, and a failed test says “broken”.
