Mixed practice: the incident lookup as an MCP tool

40 minhands-onfree
Today you will be able to expose a lookup as an MCP tool that obeys the same rules as your own loop, from a blank file.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Between which two parties does MCP work, and between which does function calling?
  2. Why must a stdio server not print to standard output?
Answers
  1. MCP: the host and the tools (a server). Function calling: the host and the model.
  2. Standard output carries the protocol messages; extra text can break them. Use standard error for logs.

2 · The contract 5 min

Today there is no code to copy. You get a contract, and you write the server and the client yourself, from blank files. Use tool_design.py from Monday and what you learned on Wednesday.

Hint: where to start

Copy the shape of word_server.py. Inside the tool call execute("mcp", "lookup_error", {"code": code}, ROLE). If the result has is_error, raise ToolError (from mcp.server.mcpserver.exceptions) with the content; otherwise return the content. In the client, pass the role to the server process with env={"INCIDENT_ROLE": role, "PYTHONPATH": "src"} in StdioServerParameters.

Solution
import os

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

from my_ai_project.tool_design import LOOKUP_TOOL, execute

# The role is decided by whoever starts the server (here an environment variable), not by the model.
ROLE = os.environ.get("INCIDENT_ROLE", "customer")

mcp = MCPServer("incident-lookup")


@mcp.tool(description=LOOKUP_TOOL["description"])
def lookup_error(code: str) -> str:
    result = execute("mcp", "lookup_error", {"code": code}, ROLE)
    if result.get("is_error"):
        raise ToolError(str(result["content"]))   # becomes a result with isError = true
    return str(result["content"])


if __name__ == "__main__":
    mcp.run()

call_incident_server.py:

import asyncio
import sys

from mcp import Client, StdioServerParameters

CALLS = [("staff", "E104"), ("staff", "104"), ("staff", "E999"), ("customer", "E104")]


async def main() -> None:
    for role, code in CALLS:
        server = StdioServerParameters(command=sys.executable, args=["incident_server.py"], env={"INCIDENT_ROLE": role, "PYTHONPATH": "src"})
        async with Client(server) as client:
            if (role, code) == CALLS[0]:
                print("tools:", [tool.name for tool in (await client.list_tools()).tools])
            result = await client.call_tool("lookup_error", {"code": code})
            print(f"role={role:<9}code={code:<5}is_error={result.is_error}")
            print("   ", result.content[0].text)


asyncio.run(main())

Read the four results

The staff call returns the record. The format error and the unknown code come back with the hints of Monday, now wrapped by the protocol as a tool error. The customer is refused before anything is looked up. All four use the same execute as your function-calling loop, so the rules live in one place and both ways of reaching the tool obey them.

Why is the role in an environment variable? Whoever starts the server decides who it works for. If the role were an argument of the tool, the model could write role=staff itself.

4 · Check yourself 5 min

  1. Why does the MCP tool call execute and not repeat the checks?
  2. Why must the role not be an input of the tool?
  3. What is the difference between this server and the function-calling loop of Wednesday last week, in what the model sees?
Answers
  1. One place for the rules: a fix or a new rule applies to every way of calling the tool.
  2. The model chooses the input, so it could choose a role. The role comes from outside, from whoever started the server or from a login.
  3. The model sees the same thing: a tool with a name, description and schema. The difference is where the tool lives and how the host finds and calls it.
