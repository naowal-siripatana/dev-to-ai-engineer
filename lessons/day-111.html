Teach-back: how to review AI-written code

30 minhands-onfree
Today you will be able to explain in 5 sentences how to review code written by an agent, with examples of what a review finds that tests do not.

1 · Warm-up: write down what you know 5 min

Close your notes. A colleague says: “The agent wrote it and the tests pass. Why would I read every line?” Write what you would answer in two lines. Then write one thing that tests do not catch, and one thing a quick read does not catch.

Do not look anything up. Your guess is the most useful line you will write today.

2 · Explain it 10 min

Your task: explain how to review code written by an AI agent in 5 sentences or a 60-second voice note.

  • Who you are talking to: the colleague above, who wants to merge when the tests are green.
  • Use these words: diff, edge case, silent failure, scope, responsible.
  • Rules: no notes, and give one example from your own runs.

Write it or record it now. A rough first try is exactly right.

Stuck? Sentence starters

Use these if you freeze:

1. AI-written code looks ..., so I review it as ... : a pull request from ... .
2. I read the diff before the ... , because the summary is what it ..., the diff is what it ... .
3. I run it with ... input, because the problems are in ... .
4. I check what it did NOT do: ... .
5. I stay responsible because ... .

3 · Check it against the key points 8 min

Read the six key points and tick each one that your explanation said clearly. Be strict.

  1. Review it like a pull request from a fast colleague who never tires and sometimes invents: it can be right, and confidently wrong.
  2. Read the diff before the summary: the summary is what the agent says it did; the diff is what it did.
  3. Run it with wrong inputs: agents write for the happy path. The problems are in empty, odd and wrong input, and in failures.
  4. Look for silent failures and side effects: an error that looks like success, a file that is overwritten, data that is logged or sent.
  5. Check what is missing: tests for the new behaviour, unrelated changes, new dependencies, secrets or private data.
  6. You stay responsible: the merge is yours. Keep diffs small so that you can really review them, and verify “tests pass” yourself.
A model answer in 5 sentences

I review code from an agent like a pull request from a fast colleague who never tires and is sometimes confidently wrong. I read the diff before the summary, because the summary is what the agent says it did and the diff is what it did. I run the feature with wrong and empty input, because agents write for the happy path: in my own run a typo in a question id ran zero questions, printed ‘passed 0/0’ and exited with code 0, while the tests were green. I also check what it did not do, such as tests for the new behaviour, and what it overwrites or logs, such as a log folder with user questions inside the repository. The merge is my decision, so I keep the diff small enough to review and I run the tests myself.

Count your ticks. 6: very clear. 3 to 5: good, you found your gaps. 0 to 2: also fine, the next step fills them in.

4 · Look at the evidence 5 min

Do not trust the argument. Here is what the real runs of this module showed, and how each problem was found:

Day 107  --top-k: the agent ran the script with 0, saw nonsense (hit@0 0%), and added a check.
                 Found by: RUNNING with a value the task did not mention.
Day 110  --only: a typo in the ids ran 0 questions, printed 'passed 0/0', exit code 0.
                 Found by: RUNNING with a wrong input. The tests were green; none tested the new option.
Day 110  --only: a partial run wrote the same report file as a full run.
                 Found by: READING the diff with the question 'what does it overwrite?'
Day 112  question log: pytest passed, but left a logs/ folder with user questions inside the repository.
                 Found by: RUNNING pytest and then 'git status'.
Day 112  question log: if the log could not be written, the answer request would fail.
                 Found by: READING the diff with the question 'what if this fails?'

The checklist that found them:

1  Does it do what I asked? (run it)
2  Wrong, empty and odd inputs?
3  Silent failures?  (an error that looks like success)
4  What does it overwrite, delete, send or log?
5  Tests: do they test the NEW behaviour?
6  Unrelated changes? Is every line needed?
7  Secrets, privacy, permissions?
8  Did I see tests, types and the score table pass myself?

Look at the pattern. In every case the agent’s first version worked for the normal case, and the problem was found by running it differently or by asking a question of the diff, never by the green tests alone. An explanation that says “AI code is full of bugs” is wrong; one that says “AI code is usually fine for the normal case, and its risks are at the edges, so I check the edges” is right.
