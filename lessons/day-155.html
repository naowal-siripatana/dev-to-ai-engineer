1 · Self-test 25 min

A note on this module. The Docker images and the GitHub Actions workflow of Module 13 were checked as far as possible without a working Docker engine and without a GitHub repository: the Compose file with docker compose config, every command of every job by hand, and a workflow linter. Your runs are the real ones, and section 3 asks you to write down exactly what you ran.

Close your notes. Answer each question in your own words, and write a confidence number next to it: 1 = guessing, 2 = fairly sure, 3 = certain. Then open the answers and mark each one right, partly right or wrong.

  1. Name the three kinds of setting, and where each one lives. (Day 149)
  2. Why does one class read all the settings, and what does SecretStr do? (Day 149)
  3. You committed a password and removed it in the next commit. What is true, and what do you do? (Day 149, 153)
  4. What are a workflow, a job and a step? (Day 151)
  5. What does needs do, and how does a failing test block the build? (Day 151, 152)
  6. Why does CI use a fake writer, a service container and a throwaway password? (Day 151)
  7. Why does || true make a gate useless? (Day 152)
  8. What is the difference between a red mark and a blocked merge? (Day 152)
  9. What does your badge show, and what does it not show? (Day 154)
Answers
  1. Safe defaults in the code; settings that change by place in the environment; secrets in the environment too, and never in Git (a .env file that Git ignores, or the secret store of the host).
  2. One place to check, to type and to document the settings; a wrong or missing value fails early with a clear message. SecretStr prints as stars, so a log or a crash report does not copy the value.
  3. The history still holds it, and so does every clone. Replace the secret at its source first and revoke the old one; then clean up the history if you want to.
  4. A workflow is the file (when and what); a job runs on its own fresh machine; a step is one action or one command inside a job.
  5. A job with needs starts only when the jobs it names are green and is skipped if one fails. So a red test job leaves the build job grey.
  6. CI must not need a real key or a real password: a leak would cost money or touch real data, and a test run must not depend on a model or a shared database.
  7. It runs true when the command fails, so the line exits with 0 and the step passes.
  8. The red mark tells; a branch protection rule (a setting on GitHub) can refuse the merge while a named check is not green.
  9. It shows the result of the last run of the workflow. It does not show the quality of answers, a deploy, or that the images run.

Read your numbers. If you were sure (3) and wrong, that is the most valuable thing you found. Circle those.
