1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. What does the demo check prove, and what does it not?
  2. What do you do in the second rehearsal that you do not do in the first?
Answers
  1. That every beat works on the running system. Not that the page, the screen share or you will go well.
  2. You do not stop, whatever happens: you say your fallback line and carry on.

2 · Today 2 min

Today you practise without the lesson open. Goal: a script that tells you in a second whether your demo path works, and a dry run of your demo for one real person. You write the check from a blank file, then run the dry run, then compare with the model.

Be clear about what was run. The check below was run for real on one laptop (the capstone, from a fresh clone, with the stand-in writer), also with a wrong expectation and with the AI service off. The dry run with a friend was not carried out by the author: it is a procedure with sheets, and your friend’s feedback will be your own.

3 · Plan first 5 min

On paper: list the beats of your demo, one line each, and for each beat write what the system must return for the beat to count (an exact phrase, a status code, a number that must be at least 1). Which beats cannot be checked by a script (the page, your voice)? Those are what the friend is for. Choose the friend: someone who has not seen the project, who will tell you the truth, and who is not a developer if you can find one.

4 · Do it from a blank file 25 min

  1. The helper. A function that sends one request to your system (a method, a path, a role, a body) and returns the status and the JSON, without crashing on an HTTP error.
  2. One function per beat. Each calls the helper and asserts what the beat promises, with the actual answer in the message.
  3. The runner. It runs every beat, prints its name, ok or FAILED with the reason, and the time. It exits with 1 if any failed, so that another script can use it.
  4. Run it. Fix what fails. Then run the full demo once.
  5. The dry run. Follow the protocol below with your friend, and fill in the sheet.

Break it on purpose: (a) change one expectation to a wrong value and read the message; (b) switch off the service behind your front door and run the check.

DRY RUN WITH A FRIEND (45 minutes)
before     run the demo check; start from the README; warm up; close what is not needed
setup      the friend sits where the audience will; you share the screen the way you will on the day
ground rules   you do NOT explain or defend while they watch. They write down, they do not interrupt (questions at the end)
the run    your full 3 minutes, with a timer, as if it were real. If it breaks, say your fallback line and carry on
after      5 minutes: they say what they understood, in their own words (this is the test)
           then the sheet below, then the questions you are afraid of

5 · Compare with the model 10 min

Open these only after your own try.

The demo check
"""The demo, as a test: run every beat of the demo script against the running system and check what comes back.
Usage: python scripts/demo_check.py [base_url]     Exit code 1 if any beat is wrong. Run it before every demo, and before every friend sees it."""
import json
import sys
import time
import urllib.error
import urllib.request

BASE = sys.argv[1] if len(sys.argv) > 1 else "http://localhost:5100"


def call(method: str, path: str, role: str | None = None, question: str | None = None) -> tuple[int, dict[str, object]]:
    headers = {"content-type": "application/json", **({"x-demo-role": role} if role else {})}
    data = json.dumps({"question": question}).encode() if question is not None else None
    request = urllib.request.Request(BASE + path, data=data, method=method, headers=headers)
    try:
        with urllib.request.urlopen(request, timeout=60) as response:
            return response.status, json.loads(response.read())
    except urllib.error.HTTPError as err:
        return err.code, {}


def ask(role: str, question: str) -> dict[str, object]:
    status, body = call("POST", "/api/ask", role, question)
    assert status == 200, f"HTTP {status}"
    return body


def beat_calibration() -> None:
    body = ask("customer", "How often should I calibrate the sensor?")
    assert "once a month" in str(body["answer"]) and "[manual-calibration#0]" in str(body["answer"]), body["answer"]


def beat_refusal() -> None:
    body = ask("customer", "Where can I buy a coffee?")
    assert body["refused"] is True and body["sources"] == [], body["answer"]


def beat_customer_cannot_read_errors() -> None:
    assert ask("customer", "What does error E104 mean?")["refused"] is True


def beat_staff_can() -> None:
    body = ask("staff", "What does error E104 mean?")
    assert "[error-e104#0]" in str(body["answer"]), body["answer"]


def beat_stats_are_for_staff() -> None:
    assert call("GET", "/api/stats", "customer")[0] == 403
    status, body = call("GET", "/api/stats", "staff")
    assert status == 200 and int(str(body["questions"])) >= 1, body


def beat_ready() -> None:
    assert call("GET", "/ready")[0] == 200, "the gateway cannot reach the AI service"


BEATS = [beat_ready, beat_calibration, beat_refusal, beat_customer_cannot_read_errors, beat_staff_can, beat_stats_are_for_staff]
failed = 0
for beat in BEATS:
    started = time.perf_counter()
    try:
        beat()
        verdict = "ok"
    except (AssertionError, KeyError, urllib.error.URLError) as err:
        verdict, failed = f"FAILED: {err}", failed + 1
    print(f"{beat.__name__.removeprefix('beat_'):<34} {verdict:<8} {(time.perf_counter() - started) * 1000:6.0f} ms")
print("the demo path works" if failed == 0 else f"{failed} beat(s) failed: fix them before the demo")
sys.exit(1 if failed else 0)

The feedback sheet and the triage
FEEDBACK SHEET (the friend fills in, you do not argue)
what I understood the project is, in one sentence:                    ...
the moment I got lost (a time, or a word):                            ...
the moment I was most interested:                                     ...
a word I did not know:                                                ...
what looked broken or slow:                                           ...
the question I wanted to ask and did not:                             ...
one thing I would cut:                                                ...
one thing I would add:                                                ...
TRIAGE: for each line of feedback, one of three boxes
FIX NOW     small, and it would hurt on the day (a confusing word, a slow step, a typo on the first screen)
SAY IT      it is a real limit and you cannot fix it this week: put the honest sentence in your talk and your README
LET GO      one person's taste, or a new feature: it goes on the ticket list (the freeze rule)
RULE: at most three FIX NOW items. Then run the demo check and the full demo once more.

6 · Check yourself 5 min

  1. Why does the failure message of the check show the actual answer?
  2. Why do you not explain or defend while your friend watches?
  3. How many items of feedback do you fix now, and why that few?
Answers
  1. So that you see at once whether the system or the expectation is wrong, without a second run.
  2. A real audience will not let you explain. If you explain, you hide exactly the places where the demo does not speak for itself.
  3. At most three: the day is close, every change can break something, and you must run the demo check and the whole demo once more after them.
