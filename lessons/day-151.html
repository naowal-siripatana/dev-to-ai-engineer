DAY 151 · LEVEL 13: DEPLOYMENT

CI/CD with GitHub Actions

60-70 minhands-onfree
Today you will be able to write a workflow that runs your tests, your secret check and your builds on every push, and check it before you push.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Why does a settings class return a SecretStr and not a plain string?
  2. You committed a password and removed it in the next commit. Is it safe now?
Answers
  1. A printout, a log or a crash report shows stars, not the value. You must ask for the real value on purpose.
  2. No: the history keeps it. Replace the secret at its source.

2 · Hook 2 min

You run the tests before every commit. Tonight you are tired and you skip it, and the push breaks the gateway. Who stops you, and who tells you before your users do?

Guess first, then open

A machine that does not get tired. Continuous integration (CI) runs the same checks, in a clean place, on every push, and shows red or green next to the commit. Not “it works on my machine”, but “it works on an empty machine that has only what the repository says”.

3 · The idea, in three small pieces 8 min

Be clear about what was run. The workflow below was never run on GitHub: that needs a repository there. What was run for real: a linter for workflow files (actionlint) on the file, and every command of every job by hand on the author’s laptop. The image build was not run (no working Docker engine); only docker compose config was. How the GitHub machines behave (starting the database, caching, skipping jobs) is standard behaviour that was not observed. The first push is the first real run: read the log, and tell us.

Piece 1: a workflow is a file in the repository

A file in .github/workflows/ says when to run (on:), and what to run (jobs:). Each job gets a fresh machine and a list of steps. A step is either uses: (a ready-made action, such as “copy the code here”) or run: (a command). A command that exits with anything other than 0 fails the step, the job and the run.

Piece 2: jobs run in parallel, unless one needs another

The Python tests, the .NET tests and the page build do not depend on each other, so they run side by side and finish sooner. The image build must wait: needs: [python, gateway, web] means “only when all three are green”. If any of them fails, the build job is skipped. That one line is how a failing test blocks the build (Thursday).

Piece 3: CI must need no secrets

A test run that needs your real key is a leak waiting to happen, and costs money. So CI uses the fake writer (LLM_MODE=fake), a service container for the database with a throwaway password, and permissions: contents: read so a job can read the code and nothing more. Real secrets, when they are needed later for a deploy, live in the settings of the repository, never in the file.

If you know another typed language (C# as the example): this is the same idea as an Azure DevOps or TeamCity build: a trigger, stages that run on clean agents, and a gate between the test stage and the next one. needs: is dependsOn, and a service container is the database you used to spin up on the build agent.
Capstone: the whole pumpguard repository gets one workflow. Saturday you finish it, push it, and put a badge in the README.

4 · Worked example 5 min

Read it first. The skeleton, with a comment for every part:

name: CI                     # the name on the badge and in the list of runs
on:                          # WHEN: a push to main, and every pull request
  push:
    branches: [main]
  pull_request:
jobs:                        # WHAT: jobs run in parallel unless one needs another
  python:
    runs-on: ubuntu-24.04    # a fresh, empty machine for every run
    steps:
      - uses: actions/checkout@v7   # uses: a ready-made step (here: copy the code onto the machine)
      - run: uv run pytest -q       # run: one command; if it exits with a code other than 0, the job stops and fails

The Python job needs a database for its tests. A service container starts one next to the job (the tests already read TEST_DATABASE_URL, so they need no change):

    services:
      db:
        image: pgvector/pgvector:pg17
        env:
          POSTGRES_PASSWORD: ci-only-password   # a throwaway database that lives for this job only
        ports: ["5433:5432"]
        options: --health-cmd "pg_isready -U assistant" ...

The whole file, .github/workflows/ci.yml, is in the template in Stuck, so that you can open it now. Check it with the linter before you push:

You should see

5 · Try it 30 min

Work in the root of the capstone repository (the folder that holds python-service, gateway, web and compose.yaml), on a branch: git switch -c ci. A GitHub repository is needed for steps 2 and 3. If you do not have one yet, create an empty private one and add it as origin; step 1 and 4 need only your laptop.

Step 1 Copy and check

Create .github/workflows/ci.yml from the template in Stuck. Run the linter (for example pipx run --spec actionlint-py actionlint .github/workflows/ci.yml, or install actionlint any way you like): it should print nothing. Then run each command of each job by hand, in its folder, with the same variables, and write down any that fails on your machine: it will fail on GitHub too.

Step 2 Push and watch

Push the branch and open a pull request. Open the Actions tab and watch the four jobs. Predict first: which will finish last, and which can fail for a reason that has nothing to do with your code (think of the model download and the first-time cache)? Read the log of one step.

Step 3 Break it on purpose

Misspell a name in needs: and run the linter: read the message. Then fix it, and on the branch make one test fail on purpose (change an expected value), push, and look at the red mark next to the commit. Which jobs ran, and which did not?

Step 4 Your turn

Add the secret finder as a step of the Python job (it is already in the template: check that it passes), and write in the README one sentence for a new contributor: “what must be green before I merge”. Commit: git add .github/workflows/ci.yml README.md and git commit -m "Run the tests on every push".

6 · Stuck? anytime

  • The Python job fails on connection refused: the database was not ready, or the port in TEST_DATABASE_URL does not match the mapping in ports:. The health options make the job wait until it is ready.
  • Tests pass on your laptop and fail on GitHub: the laptop has something the repository does not (a file that is ignored by Git, a model in your cache, a variable in your shell). That is exactly what CI is for. Find the difference.
  • The first run is slow: nothing is cached yet. The model for the embeddings (64 MB) is downloaded once, and then restored from the cache.
  • “Resource not accessible by integration”: a step needs a permission that the file does not give. Add only that one permission, to that one job.
  • An action version does not exist: the file names a version that you mistyped, or one that is gone. Check the releases of that action. (The versions in the template were the newest when written.)
Hint: Step 2

The first run of every job downloads and installs things, so the Python job (packages, model, database) and the image job (the base images) are the slowest. A repeat run with caches is much faster.

Template: ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read   # the least a job needs: it can read the code and nothing else

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true   # a newer push replaces the run of an older one

jobs:
  python:
    runs-on: ubuntu-24.04
    timeout-minutes: 20
    defaults:
      run:
        working-directory: python-service
    services:
      db:
        image: pgvector/pgvector:pg17
        env:
          POSTGRES_USER: assistant
          POSTGRES_PASSWORD: ci-only-password   # a throwaway database that lives for this job only
          POSTGRES_DB: assistant
        ports: ["5433:5432"]
        options: >-
          --health-cmd "pg_isready -U assistant -d assistant"
          --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      TEST_DATABASE_URL: postgresql://assistant:ci-only-password@localhost:5433/assistant
      DATABASE_URL: postgresql://assistant:ci-only-password@localhost:5433/assistant
      LLM_MODE: fake   # no real model, no key: CI never needs a secret
      FASTEMBED_CACHE_PATH: ${{ github.workspace }}/.fastembed
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10
      - uses: actions/cache@v6
        with:
          path: .fastembed
          key: fastembed-bge-small-en-v1.5
      - run: uv sync --frozen
      - run: uv run mypy src tests
      - run: uv run pytest -q
      - run: uv run python find_secrets.py

  gateway:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    defaults:
      run:
        working-directory: gateway
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: 10.0.x
      - run: dotnet test AskGateway.Tests

  web:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    defaults:
      run:
        working-directory: web/chat-ui
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm ci
      - run: npm run build

  images:
    needs: [python, gateway, web]   # only when all three test jobs are green
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    env:
      POSTGRES_PASSWORD: ci-only-password   # compose.yaml refuses to run without it
    steps:
      - uses: actions/checkout@v7
      - run: docker compose config -q
      - run: docker compose build

7 · Check yourself 5 min

  1. What is CI, in one sentence, and what does runs-on give each job?
  2. What does needs: [python, gateway, web] do?
  3. Why does the workflow use a fake writer and a throwaway database password?
Answers
  1. A machine runs the same checks on every push in a clean place and shows red or green. runs-on gives the job a fresh machine with only what the repository and the steps put on it.
  2. The job starts only when all three jobs are green; if any fails, it is skipped.
  3. CI must not need a real key or a real password: a leak would cost money or data, and a test run should never touch production. The values are fakes that live for one run.
