Teach-back: why a vector database

30 minhands-onfree
Today you will be able to explain in 5 sentences why vectors live in a database, with the speed, accuracy and cost of an index measured.

1 · Warm-up: write down what you know 5 min

Close your notes. A colleague says: “I keep 1,000 embeddings in a numpy array and it works. Why would I run a database for vectors?” Write what you would answer in two lines. Then write one situation in which the colleague is right, and one in which they are not.

2 · Explain it 10 min

Your task: explain why we use a vector database (here: PostgreSQL with pgvector) instead of a list in memory, in 5 sentences or a 60-second voice note.

  • Who you are talking to: the colleague above, who is happy with numpy.
  • Use these words: persist, index, nearest, filter, approximate.
  • Rules: no notes, and be fair: give the case where the database is not needed.

Write it or record it now. A rough first try is exactly right.

Stuck? Sentence starters

Use these if you freeze:

1. A vector database keeps ... so that ...
2. Searching without an index means ..., so it gets ... when there are more rows.
3. An index such as HNSW ..., but the answer is only ...

3 · Check it against the key points 8 min

Read the six key points and tick each one that your explanation said clearly. Be strict.

  1. Persistence and sharing: the vectors survive a restart, and several programs can use them.
  2. Speed at scale: an exact search compares the question with every row, so it slows down as the data grows. An index (such as HNSW) finds the nearest rows without looking at all of them.
  3. Approximate: an index usually gives almost the same answer, not exactly the same. You trade a little accuracy (recall) for a lot of speed.
  4. SQL: you can filter by metadata (language, product, date), join other tables, and update or delete rows, in the same place as the rest of your data.
  5. Not always needed: for a few hundred or thousand chunks that rarely change, an array in memory is simple and fast enough.
  6. It costs something: time to build an index, memory, and one more thing to run and back up.
A model answer in 5 sentences

A vector database keeps the embeddings so that they survive a restart and several programs can use them. Searching without an index means comparing the question with every row, so it gets slower as the data grows, and an index such as HNSW finds the nearest rows without checking all of them. The answer from an index is only approximate, so I trade a little accuracy for a lot of speed. Because it is SQL, I can also filter by metadata and join other tables in the same place as my other data. But for a few hundred chunks that rarely change, an array in memory is simpler and fast enough, so I would not run a database for that.

Count your ticks. 6: very clear. 3 to 5: good, you found your gaps. 0 to 2: also fine, the next step fills them in.

4 · Look at the evidence 5 min

Do not trust the argument. Measure it. This script puts 50,000 synthetic vectors of 384 numbers into your database (they are grouped around 200 “topics”, like real text embeddings are, and every question is near a topic). It runs 20 questions with an exact search, then builds an HNSW index and runs the same 20 questions again, and compares the answers. It needs the database from Day 60 (port 5433). Save it as scale_test.py:

import time

import numpy as np
import psycopg
from pgvector.psycopg import register_vector

DSN = "postgresql://assistant:assistant@localhost:5433/assistant"
ROWS, DIMS, QUERIES, TOPICS = 50_000, 384, 20, 200

# Real embeddings are not random: texts about the same topic sit close together. So we make 200 "topics"
# and put every vector near one of them, and every question near one of them.
rng = np.random.default_rng(0)
topics = rng.normal(size=(TOPICS, DIMS)).astype(np.float32)


def near_topics(count: int) -> np.ndarray:
    points = topics[rng.integers(0, TOPICS, size=count)] + 0.4 * rng.normal(size=(count, DIMS)).astype(np.float32)
    return points / np.linalg.norm(points, axis=1, keepdims=True)


vectors = near_topics(ROWS)
queries = near_topics(QUERIES)

SEARCH = "SELECT id FROM big ORDER BY embedding <=> %s LIMIT 10"


def run_queries(conn: psycopg.Connection) -> tuple[float, list[list[int]]]:
    started = time.perf_counter()
    results = [[row[0] for row in conn.execute(SEARCH, (q,)).fetchall()] for q in queries]
    return (time.perf_counter() - started) / QUERIES * 1000, results


with psycopg.connect(DSN, autocommit=True) as conn:
    register_vector(conn)
    conn.execute("DROP TABLE IF EXISTS big")
    conn.execute("CREATE TABLE big (id int PRIMARY KEY, embedding vector(384) NOT NULL)")
    with conn.cursor().copy("COPY big (id, embedding) FROM STDIN WITH (FORMAT BINARY)") as copy:
        copy.set_types(["int4", "vector"])
        for i, v in enumerate(vectors):
            copy.write_row((i, v))
    print("rows:", conn.execute("SELECT count(*) FROM big").fetchone()[0])

    plan = conn.execute("EXPLAIN " + SEARCH, (queries[0],)).fetchall()
    print("without an index:", [line[0].strip() for line in plan if "Scan" in line[0]][0])
    exact_ms, exact = run_queries(conn)
    print(f"  exact search: {exact_ms:.1f} ms per query")

    started = time.perf_counter()
    conn.execute("CREATE INDEX big_hnsw ON big USING hnsw (embedding vector_cosine_ops)")
    print(f"building the HNSW index: {time.perf_counter() - started:.1f} s")
    plan = conn.execute("EXPLAIN " + SEARCH, (queries[0],)).fetchall()
    print("with the index:", [line[0].strip() for line in plan if "Scan" in line[0]][0])
    fast_ms, approx = run_queries(conn)
    recall = np.mean([len(set(a) & set(e)) / 10 for a, e in zip(approx, exact)])
    print(f"  index search: {fast_ms:.1f} ms per query, recall of the top 10: {recall:.0%}")
    conn.execute("DROP TABLE big")

You should see

without an index: ->  Parallel Seq Scan on big  (cost=0.00..16694.33 rows=531707 width=12)
  exact search: 8.6 ms per query
building the HNSW index: 10.2 s

On this laptop the index is about 14 times faster (0.6 ms against 8.6 ms), it finds 95 percent of the true top 10 (the rest are near neighbours instead), and it needed about 10 seconds to build. The plan changes from a scan of every row (Seq Scan) to Index Scan using big_hnsw. Your numbers will be different: speeds depend on your machine. The pattern is what matters: faster, approximate, and a build cost. With your 26 chunks, the planner would not even use the index, and that is fine.

The vectors are synthetic, made for this experiment, so the table says nothing about your assistant’s quality. And with 50,000 rows the exact search is still only 9 ms: the gap becomes important with millions of rows or many users at once.
