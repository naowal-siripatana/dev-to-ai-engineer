3 · The idea, in three small pieces 8 min

Piece 1: raise a clear error, catch a specific one

When something is wrong, raise an error with a message. Make your own error type with one line (class DocumentNotFoundError(Exception)), so the name says what happened. Then catch that error, not everything. Think of a label on a box: “fragile” tells you more than “thing”. An exception is Python’s word for an error you can catch.

Piece 2: logs are for you, print is for the user

The logging module writes messages with a level, so you can turn the detail up or down without changing the code. Think of levels as volume knobs for your program’s diary.

LevelUse it for
DEBUGDetail for you while building
INFONormal events (“found document 1”)
WARNINGSomething odd, but we recovered
ERRORSomething failed

Python shows WARNING and above unless you turn it down. logging.basicConfig(level=...) sets that once, at the start of the program.

Piece 3: handle it or let it travel, never swallow it

In an except block you have two good choices: handle it (return a safe answer and log what happened) or let it travel up to someone who can. The choice to avoid is except Exception: pass. It is like taking the battery out of a smoke alarm: the problem does not go away, it shows up somewhere else, later, with a confusing message.

If you know another typed language (C# as the example): raise is throw, and try / except is try / catch. The levels are the same as ILogger (LogDebug, LogInformation, LogWarning, LogError). One difference: Python has no checked exceptions, so nothing forces you to catch. You have to choose to. (Java is different: it has checked exceptions.)
Capstone: model calls will time out and hit rate limits. The service has to fail clearly, say what went wrong, and leave a log line for every call. This is that habit.

4 · Worked example 3 min

Read it first. A lookup that can fail, a clear error, and a log line for each outcome.

import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(name)s: %(message)s")
logger = logging.getLogger("docs")


class DocumentNotFoundError(Exception):
    """Raised when a document id is not in the store."""


STORE = {"1": "Error E101 means the sensor timed out."}


def get_document(doc_id: str) -> str:
    if doc_id not in STORE:
        raise DocumentNotFoundError(f"no document with id {doc_id!r}")
    return STORE[doc_id]


def answer(doc_id: str) -> str:
    try:
        text = get_document(doc_id)
    except DocumentNotFoundError as err:
        logger.warning("lookup failed: %s", err)
        return "Sorry, I could not find that document."
    logger.info("found document %s (%d words)", doc_id, len(text.split()))
    return text


print(answer("1"))
print(answer("99"))
You should see
INFO docs: found document 1 (7 words)
WARNING docs: lookup failed: no document with id '99'
Error E101 means the sensor timed out.
Sorry, I could not find that document.

The log lines go to a different place than print, so in your terminal the order of the lines can differ a little. That is normal.

logging.getLogger("docs") makes a logger named “docs”, and the name shows up in every line. format=... chooses what each log line looks like.

Step 2 Change one thing

Change level=logging.INFO to level=logging.DEBUG, and add this as the first line inside answer (before try:):

Check your prediction

DEBUG docs: looking up 99
WARNING docs: lookup failed: no document with id '99'
...

One DEBUG line per call. Set it back to INFO and they go quiet, without touching any other line.

Step 3 Break it on purpose

Swallow the error. Replace the whole except DocumentNotFoundError ... block with:

    try:
        text = get_document(doc_id)
    except Exception:
        pass

Run it and read the last line of the error.

You should see
UnboundLocalError: cannot access local variable 'text' where it is not associated with a value

The real problem (document 99 does not exist) is gone. You get a confusing error in a different line. That is what swallowing costs. Now put the good block back, and change logger.warning(...) to logger.exception("lookup failed"). Run it and see the full traceback (the list of lines that led to the error, with the file and line number of each) in the log: this is how you find a bug at 2 a.m.

Step 4 Your turn

In a new file src/my_ai_project/params.py, write safe_top_k(raw: str) -> int. It turns text like "5" into the number 5. If the text is not a number, or the number is outside 1 to 10, it logs a warning and returns the default, 3. Test it with "5", "abc" and "99": you should get 5, 3 and 3, plus two warning lines.

Hint 1

int(raw) raises ValueError when the text is not a number. Catch that one only.

Hint 2

Check the range with if not 1 <= value <= 10: after the try block.

Solution
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(name)s: %(message)s")
logger = logging.getLogger("params")

DEFAULT_TOP_K = 3


def safe_top_k(raw: str) -> int:
    try:
        value = int(raw)
    except ValueError:
        logger.warning("top_k %r is not a number, using %d", raw, DEFAULT_TOP_K)
        return DEFAULT_TOP_K
    if not 1 <= value <= 10:
        logger.warning("top_k %d is outside 1-10, using %d", value, DEFAULT_TOP_K)
        return DEFAULT_TOP_K
    return value


for raw in ["5", "abc", "99"]:
    print(raw, "->", safe_top_k(raw))
You should see
WARNING params: top_k 'abc' is not a number, using 3
WARNING params: top_k 99 is outside 1-10, using 3
5 -> 5
abc -> 3
99 -> 3

6 · Stuck? anytime

  • I see no log lines: you forgot logging.basicConfig(...), or the level is higher than the message. The default level hides INFO and DEBUG.
  • The lines come in a different order: normal. Logs and print travel by different channels.
  • The log line appears twice: you called basicConfig in two files. Call it once, at the start of the program.
  • “nothing to commit”: you did not save the files, or you are in the wrong folder.

7 · Check yourself 5 min

  1. Why is except Exception: pass a bad idea?
  2. When would you use print, and when logging?
  3. A document is not found (expected) versus the database is down (unexpected). Which log level fits each?
Answers
  1. It hides the real problem, so you see a confusing error later, or no error at all.
  2. print is for the person using the program. logging is for you, with levels you can turn up and down.
  3. Not found: WARNING (or INFO), and handle it. Database down: ERROR, with the traceback.
