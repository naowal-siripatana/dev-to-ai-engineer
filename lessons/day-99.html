1 · Self-test 25 min

Close your notes. Answer each question in your own words, and write a confidence number next to it: 1 = guessing, 2 = fairly sure, 3 = certain. Then open the answers and mark each one right, partly right or wrong.

  1. What are the three parts of one turn of an agent loop? (Day 93)
  2. Name two stop rules for an agent, and say who sets them. (Day 93, 96)
  3. What is a trace for? (Day 93)
  4. Which tools need a human approval, and what is the order of the checks? (Day 95)
  5. Why must a risky action be safe to repeat? (Day 95)
  6. When should you use a workflow and not an agent? (Day 95, 97)
  7. Why does the page call the .NET gateway and not the Python service? (Day 98)
  8. Why is a role selector in the page only a demo? (Day 98)
  9. Which parts of your Module 7 runs were simulated, and which were real? (Days 81 to 98)
Answers
  1. Think (the model decides), act (your code runs the tool), observe (the result goes into the history).
  2. A maximum number of steps, and stopping before a repeated action. Your code sets them, not the model.
  3. To understand a run afterwards (what was thought, called and returned), and as the raw material for evaluation.
  4. The ones that change, send or delete something. The order: rights, then input, then approval, then the action.
  5. Approvals and retries happen. Doing it twice must not do harm (closing a closed incident is not an error).
  6. When you can write the steps down in advance. Use an agent only when the next step really depends on what the last one found.
  7. The gateway is the front door that will own login, rules and logging. The browser should know one address.
  8. Anything in the browser can be changed by the user. A real role comes from a login that the server checks.
  9. The models (pretend, stubborn) were stand-ins. The SDK message shapes, the loops, the limits, the roles, the approval, the gateway and the page were real.

Read your numbers. If you were sure (3) and wrong, that is the most valuable thing you found. Circle those.

2 · Module 7 retrospective 20 min

Module 7 asked for one real tool, a simple loop, and a way to use it. You have a tool with roles and structured errors, an MCP server, a tool loop, an agent loop with limits and approval, a gateway and a page. Answer these in your notebook, two lines each, with an example:

Module 7 retrospective (write 2 lines for each)
1. Which tool do I trust most in my assistant, and why? (give an example)
2. Which part would worry me if a real user used it tomorrow?
3. What did I only understand when I built it (not when I read it)?
4. Did the stand-in models hide anything? What would I check with a real model and a key?
5. If a user asked 'can I trust the tool?', what would I say today?

Look at your answer to question 4. The stand-in models were honest tools for learning, and they hid one thing: how a real model behaves. If you have a key, run the page once with LLM_MODE=real and write down what was different. That note is worth more than the rest of this section.

3 · Start your job applications 30 min

From now on, your plan includes two or three applications a week. This is not a promise of a job: it is a habit that gives you feedback from the market while you learn, and it is easier to start before you feel ready. Today you set it up. Nothing here needs a final CV or a perfect repository.

1. Choose the roles

Pick two or three kinds of role, and write what your project shows for each:

role I could apply for           what a posting usually asks for            what in my project matches
Backend / .NET developer         APIs, databases, tests, Git                the .NET gateway, Postgres, tests
AI / LLM application developer   APIs for models, RAG, tool calling         the RAG pipeline, the tool loop
Full-stack with AI features      a web UI and an API                        the React page and the gateway

2. Say only what is true

Say what is true, and say what was simulated.
  good : "I built a RAG assistant: a Python service with Postgres and pgvector, a .NET gateway and a React page."
  good : "The model calls in my tests use a stand-in; I tested the real adapter against a mock server."
  not  : "I built an AI agent that handles customer support."   (it is a learning project with a mock knowledge base)
Link to code a person can run. A README that works is worth more than a long CV line.

3. One application, in 45 minutes

One application (about 45 minutes)
 5 min  read the posting; write down 3 things they ask for that I can show
10 min  pick the one repository or demo that fits; check that its README runs
15 min  write 5 sentences: who I am, what I built, why this company (no copied text)
10 min  adjust the CV: move the matching project to the top; remove what does not help
 5 min  send it; write one line in the log, with a follow-up date in 7 days

4. Keep a log

...  | ...     | ...  | ...              | ...         | ...

5. Practise the demo

You will be asked to show something. Rehearse this once, out loud, with a timer:

A 60-second demo of the assistant
 1. (10 s) The problem: a monitor shows E104 and a user does not know what it means.
 2. (20 s) Open the page as a customer: it is refused politely. Switch to staff: it answers, and shows the tool call.
 3. (15 s) Show the same question through /api/ask: the answer with its sources.
 4. (15 s) Say what is simulated, and what you would measure next (the evaluation weeks).

Now do the first one: choose one posting, and do the 45-minute routine. Sending is your decision; the point today is to learn how long it takes you.
