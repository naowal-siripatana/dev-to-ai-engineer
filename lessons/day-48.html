Teach-back: why validate model output

30 minhands-onfree
Today you will be able to explain in 5 sentences why model output must be validated, with concrete failures and the one a schema cannot catch.

1 · Warm-up: write down what you know 5 min

Close your notes. A colleague says: “The prompt says return only JSON, and the model always does. Why add a check?” Write what you would answer in two lines. Then write one thing that could still go wrong, even with a perfect prompt.

Do not look anything up. Your guess is the most useful line you will write today.

2 · Explain it 10 min

Your task: explain why model output must be validated before your program uses it, in 5 sentences or a 60-second voice note.

  • Who you are talking to: the colleague above, who is sure that a good prompt is enough.
  • Use these words: predict, untrusted, schema, wrong, retry.
  • Rules: no notes, and give two concrete ways the output can go wrong.

Write it or record it now. A rough first try is exactly right.

Stuck? Sentence starters

Use these if you freeze:

1. A model does not calculate an answer, it ...
2. So its output is like ... input: I must ... it.
3. Things that go wrong are ... (give two or three)
4. A schema check catches ..., but it cannot catch ...
5. So when the check fails, I ..., and I never ...

3 · Check it against the key points 8 min

Read the six key points and tick each one that your explanation said clearly. Be strict.

  1. A model predicts likely text. It does not compute an answer, so it is usually right in shape, but never guaranteed.
  2. Its output is untrusted input, like what a stranger types into a form. A prompt asks for good behaviour, it does not enforce it.
  3. Real mistakes: a wrong value, a missing field, a wrong type, extra text around the JSON, or an answer cut off by the token limit.
  4. A schema check (Pydantic) catches the shape. It cannot catch a reply that is valid but wrong in meaning, so you need other checks too: sources, rules, tests, and a person for high stakes.
  5. When the check fails: retry with the exact problem, a few times at most, then fail loudly (an error, a 502). Never guess, and never pass unchecked data on.
  6. Validation is cheap. A wrong value that reaches a database, a screen or a tool call is expensive.
A model answer in 5 sentences

A model does not calculate an answer, it predicts likely text, so its output is usually well formed but never guaranteed. That makes it untrusted input, like what a stranger types into a form, and a good prompt only asks for good behaviour. It can give a wrong value, miss a field, add words around the JSON, or be cut off by the token limit. A schema check catches those shape problems, but not a reply that is valid and wrong, so I also check the facts against sources and rules. When a check fails I retry with the exact problem, and if it still fails I return an error, because passing unchecked data on is much more expensive than checking.

Count your ticks. 6: very clear. 3 to 5: good, you found your gaps. 0 to 2: also fine, the next step fills them in.

4 · Look at the evidence 5 min

Do not trust the argument. Run six replies that a model could plausibly give, through your validation. The replies are made up for this exercise, and each one is a real kind of mistake. Save this as validation_gap.py:

from pydantic import ValidationError

from my_ai_project.extractor import Extraction
from my_ai_project.structured import StructuredOutputError, describe, extract_json

replies = {
    "wrong value": '{"error_code": "E101", "severity": "urgent", "action": "Check the cable"}',
    "missing field": '{"error_code": "E101", "severity": "medium"}',
    "wrong type": '{"error_code": 101, "severity": "medium", "action": "Check the cable"}',
    "no JSON at all": "I am sorry, I cannot help with that.",
    "cut off by max_tokens": '{"error_code": "E101", "severity": "medium", "act',
    "valid, but wrong": '{"error_code": "E103", "severity": "low", "action": "Ignore it"}',
}
for name, reply in replies.items():
    try:
        result = Extraction.model_validate_json(extract_json(reply))
        print(f"{name:<22} PASSES -> {result.model_dump()}")
    except (ValidationError, StructuredOutputError) as err:
        print(f"{name:<22} rejected: {describe(err)}")

Predict first: how many of the six will your validation reject, and which one worries you most?

You should see
wrong value rejected: severity: Input should be 'low', 'medium' or 'high'
missing field rejected: action: Field required
wrong type rejected: error_code: Input should be a valid string
no JSON at all rejected: no JSON object in the reply
cut off by max_tokens rejected: no JSON object in the reply
valid, but wrong PASSES -> {'error_code': 'E103', 'severity': 'low', 'action': 'Ignore it'}

Five are rejected, each with a message that says exactly what is wrong. The sixth passes: it has the right shape, but a reply that says an overheating device is a low severity problem, with the action Ignore it, is wrong. No schema can know that. That is the limit of validation, and the reason you add checks of meaning (sources, rules) and, for important decisions, a human.
