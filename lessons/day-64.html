1 · Self-test 25 min

Close your notes. Answer each question in your own words, and write a confidence number next to it: 1 = guessing, 2 = fairly sure, 3 = certain. Then open the answers and mark each one right, partly right or wrong.

  1. In which order do you fill the context window, and what is dropped first? (Day 58)
  2. What is context rot, and why does a bigger window not fix it? (Day 58)
  3. What do an image, a container and a volume each do? (Day 60)
  4. Which pgvector operator would you use for cosine closeness, and how do you sort? What happens if the vector has the wrong number of dimensions? (Day 60)
  5. Why should the ranking from the database equal the ranking from memory? (Day 61)
  6. What is an upsert, and why does your ingest need one? (Day 61, Day 63)
  7. What does an HNSW index give you, and what does it cost? (Day 62)
  8. When is a numpy array enough, and when do you want a vector database? (Day 62)
Answers
  1. First the system prompt and the question, then the best sources, then the history. The oldest history is dropped first.
  2. Quality can fall when the context is long and full of things that do not matter for the question, even when it fits. A bigger window only allows more noise: you have to choose what goes in.
  3. The image is the recipe (Postgres with pgvector installed), the container is one running copy, and the volume keeps the data outside the container so that it survives a restart.
  4. <=> for the cosine distance, sorted ascending (smaller means closer), with LIMIT. A vector of the wrong length is an error, such as expected 3 dimensions, not 2.
  5. The model, the texts and the formula are the same, only the storage differs. A different result means a bug: a different text, model or operator.
  6. An insert that updates the row if it already exists. Without it, running the script twice gives a duplicate-key error or doubled data.
  7. Speed on big tables, because it finds near neighbours without checking every row. It costs some accuracy (the answer is approximate), build time and memory.
  8. An array in memory is enough for a few hundred or thousand chunks that rarely change. A database is better when the data is big, shared, changing, or needs filters and joins, and when it must survive restarts.

Read your numbers. If you were sure (3) and wrong, that is the most valuable thing you found. Circle those.
