1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. What goes into a safe cache key, and why the role?
  2. Why should a fallback only catch some errors?
Answers
  1. The normalised question, the role, and anything else that changes the answer (such as top_k). The role keeps an answer made for staff from being served to a customer.
  2. A provider error is expected and recoverable; a bug in your own code should not be hidden by a second model.

2 · Hook 2 min

A user clicks “bad answer”. What do you need to have stored for that click to be useful, and what do you do with it next week?

Guess first, then open

The request id of the answer, so that you can find the question, the sources, the tokens and the logs of exactly that answer. And a habit: read the down-votes, turn the bad answers into new golden questions, fix them, and let the score table show whether you improved things. A vote without a request id is only a number.

3 · The idea, in three small pieces 8 min

Piece 1: a vote is tied to a request

Under each answer, a thumbs up and a thumbs down. The page already knows the request id (the X-Request-Id of the response), so it sends it with the vote. The service checks that the request exists, stores (request_id, rating, comment) in a table, and hides private strings in the comment, because a comment is user input. A vote for an unknown id is a 404, a rating other than up or down is a 422.

Piece 2: SLI, SLO and the error budget

An SLI (service level indicator) is a measurement of what the user feels. An SLO (objective) is the target for it. The error budget is what the target leaves: a 99% objective allows 1% bad requests. For your assistant: a request is good if it did not fail on your side (status below 500) and was fast enough (under 2 seconds). A 4xx is the caller’s mistake, so it does not count against you. The SLI is the share of good requests, and the SLO says how high it must be.

Piece 3: let the numbers send you to a fix

The metrics of last week showed one very slow request: the first one after a start. Counted against a 2-second SLI, that single request would put 20 requests at 95%, below a 99% objective. The cause is known (the model and the keyword index load on the first request), so the fix is a warm-up at start. A number that sends you to a cause and a fix is what a good indicator is for.

If you know another typed language (C# as the example): the vote is a small entity with a foreign key to the request, like a comment on an order. The SLI is a ratio of two counters, the kind you would export as a Prometheus or OpenTelemetry metric; the SLO is an alert threshold on it, and the warm-up is a hosted service that runs before the app starts taking traffic (IHostedService).
Capstone: on Saturday your dashboard shows the SLI against its SLO, and the votes, next to the five numbers.

4 · Worked example 5 min

The words, and the feedback loop:

SLI  service level INDICATOR   a measurement of what the user feels         'the share of requests that did not fail on our side and took under 2 s'
SLO  service level OBJECTIVE   the target for that measurement                       'at least 99% of requests are good'
     error budget              the room the SLO leaves for failure:  100% - 99% = 1%   'one request in a hundred may be bad before we break the promise'
     SLA                       a promise to a customer, with consequences              (not needed here: it is an SLO with a contract)
THE FEEDBACK LOOP
 user votes (thumbs)  ->  the vote is stored with the REQUEST ID  ->  you read the down-votes with their question, sources and answer
   ->  a bad answer becomes a new GOLDEN question  ->  you fix it  ->  the score table shows that it is better, and that nothing else got worse
Three rules: a vote must be tied to a request (so it can be investigated); a comment is user input (hide emails, limit its length);
and a vote is a SIGNAL, not a score: a few votes say little, and people vote mostly when they are unhappy.

The vote store, in src/my_ai_project/feedback.py: it checks that the request exists, hides private strings in the comment, and stores the vote:

import logging
from typing import Literal

import psycopg

from my_ai_project.audit import redact

logger = logging.getLogger("feedback")

Rating = Literal["up", "down"]

SCHEMA = """
CREATE TABLE IF NOT EXISTS feedback (
    id bigserial PRIMARY KEY,
    time timestamptz NOT NULL DEFAULT now(),
    request_id text NOT NULL,
    rating text NOT NULL CHECK (rating IN ('up', 'down')),
    comment text
);
CREATE INDEX IF NOT EXISTS feedback_request_id_idx ON feedback (request_id);
"""


class FeedbackStore:
    """A thumbs up or down for one answer, tied to the request id. The id is how a vote finds its question, tokens and sources."""

    def __init__(self, dsn: str) -> None:
        self.dsn = dsn

    def record(self, request_id: str, rating: Rating, comment: str | None) -> bool:
        """Returns False when no request has that id (a typo, or a request that was never made). Raises psycopg errors: a lost vote should be seen."""
        clean = redact(comment) if comment else None   # a comment may contain an email or a key
        with psycopg.connect(self.dsn) as conn:
            conn.execute(SCHEMA)
            exists = conn.execute("SELECT 1 FROM requests WHERE request_id = %s LIMIT 1", (request_id,)).fetchone()
            if exists is None:
                return False
            conn.execute("INSERT INTO feedback (request_id, rating, comment) VALUES (%s, %s, %s)", (request_id, rating, clean))
        return True

The numbers, in src/my_ai_project/stats.py: the five numbers of Saturday, and the SLI against the SLO, from the table you filled last week:

import psycopg

from my_ai_project.metrics import SCHEMA

# An SLI is a measurement of what the user feels; an SLO is the target for it. Here: a request is GOOD when it did not fail on our side
# (status below 500) and was fast enough. A 4xx is the caller's mistake: it does not count against us.
SLI_LATENCY_MS = 2000
SLO_TARGET_PERCENT = 99.0


def compute_stats(dsn: str) -> dict[str, object]:
    """The five numbers of the dashboard, the SLI against its SLO, and the votes. Everything comes from the requests and feedback tables."""
    with psycopg.connect(dsn) as conn:
        conn.execute(SCHEMA)   # a fresh database has no requests table yet: the dashboard must show zeros, not crash
        conn.execute("CREATE TABLE IF NOT EXISTS feedback (id bigserial PRIMARY KEY, time timestamptz NOT NULL DEFAULT now(), request_id text NOT NULL, rating text NOT NULL, comment text)")
        row = conn.execute(
            """
            SELECT count(*),
                   count(*) FILTER (WHERE outcome IN ('answered', 'refused')),
                   coalesce(avg(latency_ms), 0),
                   coalesce(percentile_cont(0.5) WITHIN GROUP (ORDER BY latency_ms), 0),
                   coalesce(percentile_cont(0.95) WITHIN GROUP (ORDER BY latency_ms), 0),
                   coalesce(sum(cost_usd), 0),
                   count(*) FILTER (WHERE outcome = 'error'),
                   count(*) FILTER (WHERE outcome = 'refused'),
                   count(*) FILTER (WHERE status_code < 500 AND latency_ms <= %s)
            FROM requests WHERE route = '/api/ask'
            """,
            (SLI_LATENCY_MS,),
        ).fetchone()
        votes: dict[str, int] = {str(rating): int(count) for rating, count in conn.execute("SELECT rating, count(*) FROM feedback GROUP BY rating").fetchall()}
    questions, succeeded, average, median, p95, cost, failed, refused, good = row or (0, 0, 0, 0, 0, 0, 0, 0, 0)
    sli = 100.0 * good / questions if questions else 100.0
    budget = 100.0 - SLO_TARGET_PERCENT
    return {
        "questions": questions,
        "success_percent": round(100.0 * succeeded / questions, 1) if questions else 100.0,
        "avg_ms": round(float(average)),
        "median_ms": round(float(median)),
        "p95_ms": round(float(p95)),
        "total_cost_usd": round(float(cost), 6),
        "failed": failed,
        "refusal_percent": round(100.0 * refused / questions, 1) if questions else 0.0,
        "sli_percent": round(sli, 1),
        "slo_percent": SLO_TARGET_PERCENT,
        "slo_met": sli >= SLO_TARGET_PERCENT,
        "error_budget_used_percent": round(min(100.0, 100.0 * (100.0 - sli) / budget), 1) if budget else 0.0,
        "feedback_up": int(votes.get("up", 0)),
        "feedback_down": int(votes.get("down", 0)),
    }

6 · Stuck? anytime

  • A vote is a 404: the request id must be one that is in the requests table. Read it from the X-Request-Id header of the answer.
  • A 422 on a good vote: the rating must be exactly up or down, and the id must match the safe shape.
  • The SLI is 100% and you expected less: check what counts as bad: only status 500 and above, or a slow request. A 422 is the caller’s mistake.
  • The warm-up does nothing: it only runs when the application starts (the lifespan), not in a test client that is not used as a context manager.
Solution: Step 2 (the query)
SELECT f.request_id, f.rating, r.outcome, r.latency_ms
FROM feedback f JOIN requests r USING (request_id)
WHERE f.rating = 'down'
ORDER BY f.time DESC;
-- then: grep <request_id> audit.jsonl   (it holds the question and the sources)

In the run above, the two down-votes were the price question (answered with the warranty page, a real wrong answer) and the factory-reset question (the stand-in writer wrote only the first sentence). Both are already in the golden set: q17 and q07. A vote that points to a question you already track is a good sign for the golden set; one that points to a question you do not have is a new golden question.

Solution: Step 3

Good = status below 500 and 2000 ms or less. In the 20-request run of last week, 19 were good and one (the cold start, 3584 ms) was not, so the SLI was 19 of 20 = 95%, and the 99% objective was not met. The error budget (1%) was used up several times over by that one request. After the warm-up, the SLI of the 24 requests is 100%.
