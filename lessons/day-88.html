MCP: what it is, and a tiny server

60-70 minhands-onfree
Today you will be able to run a tiny MCP server, list its tools from a client, call one, and say where MCP sits next to function calling.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Why is the permission checked before the input in a tool?
  2. Name two parts of a good tool error.
Answers
  1. So that a refused caller learns nothing about the data (no list of valid codes, no hint that a record exists).
  2. A stable code, a plain message, a hint for the next step.

2 · Hook 2 min

You wrote a tool for your assistant. A colleague writes another AI app and wants the same tool. Do they copy your code? And what if there are ten apps and ten tools?

Guess first, then open

Copying does not scale: ten apps and ten tools means a hundred little adapters. The Model Context Protocol (MCP) is a shared standard: you put the tool in a server once, and any MCP-aware app can list its tools and call them, in the same way, without knowing how they are written.

3 · The idea, in three small pieces 8 min

Piece 1: a host, a client and a server

The host is the AI application. Inside it, an MCP client keeps a connection to an MCP server, which is a separate program. The server offers tools (and, in the protocol, also resources and prompts; today only tools). The client can ask list_tools and call_tool.

Piece 2: MCP does not replace function calling

This is the part that is easy to mix up. The model still uses function calling, as on Day 81: the host passes the tool list in the request, and the model replies with a tool_use. MCP is what happens around that: how the host finds the tools (it asks the server) and how it runs the call (it sends it to the server). Function calling is between the host and the model. MCP is between the host and the tools.

Piece 3: a server talks over stdio or HTTP

With stdio, the client starts the server as a process and they talk through standard input and output. With HTTP, the server runs somewhere and the client connects to a URL. One rule of stdio is important: a stdio server must never print to standard output, because that channel carries the protocol. Logs go to standard error.

If you know another typed language (C# as the example): it is like a language server (LSP) or a plug-in host: one protocol, many tools, and the editor does not know how each one is written. An MCP server with a stdio transport is like a child process you start with Process.Start and talk to with JSON-RPC lines.

4 · Worked example 5 min

Read the picture first:

  the AI application (the host)
     |  1. starts / connects to a server        2. asks: which tools do you have?
     |  3. passes those tools to the model      4. the model asks for one (tool_use)
     |  5. the app sends the call to the server 6. the server runs it and replies
     v
  the MCP server (a separate program: word_server.py)

Add the SDK with uv add mcp. A tiny server with one tool, in word_server.py. The type hints become the input schema, and the docstring becomes the description, so write them like a prompt:

from mcp.server import MCPServer

mcp = MCPServer("word-tools")


@mcp.tool()
def count_words(text: str) -> int:
    """Count the words in a text. Use it when the user asks how long a text is."""
    return len(text.split())


if __name__ == "__main__":
    mcp.run()   # talks over stdin and stdout: a client starts this file as a process

A client that starts the server, lists its tools and calls one. list_and_call.py:

import asyncio
import sys

from mcp import Client, StdioServerParameters


async def main() -> None:
    server = StdioServerParameters(command=sys.executable, args=["word_server.py"])
    async with Client(server) as client:
        listing = await client.list_tools()
        for tool in listing.tools:
            print("tool:       ", tool.name)
            print("description:", tool.description)
            print("input:      ", tool.input_schema)
        result = await client.call_tool("count_words", {"text": "calibrate the sensor once a month"})
        print("result:     ", result.content[0].text, "| is_error:", result.is_error)


asyncio.run(main())
You should see
tool: count_words
description: Count the words in a text. Use it when the user asks how long a text is.
input: {'type': 'object', 'properties': {'text': {'title': 'Text', 'type': 'string'}}, 'required': ['text'], 'title': 'count_wordsArguments'}
result: 6 | is_error: False

Nobody typed the schema: it was made from text: str. The client learned the tool’s name, description and input by asking, which is exactly what a host needs to pass the tool to a model.

Version note. This lesson was run with the Python SDK mcp 2.3.0, where the server class is MCPServer and the client is mcp.Client. Many older examples use version 1: FastMCP from mcp.server.fastmcp and a ClientSession. The ideas are the same; if your install is version 1, use its names.
from mcp.server.fastmcp import FastMCP     # version 1 of the SDK
mcp = FastMCP("word-tools")

6 · Stuck? anytime

  • “cannot import name MCPServer”: you have version 1 of the SDK. Use FastMCP (see the version note) or upgrade with uv add -U mcp.
  • The client hangs: the server file path is wrong, or the server crashed on start. Run uv run python word_server.py alone; it should wait silently for input (press Ctrl-C).
  • A parse or JSON error from the client: check whether something is printed to standard output. Remove the print or send it to standard error.
  • Windows or a different folder: use sys.executable as in the example, and a path that does not depend on the current folder.
Solution: Step 2

The list shows two tools, count_words and shout, and you did not change the client: it asks the server what it has. That is the point of the protocol.

Solution: Step 3

I did not record one fixed result for this step, because it depends on the version of the SDK: some versions stop with a parse error, some log the bad line and go on. Either way the rule does not change. For a stdio server, standard output belongs to the protocol, and a line that is not a protocol message is a bug waiting to happen. Use print(..., file=sys.stderr) or the logging module (which writes to standard error). Write down what your version did.

Solution: Step 4

The server checks the input against the schema, so 5 instead of a string should give is_error: True and a message from the server (check it on your version). You get the same shape of failure as with your own tools on Day 82, from a program you did not write the client for.

The six arrows: (1) the host starts the server, (2) it asks for the tools, (3) it sends the tools and the question to the model, (4) the model replies with a tool_use, (5) the host sends the call to the server, (6) the server’s result goes back to the host, which sends it to the model as a tool_result.

7 · Check yourself 5 min

  1. Does MCP replace function calling? What is each one between?
  2. Why must a stdio server not print to standard output?
  3. What does the client learn when it calls list_tools?
Answers
  1. No. Function calling is between the host and the model (the model asks for a tool). MCP is between the host and the tools (how it finds and runs them).
  2. Standard output carries the protocol messages, so extra text can break them. Logs go to standard error.
  3. Each tool’s name, description and input schema: everything the host needs to offer it to a model.
