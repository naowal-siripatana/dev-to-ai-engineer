2 · The goal 5 min

This is the Module 9 checkpoint: an instructions file, and one real feature built end to end by a coding agent, reviewed by you like a pull request. By the end:

  • AGENTS.md (and a one-line CLAUDE.md) in your repository, with commands that work.
  • A feature built by an agent on its own branch: the question log of /api/ask.
  • The agent’s first version committed alone, your review with findings (how found, how serious), and a second commit with the fixes and tests.
  • Proof that nothing got worse (tests, types, the golden table), and a pull request description.
Capstone: this is the working method you will use for the rest of the project, and the story to tell a reviewer: “I use a coding agent, and here is how I keep control of what it writes.”
Who did this? The feature below was really built by a coding agent (Claude Code, working in the repository) from a prompt like the one in this lesson. The diffs, the runs and the findings are real. Your agent will write other code and you will find other problems; that is the point. The assistant’s answers in the demo come from the simulated writer (not a real model).

Step 1: the instructions file

If you did not finish it on Day 109, do it now. Here is the one used in this lesson, to compare with yours:

# AGENTS.md: my-ai-project (the PumpGuard assistant)

## What this is
A Python service (FastAPI) that answers questions about a fictional pump monitor from a small knowledge base (`data/kb`):
hybrid search (pgvector and keywords), cited answers, user roles, and a tool loop. A .NET gateway and a React page sit in
front of it (other folders). The product is fictional; there is no real customer data.

## Commands
    uv sync
    docker compose up -d            # Postgres with pgvector on port 5433 (throwaway credentials)
    uv run python ingest.py         # chunk, embed and store the knowledge base
    uv run pytest -q                # needs no model and no key; database tests skip when the database is down
    uv run mypy src tests           # must stay clean
    uv run python run_golden.py     # the score table (18 questions); compare it with the baseline I saved
    uv run uvicorn my_ai_project.api:app --port 8000

## Layout
- `src/my_ai_project/`: `api.py` routes, `deps.py` dependencies, `store.py` SQL, `hybrid.py` search, `rag.py` pipeline,
  `grounding.py` prompt and citations, `tool_design.py` / `agent.py` / `tool_loop.py` tools, `golden.py` / `scoring.py` evaluation.
- `tests/`: one file per module, with fakes for the model, the embedder and the store.
- `data/kb/` the pages, `data/golden.jsonl` the golden questions.

## Rules
- Every search and every tool takes the user's role (`allowed_kinds`). Never add a path that skips it.
- A tool's error is a result (`is_error`), not an exception. A tool that changes data needs a person's approval first.
- A stdio MCP server never prints to standard output; use `logging`.
- Models in tests and demos are stand-ins (`Pretend...`, `Simulated...`). Keep them named as such, and never present
  their answers as a real model's.
- No secrets in Git: keys come from environment variables, and `.env` is ignored.
- Type hints everywhere. Small functions. No new dependency without asking.

## Before you say you are done
1. Run `pytest` and `mypy`, and show the results.
2. If you touched retrieval, prompts, thresholds or chunking: run `run_golden.py` before and after and show both tables.
   Do not accept a change that makes a question fail that passed before.
3. Show the diff, and list what you did not test.

## Ask first
Changing a prompt in `grounding.py`, the minimum similarity, the chunk size, the database schema, or anything about deployment.

5 · Stuck? anytime

  • The agent changed more than the feature: send it back, or throw the branch away and give a smaller task. A big diff cannot be reviewed.
  • You found nothing: look again with the checklist, one question at a time, and run the feature with a wrong input and with a failure (a log path that cannot be written). “I found nothing” is also a result; write what you checked.
  • The agent argues with a finding: you decide. Ask for a test that shows the problem, then fix it.
  • Tests need the database: they skip when it is down. For the golden table you need the database and the data (ingest.py).
README line for the log
## Question log

    QUESTION_LOG=logs/questions.jsonl   # where /api/ask appends one JSON line per question (default shown)
    Fields: time (UTC), role, question, refused, sources (document ids). Not logged: the answer text.
    The folder is ignored by Git. The log holds user input: treat it as private.

Answers
  1. So that the review is a real diff, and your fixes are a separate commit: you can show what the agent wrote and what you changed.
  2. The test litter was observed by running pytest and git status; the unwritable log and the missing tests were read from the diff. Observed findings are certain; read ones are risks you should confirm with a test.
  3. Why, how it was tested, what was not tested, and the risks. A reviewer needs the honest list of what is not covered.
