Today you will be able to store 10 embeddings in pgvector and query them from Python, with the same ranking as in memory, from a blank file.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. What do the image, the container and the volume do?
  2. Which operator gives the cosine distance, and how do you sort for the nearest rows?
Answers
  1. The image is the recipe, the container is one running copy, and the volume keeps the data outside the container so it survives a restart.
  2. <=>, sorted ascending: ORDER BY embedding <=> query LIMIT 3. A smaller distance is closer.

2 · Hook 2 min

Another blank file. On Day 40 you ranked 10 documents in Python. Today the same ten go into a database. If everything is right, what should the ranking look like, compared with the one in memory?

Guess first, then open

Identical: the same documents, the same model, the same cosine similarity, so the same order and the same scores. A database that gives a different answer than your in-memory code would be a bug, so the comparison is a good test. Today you also see something new: the data stays, so you can restart the database and ask again without embedding the documents.

3 · The idea, in three small pieces 5 min

No new ideas today. The map of what you reuse:

Piece 1: embeddings and the knowledge base (Day 37 and Day 40)

FastEmbedder.embed gives vectors of 384 numbers, and load_knowledge_base gives the documents.

Piece 2: a table with a vector column (Day 60)

A table docs with doc_id (the primary key), title and embedding vector(384). The driver needs one extra step to speak vectors: register_vector(conn) from the pgvector Python package.

Piece 3: write so that you can run it twice

A script you run twice must not break or double the data. Upsert means “insert, or update if the row already exists”: INSERT ... ON CONFLICT (doc_id) DO UPDATE .... A database that you can fill again and again is much easier to work with.

If you know another typed language (C# as the example): register_vector is like registering a custom type handler with Dapper or Npgsql, and the upsert is the same INSERT ... ON CONFLICT you would write for Postgres in any language (or MERGE in SQL Server).
Capstone: this is the first time the assistant’s documents live outside Python’s memory. On Saturday you do the same with chunks and add the metadata that makes a search useful.

6 · Stuck? anytime

  • “connection failed” or “Connection refused”: the database is not running, or the port differs. Check docker compose ps and the port in your connection string.
  • “cannot adapt type 'ndarray'”: register_vector(conn) is missing, or it ran before the connection existed.
  • “expected 384 dimensions, not 3” (or the other way round): the table and the model disagree. The model gives 384 numbers. Drop the table and create it again with vector(384).
  • The scores differ from Day 40: check that you embed title. body in both places, and that the same 10 documents are in the table.
  • The first run is slow: the embedding model is loaded, as on Day 37.
Hint: Step 1

Embed all the documents in one call: embedder.embed([...]) returns one row per text. Insert them in a loop with a parameterised statement (%s, never string formatting). For a query, embed the question as a list of one text and take the first vector, and use it twice in the SQL: once in the similarity column, once in ORDER BY.

Solution: Step 1 and 2
from pathlib import Path

import psycopg
from pgvector.psycopg import register_vector

from my_ai_project.embedder import FastEmbedder
from my_ai_project.knowledge_base import load_knowledge_base

DSN = "postgresql://assistant:assistant@localhost:5433/assistant"

documents = load_knowledge_base(Path("data/kb"))[:10]
embedder = FastEmbedder()
vectors = embedder.embed([f"{d.title}. {d.body}" for d in documents])

with psycopg.connect(DSN) as conn:
    register_vector(conn)
    conn.execute("CREATE TABLE IF NOT EXISTS docs (doc_id text PRIMARY KEY, title text NOT NULL, embedding vector(384) NOT NULL)")
    for document, vector in zip(documents, vectors):
        conn.execute(
            "INSERT INTO docs (doc_id, title, embedding) VALUES (%s, %s, %s) "
            "ON CONFLICT (doc_id) DO UPDATE SET title = EXCLUDED.title, embedding = EXCLUDED.embedding",
            (document.doc_id, document.title, vector),
        )
    count = conn.execute("SELECT count(*) FROM docs").fetchone()
    print("rows in docs:", count[0] if count else 0)

    for question in ["My monitor stopped responding", "How long will it run on battery?"]:
        query = embedder.embed([question])[0]
        rows = conn.execute(
            "SELECT doc_id, 1 - (embedding <=> %s) AS similarity FROM docs ORDER BY embedding <=> %s LIMIT 3",
            (query, query),
        ).fetchall()
        print(question)
        for doc_id, similarity in rows:
            print(f"  {similarity:.2f}  {doc_id}")

7 · Check yourself 5 min

  1. Why should the ranking from the database equal the one from memory?
  2. What is an upsert, and why does the script need one?
  3. What does register_vector do?
Answers
  1. The model, the texts and the formula are the same, only the storage differs. If the results differ, there is a bug (a different text, a different model, or a wrong operator).
  2. An insert that updates the row if it already exists. Without it, running the script twice fails with a duplicate key or doubles the data.
  3. It teaches the database driver how to send and read the vector type as numpy arrays.
