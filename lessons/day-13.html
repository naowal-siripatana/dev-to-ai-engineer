DAY 13 · LEVEL 2: AI BACKEND · TEACH-BACK

Teach-back: from request to function

30 minhands-onfree
Today you will be able to explain in 5 sentences what happens between a request and your function, and prove it with your own server log.

1 · Warm-up: sketch it from memory 5 min

Close your notes. On paper, draw a line from the client to your function, and write every stop you remember along the way. Use arrows. Do not look anything up: the gaps you find are the point of today.

When you are done, count your stops. There is no right number yet.

2 · Explain it 10 min

Your task: explain what happens between a request arriving and your function running, in 5 sentences or a 60-second voice note.

  • Who you are talking to: a friend who knows Python but has never built a web API.
  • Use these words: request, address, model, function, response.
  • Rules: no notes, and if you use a technical word, say what it means in a few plain words.

Write it down or record it now. A rough, honest first try is exactly right. Explaining is hard when you only half know something, and that is why it works.

Stuck? Sentence starters

Use these if you freeze:

1. First, the client sends ...
2. The server program (uvicorn) ...
3. FastAPI looks for ... that matches both the ... and the ...
4. Then it checks the data with ..., and if it is wrong, ...
5. Only after that, ... Finally, the answer ... with a status code like 200.

3 · Check it against the key points 8 min

Now read the six key points below and tick each one that your explanation said clearly. Be strict: “I knew it but did not say it” does not count.

  1. The client sends a request: a kind (GET or POST), an address (/api/chat) and often a JSON body.
  2. A server program (uvicorn) receives it and hands it to FastAPI.
  3. FastAPI looks for a function that matches both the address and the kind of request. No such address gives 404, the right address with the wrong kind gives 405.
  4. FastAPI reads the body and checks it with the request model. If it is wrong, the client gets a 422 and your function never runs.
  5. Only now your function runs, with the checked data.
  6. What your function returns goes through the response model (extra fields are dropped) and is sent back as JSON with a status code, such as 200.
A model answer in 5 sentences

The client sends a request: a kind such as POST, an address such as /api/chat, and a JSON body. The server program, uvicorn, receives it and hands it to FastAPI. FastAPI looks for a function that matches both the address and the kind of request, and answers 404 or 405 if there is none. Then it checks the body with the request model and answers 422 if the data is wrong, without running my function. If the data is fine, my function runs, its result is filtered by the response model, and it goes back as JSON with a status like 200.

Count your ticks. 6 ticks: very clear. 3 to 5: good, you found your gaps. 0 to 2: also fine, the next step fills them in.

4 · Look at the evidence 5 min

Do not trust a model answer, even a good one. Watch it happen. In api.py, add a print as the first line of your chat function:

@app.post("/api/chat", response_model=ChatResponse)
def chat(request: ChatRequest) -> dict[str, Any]:
    print("chat function is running")
    return {...}

Start the server (uv run uvicorn my_ai_project.api:app --reload), then in another terminal send four requests: a good one, an empty question, a GET on the POST address, and an address that does not exist.

curl -s -o /dev/null -X POST http://127.0.0.1:8000/api/chat -H "Content-Type: application/json" -d '{"question": "What is E101?"}'
curl -s -o /dev/null -X POST http://127.0.0.1:8000/api/chat -H "Content-Type: application/json" -d '{"question": ""}'
curl -s -o /dev/null http://127.0.0.1:8000/api/chat
curl -s -o /dev/null http://127.0.0.1:8000/nope

Read the server terminal. Predict first: how many times will you see chat function is running?

You should see
chat function is running
INFO: 127.0.0.1:55870 - "POST /api/chat HTTP/1.1" 200 OK
INFO: 127.0.0.1:55872 - "POST /api/chat HTTP/1.1" 422 Unprocessable Entity
INFO: 127.0.0.1:55874 - "GET /api/chat HTTP/1.1" 405 Method Not Allowed
INFO: 127.0.0.1:55876 - "GET /nope HTTP/1.1" 404 Not Found

The numbers after 127.0.0.1: differ on every run.

Only the first request reached your function. The 422, 405 and 404 were all stopped before it, and each one stopped at a different place. Remove the print when you are done.

5 · Fix the biggest gap 3 min

Look at the key points you did not tick. Pick the one that matters most, and write a better sentence for it, using the evidence from the server log if it helps. Put your five sentences in your notes, so you can compare them with your next teach-back.

Your explanation is private. You can share one sentence in the comments if you like.
