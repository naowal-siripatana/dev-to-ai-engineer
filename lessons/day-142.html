Docker for the Python AI service

Today you will be able to write a Dockerfile for the Python service, build and run one image, and say why the order of its layers and the host address matter.

Answer from memory, then open the answers.

  2. Why does your Python service read DATABASE_URL from the environment and not from the code?
Answers

  2. The address and the password change between your laptop and any other place the service runs. Code that reads them from the environment can run in both without an edit.

2 · Hook 2 min

“It works on my machine.” Your service needs Python 3.12, 191 MB of packages and a 64 MB model file. A friend has Python 3.9 and no uv. How do you send them your machine and not a list of steps?

Guess first, then open

You send a box with the Python, the packages, the model and your code already inside. That box is a Docker image. When you start it, the running copy is a container. Today you write the recipe for the box.

3 · The idea, in three small pieces 8 min

Be clear about what was run. The Docker engine on the author’s laptop did not respond, and the disk was too full to pull images, so the image of this lesson was never built and no container was started. What was run for real is every step of the recipe by hand, outside Docker: the same uv commands, the same model download and the same server, with the sizes and outputs shown below. The docker build and docker run commands are standard, but their output is not shown, because it was never produced. If your build fails, the error message is the lesson: read it and tell us.

Piece 1: image and container

An image is a read-only package: a small Linux system, your files and your settings. A container is one running copy of an image. You can start ten containers from one image, and deleting a container does not delete the image. Analogy: the image is a recipe card with the ingredients; the container is the dish you cooked from it today.

Piece 2: a Dockerfile is a list of layers

Each line of a Dockerfile that changes files makes a layer. Docker keeps the layers it has built before and reuses them while nothing above has changed. So the order matters: put what changes rarely (the list of packages) first and what changes often (your code) last. A multi-stage build uses one stage to install and build and a second, clean stage that only copies the result: the tools stay behind and the final image is smaller.

Piece 3: a container has its own network and its own user

Inside a container, 127.0.0.1 means that container only. A server that listens on 127.0.0.1 cannot be reached through -p 8000:8000; it must listen on 0.0.0.0 (all addresses). And a process should not run as root inside the box: create a plain user and switch to it with USER.

If you know another typed language (C# as the example): a multi-stage Dockerfile is the same idea as dotnet publish: the SDK compiles, and only the output goes on a smaller runtime. The Python stage plays the SDK, the second stage plays aspnet. On Day 147 you write the real .NET one.
Capstone: this is the first of three images (Python, gateway, page). One command will start all of them on Saturday.

4 · Worked example 5 min

Read it first. The Dockerfile for the service sits next to pyproject.toml, in the project folder. Four things to look for: two stages; the packages before the code; --no-editable; and 0.0.0.0 with a non-root user.

# syntax=docker/dockerfile:1

# ---- stage 1: build the environment (this stage is thrown away) ----
FROM python:3.12-slim AS build
COPY --from=ghcr.io/astral-sh/uv:0.12.23 /uv /usr/local/bin/uv
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy UV_PROJECT_ENVIRONMENT=/opt/venv
WORKDIR /app
# 1. only the files that decide the dependencies: this layer is cached until they change
COPY pyproject.toml uv.lock README.md ./
RUN --mount=type=cache,target=/root/.cache/uv uv sync --frozen --no-dev --no-install-project
# 2. then the code, installed as a real package (--no-editable): an editable install points at /app/src, which the last stage does not have
COPY src ./src
RUN --mount=type=cache,target=/root/.cache/uv uv sync --frozen --no-dev --no-editable
# 3. bake the embedding model into the image, so that no container downloads 64 MB at start
ENV FASTEMBED_CACHE_PATH=/opt/models
RUN /opt/venv/bin/python -c "from fastembed import TextEmbedding; TextEmbedding('BAAI/bge-small-en-v1.5')"

# ---- stage 2: the image that runs ----
FROM python:3.12-slim
RUN useradd --create-home --uid 10001 app && mkdir /data && chown app /data
COPY --from=build /opt/venv /opt/venv
COPY --from=build /opt/models /opt/models
WORKDIR /app
COPY data/kb ./data/kb
COPY ingest.py ./
ENV PATH=/opt/venv/bin:$PATH FASTEMBED_CACHE_PATH=/opt/models PYTHONUNBUFFERED=1 AUDIT_LOG=/data/audit.jsonl
USER app
EXPOSE 8000
# no curl in a slim image: the health check is a tiny Python call. Exit code 0 = healthy, 1 = not.
HEALTHCHECK --interval=10s --timeout=3s --start-period=30s --retries=3 \
  CMD ["python", "-c", "import urllib.request, sys; sys.exit(0 if urllib.request.urlopen('http://localhost:8000/health', timeout=3).status == 200 else 1)"]
# 0.0.0.0, not 127.0.0.1: inside a container, 127.0.0.1 is reachable only from inside that container
CMD ["uvicorn", "my_ai_project.api:app", "--host", "0.0.0.0", "--port", "8000"]

What was run for real, step by step outside Docker. The environment and the model, the two big things in the image:

You should see
no-dev environment (uv sync --frozen --no-dev): 191 MB, pytest and pgserver are not in it, the app imports embedding model cache (BAAI/bge-small-en-v1.5): 64 MB

pytest and the throwaway database package are absent from the 191 MB: they sit in the dev group, not in the image. And the reason for --no-editable, from a real run:

You should see
editable install (uv sync):
  python -c "import my_ai_project; print(my_ai_project.__file__)"   (run from /)
  <scratch>/proj/src/my_ai_project/__init__.py                       <- points back at the source folder

--no-editable:
  <scratch>/venv-noeditable/lib/python3.12/site-packages/my_ai_project/__init__.py   <- a real copy inside the environment

The second stage copies only /opt/venv. With an editable install it would copy a file that says “my code is in /app/src”, a folder the second stage does not have. And the binding, from a real run on a laptop:

You should see

  curl http://127.0.0.1:8041/health        -> HTTP 200
  curl http://<this machine's LAN address>:8041/health  -> connection refused

uvicorn --host 0.0.0.0 --port 8042
  curl http://127.0.0.1:8042/health        -> HTTP 200
  curl http://<this machine's LAN address>:8042/health  -> HTTP 200

You should see

5 · Try it 30 min

Work in python-service (your my-ai-project), on a branch: git switch -c docker. You need Docker Desktop (or another Docker engine) running. Check with docker version: if it hangs, restart Docker and try again. If you cannot run Docker today, do steps 1 and 4 on paper and read the lesson for the rest: nothing is lost.

Step 1 Copy and build

Add the Dockerfile and the .dockerignore. Move pgserver from the dependencies to the dev group of pyproject.toml and run uv lock, so the image does not carry a test database. Then run docker build -t pumpguard-ai .. The first build is slow: it downloads the base image, the packages and the model.

Step 2 Run it

Run the container with the port open and a DATABASE_URL (the database of Day 60 on port 5433; from inside a container the laptop is host.docker.internal). Call /health. Then run docker ps and docker images and find the container and the image: which is which?

Step 3 Break it on purpose

Change --host 0.0.0.0 to --host 127.0.0.1, rebuild, run and call /health again. Predict first: will it answer? Read what you get, then put it back. (On the laptop, outside Docker, the same change made the machine’s own network address refuse the connection.)

Step 4 Your turn

Prove that the order of layers matters. Edit one line of a .py file and build again: it should take seconds, because the package layers are reused. Then try the slow order from Stuck, edit the same file, and build again. Write down both times. Finally commit: git add Dockerfile .dockerignore pyproject.toml uv.lock and git commit -m "Add a Dockerfile for the AI service".

6 · Stuck? anytime

  • The build cannot reach the Docker engine (it hangs or says it cannot connect): Docker Desktop is not running. Start it and wait until it says it is running.
  • “no space left on device”: images are big. Run docker system df to see the use, and remove only what you know is yours (docker image rm), never a blanket prune of things you did not create.
  • ModuleNotFoundError: my_ai_project in the container: the editable install problem. Check that the second uv sync has --no-editable.
  • The container starts and stops at once: run docker logs with the container name and read the last lines. A missing DATABASE_URL or a database that is not reachable shows there.
  • The call to /health gets no answer: check the host in CMD (0.0.0.0) and the -p 8000:8000 on the run command.
Hint: Step 4

Layers are cached from the first line that changed. If the COPY of the code comes before the install, then every edit of the code throws away the install layer as well.

Solution: Step 4 (the two orders)
# slow: the code comes first, so every edit of a .py file re-installs all the packages
COPY . .
RUN uv sync --frozen --no-dev

# fast: the files that decide the packages come first
COPY pyproject.toml uv.lock README.md ./
RUN uv sync --frozen --no-dev --no-install-project
COPY src ./src

Your times will differ by machine. The pattern is what matters: the right order rebuilds only the last layer.

Why a slim image has no curl

The base image is small on purpose. A health check that needs a tool must carry it. A Python one-liner uses what is already there. The exit code is the whole contract: 0 healthy, 1 not.

7 · Check yourself 5 min

  1. What is the difference between an image and a container?
  2. Why do the packages come before the code in the Dockerfile?
  3. Why 0.0.0.0 and not 127.0.0.1 in the container?
Answers
  1. An image is the read-only package; a container is a running copy of it. Many containers can come from one image.
  2. Layers are reused until a line changes. The packages change rarely and the code often, so this order keeps the slow layer cached.
  3. Inside a container 127.0.0.1 is only that container, so a published port cannot reach it. 0.0.0.0 listens on every address of the container.
