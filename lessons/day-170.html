2 · Hook 2 min

You have one week to the workshop and a list of 20 things that could be better. You can fix three. Which three?

Guess first, then open

The three that would hurt most in front of people, ranked by who is hurt and how likely it is, and cheap enough to fix with a test. The rest are not ignored: they go into the README as known limits, said honestly.

3 · The idea, in three small pieces 8 min

Piece 1: hunt before you decide

You will not find your worst bug by reading code you wrote. Send it awkward requests on purpose: empty, huge, in another language, not JSON, no body, the wrong method, an injection, the same vote ten times, the service behind it switched off. Write the cases in a small script, so that you can run them again after each fix.

Piece 2: rank by who is hurt and how likely

A bug that corrupts your numbers (the dashboard) or leaks internals matters more than a cosmetic one, and a bug that can strike every day matters more than one that needs a rare input. Write the ranking down, with the size of the fix, then take the top three that are small.

Piece 3: a test that fails first

For each bug write the test before the fix and watch it fail; then fix and watch it pass. A test you never saw fail may not test anything. And some things you will not fix (a multilingual model, a real login): write them as known limits, which is a fix of a different kind: the reader is not surprised.

If you know another typed language (C# as the example): the probe is a fuzz test by hand (the same idea as sending random input to a parser), and ranking by who is hurt is the severity and likelihood table of a risk register. /health against /ready is the liveness and readiness probe split of Kubernetes, also used by any load balancer.
Capstone: today you fix three bugs of your own system. The final checklist you build is the one you run again on Thursday and on the morning of the workshop.

"""Send awkward requests to the gateway and print the status and the start of each answer. Usage: python scripts/probe.py [base_url]"""
import json
import sys
import urllib.error
import urllib.request

BASE = sys.argv[1] if len(sys.argv) > 1 else "http://localhost:5100"


def call(method: str, path: str, body: object | None = None, headers: dict[str, str] | None = None, raw: bytes | None = None) -> tuple[int, str]:
    data = raw if raw is not None else (json.dumps(body).encode() if body is not None else None)
    request = urllib.request.Request(BASE + path, data=data, method=method, headers={"content-type": "application/json", **(headers or {})})
    try:
        with urllib.request.urlopen(request, timeout=30) as response:
            return response.status, response.read().decode()[:110]
    except urllib.error.HTTPError as err:
        return err.code, err.read().decode()[:110]
    except urllib.error.URLError as err:
        return 0, str(err.reason)[:110]

Bug 1, one vote per answer. A unique index and an upsert: the last vote wins. The old duplicates are cleaned first, so that the index can be made on a table that already has them:

CREATE UNIQUE INDEX IF NOT EXISTS feedback_one_vote_per_answer ON feedback (request_id);
-- and before it, so that old data does not break the index:
DELETE FROM feedback a USING feedback b WHERE a.request_id = b.request_id AND a.id < b.id;   -- keep the latest

    (request_id, rating, clean),

def test_one_vote_per_answer_the_last_vote_wins(dsn: str) -> None:

Bug 3, a health check that lies. /health stays as liveness (the gateway runs). A new /ready asks the service behind it, with a 2-second limit:

// Program.cs
app.MapGet("/health", () => Results.Ok(new { status = "ok" }));   // liveness: the gateway itself is running

// readiness: the gateway AND the service behind it. A 503 here means "do not send me traffic yet"
app.MapGet("/ready", async (PythonServiceClient python, CancellationToken cancellationToken) =>
    await python.IsReadyAsync(cancellationToken)
        ? Results.Ok(new { status = "ready" })
        : Results.Problem(detail: "the AI service is not reachable", statusCode: StatusCodes.Status503ServiceUnavailable));

5 · Try it 30 min

Work on your own capstone, on a branch: git switch -c final-bugs. Start your whole system first.

Step 1 Copy and run

Add scripts/probe.py (open the probe above) and change the cases to the routes of your system. Run it and read every line. Write down anything that surprises you: a status you did not expect, a message that shows internals, a hang.

Step 2 Change one thing

Add three cases of your own that fit your system (a second vote, a very long word without spaces, a question that has only punctuation, the service behind you switched off). Predict each status before you run it.

Step 3 Break it on purpose

Stop the service behind your front door, and call /health and then a real route. Does the health check tell the truth? Then rank everything you found in a table like the one above: who is hurt, how likely, how big the fix.

Step 4 Your turn

Fix the top three small ones, each in the same order: a test that fails, the fix, the test passes. Write the others into the README as known limits. Then run the whole checklist (below) and commit by name: git add the changed files, git commit -m "Fix the three worst known bugs".

FINAL CHECKLIST (each line is a command or a screen, not a feeling)
[ ] the README steps work from a fresh clone, with a new empty database
[ ] diagram check, secret finder, types, tests, page build: all green
[ ] the demo path, run for real, twice
[ ] the awkward-request probe: nothing leaks, nothing crashes
[ ] known bugs: the top 3 fixed or written down; the rest in "known limits"
[ ] what has not been run: written in the README

6 · Stuck? anytime

  • You find no bugs: you are probing the cases you already thought of. Ask someone else for three odd inputs, or try the other end: switch a dependency off.
  • You find too many: rank them. The top three small ones, then stop. A fixed small bug beats a half-fixed big one.
  • The test passes before the fix: it does not test the bug. Make the test check the exact thing that was wrong (the text of the answer, the number of rows).
  • A fix breaks another test: read the other test. It may have been written around the bug. Change it only if the old behaviour was wrong, and say so in the commit message.
Hint: Step 3

A liveness check answers “is this process running?”. A readiness check answers “can it do its job right now?”, so it must ask what the job needs.

7 · Check yourself 5 min

  1. How do you rank bugs when you can fix only three?
  2. Why write the test first and watch it fail?
  3. What is the difference between /health and /ready?
Answers
  1. By who is hurt and how likely it is, and by the size of the fix: the worst small ones first.
  2. A test that you never saw fail may not test the bug. Failing first proves it can fail, passing after proves the fix.
  3. /health says the process runs (liveness); /ready says it can do its job, so it checks what it depends on.
