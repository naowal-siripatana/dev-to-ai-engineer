DAY 53 · LEVEL 5: PROMPTS AND CONTEXT

Prompt engineering: rules, examples, failure modes

50-60 minhands-onfree
Today you will be able to rewrite a weak prompt into one with numbered rules, two examples and a rule for the missing answer.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Which of these do you retry: 429, 401, a timeout? Why?
  2. Why is a stream retried only before its first piece?
Answers
  1. 429 and a timeout may go away, so retry with backoff. 401 (wrong key) will fail every time, so do not retry.
  2. After a piece went to the user, a retry would repeat or mix the text.

2 · Hook 2 min

Your prompt is “You are a helpful assistant. Answer the user’s question using the documents.” It works in every demo. Then a customer asks the price of the monitor, and the documents do not say. What does a model that wants to be “helpful” do?

Guess first, then open

Very often it helps by making something up: a plausible price, a plausible fix. Nothing in the prompt told it that “I do not know” is an acceptable answer. A prompt is not a wish, it is a specification. Today you rewrite a weak prompt into one that says what to do, shows two examples, and covers the case that the answer is missing.

3 · The idea, in three small pieces 8 min

Piece 1: write rules, not wishes

“Be helpful” is a wish. A rule is something you can check: use only the sources, answer in at most two short sentences, name the source in square brackets, if the sources do not contain the answer, reply with exactly this sentence. Number the rules, keep each one short, and say what to do, not only what to avoid. Include a rule for the case where the answer is not there.

Piece 2: show two examples (few-shot)

An example shows the format and the behaviour better than a paragraph of explanation. Giving a few examples is called few-shot prompting. Two are often enough: one normal case and one “I do not know” case. Write them in the same shape as the real input. And keep them different from the questions you test with: if a test question is in the prompt, you are measuring memory, not skill (the same mistake as tuning on the test set on Day 27).

Piece 3: know the failure modes, and measure

The usual ways a prompt fails: the model makes things up when the sources do not contain the answer, it ignores the format, it is too long, it refuses too much, or two rules contradict each other. You cannot see these by reading the prompt. You see them by running a few questions and checking the answers with simple tests. And remember the price: the system prompt is sent every time, so a longer prompt costs tokens on every call.

If you know another typed language (C# as the example): a system prompt is like a configuration file and a contract for a component: it should be readable, versioned in Git and tested. The few-shot examples are like unit-test fixtures that show the expected input and output, and the “do not test with your examples” rule is the same as not using the same data in the test and in the production code.
Capstone: the assistant must cite sources and must say when it does not know. Both come from the system prompt you write now. On Saturday you measure the difference on five questions.

4 · Worked example 5 min

Read it first. Two system prompts for the same job: the weak one from the hook, and a better one with four rules and two examples (one normal, one “not found”). src/my_ai_project/prompts.py:

NO_ANSWER = "I could not find that in the knowledge base."

WEAK_SYSTEM = "You are a helpful assistant. Answer the user's question using the documents."

BETTER_SYSTEM = f"""You are a support assistant for the PumpGuard monitor.

Rules:
1. Use only the sources in the user message. Do not use any other knowledge.
2. Answer in at most two short sentences.
3. After each fact, name its source in square brackets, like [error-e101].
4. If the sources do not contain the answer, reply with exactly: {NO_ANSWER}

Example 1
Question: What does error E107 mean?
Sources:
[error-e107] E107 Calibration expired. The last calibration is older than 30 days, so readings may drift.
Answer: The last calibration is older than 30 days, so readings may drift [error-e107].

Example 2
Question: Can I pay in instalments?
Sources:
[faq-warranty] What does the warranty cover? The monitor has a two year warranty on manufacturing faults.
Answer: {NO_ANSWER}"""

The user message carries the sources and the question, in the same shape as the examples. src/my_ai_project/answering.py keeps the instructions out of it (they live in the system prompt):

from typing import Protocol

from pydantic import BaseModel

from my_ai_project.prompts import BETTER_SYSTEM, NO_ANSWER
from my_ai_project.retrieval import InMemoryIndex



class LlmClient(Protocol):
    def complete(self, prompt: str, system: str | None = None) -> str: ...


class Answer(BaseModel):
    text: str
    sources: list[str]


def build_user_message(question: str, index: InMemoryIndex, doc_ids: list[str]) -> str:
    by_id = {document.doc_id: document for document in index.documents}
    context = "\n".join(f"[{doc_id}] {by_id[doc_id].title}. {by_id[doc_id].body}" for doc_id in doc_ids)
    return f"Question: {question}\nSources:\n{context}"


def answer_question(
    question: str,
    index: InMemoryIndex,
    client: LlmClient,
    top_k: int = 3,
    min_score: float = 0.55,
    system: str = BETTER_SYSTEM,
) -> Answer:
    hits = index.search(question, top_k)
    if not hits or hits[0].score < min_score:
        return Answer(text=NO_ANSWER, sources=[])
    doc_ids = [hit.doc_id for hit in hits]
    return Answer(text=client.complete(build_user_message(question, index, doc_ids), system), sources=doc_ids)

A tiny script to look at the two prompts and what each costs. show_prompts.py:

from my_ai_project.prompts import BETTER_SYSTEM, WEAK_SYSTEM
from my_ai_project.tokens import count_tokens

for name, system in (("weak", WEAK_SYSTEM), ("better", BETTER_SYSTEM)):
    print(f"--- {name} system prompt: {count_tokens(system)} tokens, {len(system.split())} words")
    print(system)
You should see
--- weak system prompt: 14 tokens, 12 words
You are a helpful assistant. Answer the user's question using the documents.
--- better system prompt: 195 tokens, 140 words

...
(the rules and the two examples follow)

The better prompt is about 14 times longer (195 tokens against 14), and you pay for those tokens on every call. That is a trade-off: it is worth it only if the answers get better, which is why you measure.

6 · Stuck? anytime

  • Your token counts differ a little: a small change in the text (a space, a quote) changes the count. Compare the size, not the exact number.
  • The leak test fails and you do not see why: print the test questions and search your prompt for each one. Even a part of the question can count if the whole sentence is there.
  • Your rewritten prompt gets long: cut the rules that repeat each other, and keep one example for each behaviour you really need.
  • You cannot tell if the new prompt is better: you cannot, by reading. You need questions and checks. Saturday builds that.
Hint: Step 4

Start from the three parts of the better prompt: who the assistant is, the numbered rules, and the examples. For the summary, a rule can fix the length (“one sentence of at most 20 words”) and another the exact sentence for the empty case. Write the examples in the same shape as the real input: the word Ticket: and the word Summary:.

Solution: Step 4 (one possible answer)
You turn a support ticket into a short summary for the person who answers it.

Rules:
1. Use only what is in the ticket. Do not guess a cause.
2. Write one sentence of at most 20 words, then a line "Priority: low, normal or urgent".
3. If the ticket has no problem in it, reply with exactly: No problem found.

Example 1
Ticket: Hello, my monitor shows E101 again since this morning. The pump is still running. Thanks!
Summary: The monitor shows error E101 again since this morning, and the pump still runs.
Priority: normal

Example 2
Ticket: Thanks, it works now!
Summary: No problem found.

Check yours against these questions:

Questions to ask about your rewritten prompt:
1. Does each rule say what to do, in words a stranger can follow?
2. Is there a rule for the case where the answer is not there?
3. Do the examples look like the real input, and differ from the questions I will test with?
4. Does a rule contradict another one?
The tests that come with the prompts (save them as tests/test_prompts.py)
from my_ai_project.prompts import BETTER_SYSTEM, NO_ANSWER

TEST_QUESTIONS = [
    "My monitor stopped responding",
    "How long does the battery last?",
    "What does error E105 mean?",
    "Where can I buy a coffee?",
    "How much does the monitor cost?",
]


def test_the_better_prompt_has_the_rules_and_two_examples() -> None:
    assert BETTER_SYSTEM.count("Example ") == 2
    assert "square brackets" in BETTER_SYSTEM
    assert NO_ANSWER in BETTER_SYSTEM


def test_the_examples_do_not_contain_the_test_questions() -> None:
    assert all(question not in BETTER_SYSTEM for question in TEST_QUESTIONS)

7 · Check yourself 5 min

  1. What is the difference between a wish and a rule in a prompt? Give one of each.
  2. Why should the examples be different from your test questions?
  3. Why is a longer system prompt not always better?
Answers
  1. A wish cannot be checked (“be helpful”). A rule can (“answer in at most two sentences”, “if the sources do not contain the answer, reply with exactly this sentence”).
  2. If a test question is in the prompt, a good answer may be memory, and the test no longer tells you how the prompt works on new questions. It is the same mistake as tuning on the test set.
  3. You pay for its tokens on every call, and more rules can contradict each other or distract the model. Add a rule only when a failure you measured needs it.
