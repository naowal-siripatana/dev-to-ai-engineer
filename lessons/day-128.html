2 · Hook 2 min

A user writes: “I asked a question at 11:49 and it took forever.” Your system has a .NET gateway, a Python service and a database. In which log do you look, and for what?

Guess first, then open

You cannot look in one: the request passed through several. You need something that is the same in every one: a request id. The gateway makes it (or accepts the caller’s), sends it to the Python service, and both write it on every log line. Then one search finds the whole story of one request, in every service.

3 · The idea, in three small pieces 8 min

Piece 1: logs, metrics and traces

Logs say what happened, one line per event. Metrics are numbers about many requests (a median, an error count). A trace follows one request through several services and shows where the time went. You need all three, and the thing that connects them is the request id (also called a correlation id or trace id).

Piece 2: one id, set at the door, passed on, written everywhere

The first service that sees the request sets the id: it uses the caller’s if it is safe, and makes a new one if not. It puts the id on the response, so the caller can quote it, on every log line, and in the header of every call to the next service. A header comes from outside, so it is user input: accept only a safe shape (letters, digits, dot, dash, underscore, up to 64 characters). A newline in it could forge extra lines in your log.

Piece 3: log what you will need at 2 a.m., and not what you must protect

For an LLM call, record the route, the role, the latency, the model, the tokens, the outcome, and the ids of the sources, and whether a guardrail blocked something. Keep out secrets, and be careful with the text of prompts and answers: they may hold private data, so hide it (as the audit log hides emails) or do not store it.

If you know another typed language (C# as the example): ASP.NET Core already gives every request a TraceIdentifier and, through Activity, a W3C trace id (the traceparent header). Our X-Request-Id is the simplest version of the same idea, and it is the stepping stone to OpenTelemetry. In .NET, ILogger.BeginScope is how you put the id on every line; in Python, a logging.Filter and a ContextVar do it.
Capstone: Module 12 ends with a dashboard of five numbers, built on the rows you will store per request. It all starts with the id.

4 · Worked example 5 min

The three kinds of record, and what to put in an LLM call’s record:

LOGS     what happened, in words, one line per event.            'POST /api/ask -> 200 in 3584 ms'
METRICS  numbers about many requests, to count and compare.       'median 8 ms, p95 10 ms, 1 error in 20'
TRACES   the path of ONE request through several services.        'demo-123: gateway 3723 ms, of which Python 3584 ms'
All three share one thing: the REQUEST ID, so that you can move from a number, to a line, to one request.
what to record for an LLM call                              what to keep out
request id, route, role, status, outcome                     secrets and keys
latency (and where the time went)                            the full prompt and answer text (they may hold private data)
model name, input tokens, output tokens, cost                questions as typed, unless hidden (emails) and with a retention rule
which sources were used (ids, not text)
whether a guardrail blocked something, and why

The Python side, in src/my_ai_project/observability.py: a context variable that holds the id of the current request, a function that cleans an incoming id, and a logging filter that adds it to every line:

import contextvars
import logging
import re
import uuid

request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id", default="-")

# What a request id may look like when it comes from outside. Anything else is replaced: a header is user input, and a newline in it
# would let a caller forge extra lines in your log.
VALID_REQUEST_ID = re.compile(r"[A-Za-z0-9._-]{1,64}")


def clean_request_id(value: str | None) -> str:
    """Use the id the caller sent if it is safe, otherwise make a new one."""
    if value is not None and VALID_REQUEST_ID.fullmatch(value):
        return value
    return uuid.uuid4().hex


class RequestIdFilter(logging.Filter):
    """Puts the id of the current request on every log record, so that one grep follows a request through the whole system."""

    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True


LOG_FORMAT = "%(asctime)s %(levelname)s %(name)s rid=%(request_id)s %(message)s"


def setup_logging() -> None:
    logging.basicConfig(level=logging.INFO, format=LOG_FORMAT)
    for handler in logging.getLogger().handlers:
        handler.addFilter(RequestIdFilter())

Read it as an investigator. The gateway took 3723 ms, and the Python service took 3584 ms of that: so about 140 ms were spent outside Python (the gateway, the network). And the whole request was slow because it was the first one: the Python service loads its model and builds its keyword index on the first request. You would never have known without the id and the times.

6 · Stuck? anytime

  • The id is - in the log: the filter is not on the handler, or the line was written outside a request (for example by uvicorn’s own access log, which does not use your filter).
  • The id is missing in the audit log: audit.py must read request_id_var, and the middleware must set it before the route runs.
  • The response has no header: set it on the response object that comes back from call_next.
  • mypy and the middleware: the function has an untyped signature in the diff, with a comment that explains it.
Solution: Step 2 (the shape to expect, abbreviated)
You should see
$ curl -D - -X POST localhost:8000/api/ask -H "x-demo-role: staff" -H "X-Request-Id: demo-123" -d '{"question": "What does error E104 mean?"}'
HTTP/1.1 200 OK
x-request-id: demo-123

$ grep demo-123 python.log audit.jsonl
python.log: ... INFO api rid=demo-123 POST /api/ask -> 200 in ... ms
audit.jsonl: {"time": "...", "request_id": "demo-123", "event": "question", "role": "staff", ...}

With your own safe id the response repeats it. Without one, the service makes a new 32-character id, and the caller can quote it when it reports a problem.

Solution: Step 3

The unsafe ids are replaced by a new 32-character id, and the bad value never reaches a log line. A header is something the caller writes: if you copied it into your log as it came, a caller could put a line break in it and write fake lines, for example a line that says an administrator logged in. Checking the shape of everything that comes from outside is the rule here, as in Module 11.

Solution: Step 4 (what is still missing)

Usually: how many tokens the request used, what it cost, and how it ended (answered, refused or failed), as numbers that you can add up across requests. Logs are for reading one request; for the totals you need a table. That is Wednesday.
