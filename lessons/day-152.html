DAY 152 · LEVEL 13: DEPLOYMENT · MIXED PRACTICE

Mixed practice: make a failing test block the build

40 minhands-onfree
Today you will be able to write a small workflow from a blank file where a red test stops the build, and say how a gate can be undone by mistake.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. What does needs: do between two jobs?
  2. Why does the CI of your project use LLM_MODE=fake?
Answers
  1. The second job starts only when the first is green; if it fails, the second is skipped.
  2. CI must not need a real key: a leak would cost money, and a test must not touch a real model.

2 · Today 2 min

Today you practise without the lesson open. Goal: a red test stops the image build, and you can show it. You write a small workflow from a blank file, then compare with the model.

Be clear about what was run. The workflow was never run on GitHub. What was run for real: the linter on the file, a test that fails on purpose (with the real exit code), and the same command behind && and behind || true. How GitHub shows a skipped job is standard behaviour that was not observed.

3 · Plan first 5 min

Draw two boxes and one arrow on paper: which job runs first, which must wait, and what should happen to the second when the first is red? Then open the sketch.

The plan
test    -> runs the tests                         red = stop
build   -> needs: test, builds the image          grey (skipped) when test is red
(the rule: a job that must not run after a failure says needs:)

4 · Do it from a blank file 25 min

On the branch ci. Write each piece before you open the model. Run the linter after each one.

  1. A trigger. Run on every push, and nothing more. Give the workflow a name and the least permission: only reading the code.
  2. A job that tests. Check out the code, set up uv, install with the lock file, run the tests.
  3. A job that builds an image. It must run only if the test job is green.
  4. A test that fails on purpose. Add tests/test_broken.py (in the model). Run pytest on your laptop and read the last lines and the exit code (echo $?).
  5. The gate, in the shell. Put && between the test command and a harmless echo that stands for the build. Run it with the broken test and without it.

Break it on purpose: (a) misspell the name in needs: and read the linter. (b) Add || true after the test command and run it with the broken test: what is the exit code of the line, and what would the job do on GitHub?

5 · Compare with the model 10 min

Piece 5: the gate, and the hole
uv run pytest -q && echo "build the images"          -> prints "build the images" only if pytest exits with 0
(uv run pytest -q >/dev/null 2>&1 && echo "build the images") || echo "tests failed: no build"
                                                       -> with the broken test: tests failed: no build

And the same line with || true (run for real):

uv run pytest -q || true ; echo "exit code of the line: $?"
                                                       -> the failing test is printed, and the exit code of the line is 0

That is the hole: || true (or continue-on-error: true on a step) turns a failure into a pass, so nothing is blocked and the mark is green. Tests that cannot fail are decoration. If a test is flaky, fix or remove the test; do not hide the failure.

One more thing the file cannot do: the mark on the commit is information, not a lock. To stop a merge while the mark is red, the repository has a setting called a branch protection rule (or a ruleset): “require status checks to pass”, naming the jobs. It is a setting of the repository on GitHub, not a line in the workflow, and it was not set or tested for this lesson (general knowledge, you will see it in the settings page).

6 · Check yourself 5 min

  1. What exit code does a failing pytest return, and why does CI care?
  2. Why does || true hide a failure?
  3. What is the difference between a red mark and a blocked merge?
Answers
  1. 1 (not 0). CI treats any non-zero exit code as a failure of the step, and so of the job.
  2. It runs true when the command fails, and true exits with 0, so the line as a whole reports success.
  3. The red mark only tells; a branch protection rule on the repository can refuse the merge while a named check is not green.
