Mixed practice: /api/summarize with a fake LLM

40 minhands-onfree
Today you will be able to build POST /api/summarize from a blank file, with a fake LLM and tests that prove it.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Why does a test for an AI function use a fake client instead of the real model?
  2. A request has top_k 99 and the limit is 10. What does the client get back?
Answers
  1. So the test is fast, free and gives the same answer every time. It checks your code, not the model.
  2. A 422 that says the value must be at most 10. Pydantic stops the request before your function runs.

2 · Hook 2 min

Today there is no recipe to copy. You have a goal, a small contract, and everything you need is already in your project. How much of it can you build from memory?

Why a blank file?

Mixing old ideas into one new task is what makes them stick. Reading a recipe feels easy and teaches little. Getting stuck for two minutes and then finding the answer teaches a lot. If you get stuck, the Stuck section has hints before solutions.

3 · The idea, in three small pieces 5 min

No new ideas today. Here is the map of what you will reuse.

Piece 1: a fake model (Day 5)

A small class with a complete(prompt) method that returns a fixed answer. Your summarize function from Day 5 takes any client that has that method, so the fake can stand in for the real model.

Piece 2: models in, models out (Day 9 and Day 11)

One model for what the client sends, one for what comes back, and a route that connects them.

Piece 3: one test through the front door (new, but small)

TestClient lets a test call your API like a client does, without starting a server. You call client.post(...) and check the status code and the JSON.

If you know another typed language (C# as the example): TestClient plays the role of WebApplicationFactory in ASP.NET Core integration tests, and the fake client is a hand-made test double (the same idea as a mock you would register in dependency injection).
Capstone: /api/summarize is the second of the three endpoints you ship this week. Because it talks to a fake today, swapping in a real model later changes one line.

4 · Worked example 3 min

No code to copy today. This is the contract: what your finished endpoint must do. Read it, then build it.

Details
AddressPOST /api/summarize
The client sendstext (required, 1 to 20000 characters) and max_words (a whole number from 1 to 200, default 20)
The client gets backsummary (text) and words (how many words the summary has)
The modelA fake client. It answers (fake) followed by the text, and summarize cuts the answer to max_words words

When it works, this call:

curl -i -X POST http://127.0.0.1:8000/api/summarize -H "Content-Type: application/json" -d '{"text": "Error E101 means the sensor timed out after ten seconds.", "max_words": 5}'
You should see
HTTP/1.1 200 OK
content-type: application/json

{"summary":"(fake) Error E101 means the","words":5}

Note that the summary is cut at 5 words, and the 5 includes the word (fake).

5 · Try it 25 min

Work in my-ai-project, on a branch if you like (git switch -c summarize-api). You need summarizer.py from Day 5 and api.py from Day 11. If you do not have summarizer.py, open Day 5 and copy the finished summarize function and the LlmClient class.

Step 1 The fake client, from a blank file

Create src/my_ai_project/llm.py with a class FakeLlmClient. Its method complete(prompt) returns "(fake) " followed by the prompt without the first part, "Summarize in one sentence: " (look at what summarize sends). Check it before you go on: run uv run mypy src and expect Success: no issues found.

Step 2 The models and the route

In api.py, write SummarizeRequest and SummarizeResponse from the contract table, then the route POST /api/summarize that calls your summarize function with the fake client. Start the server (uv run uvicorn my_ai_project.api:app --reload) and run the call from the worked example. Match the output, including the words number. Then change max_words to 3 and predict the summary before you send it.

Step 3 One test

Add the tools, then write one test in tests/test_api.py that sends the worked-example request through TestClient and checks the status code, the summary and words.

uv add --dev pytest httpx2

Run uv run pytest and expect 1 passed. Then break it on purpose: change the expected words from 5 to 6, run it, and read how pytest shows the difference. Change it back.

Step 4 Your turn: a surprise

Send this request with curl (or from /docs):

curl -i -X POST http://127.0.0.1:8000/api/summarize -H "Content-Type: application/json" -d '{"text": "   "}'

Look at the status code. The text has three spaces, so it passes the min_length rule. What does the client get, and is it a good answer? Fix it so the client gets a clear 400 instead, and add a second test that proves it. You already know two ways to do it from Day 5 and Day 11.

Finally, commit your work: git add . and git commit -m "Add /api/summarize with a fake LLM and tests".

6 · Stuck? anytime

  • “ModuleNotFoundError: No module named 'my_ai_project.llm'”: the file must be inside src/my_ai_project/, and you must run commands with uv run.
  • The summary has no (fake): the fake client must put "(fake) " in front of its answer.
  • Your test fails with ValueError and not a status code: TestClient re-raises an error that your route does not handle. That is the same bug as the 500 in Step 4, shown differently. Fix the route, not the test.
  • “fixture 'client' not found” or “ModuleNotFoundError: httpx2”: run uv add --dev pytest httpx2, and create client = TestClient(app) at the top of the test file.
Hint 1: Steps 1 and 2

Your summarize function has the shape summarize(text, client, max_words) and returns text. The response needs the number of words in that text: split it and count. The route can build the response with SummarizeResponse(summary=..., words=...).

Solution: Steps 1 and 2

src/my_ai_project/llm.py:

class FakeLlmClient:
    """Stands in for the real model: no network, no cost, same answer every time."""

    def complete(self, prompt: str) -> str:
        return "(fake) " + prompt.removeprefix("Summarize in one sentence: ")

Add two imports at the top of api.py, then the models and the route at the bottom:

from my_ai_project.llm import FakeLlmClient
from my_ai_project.summarizer import summarize
class SummarizeRequest(BaseModel):
    text: str = Field(min_length=1, max_length=20000)
    max_words: int = Field(default=20, ge=1, le=200)


class SummarizeResponse(BaseModel):
    summary: str
    words: int
llm_client = FakeLlmClient()


@app.post("/api/summarize")
def summarize_text(request: SummarizeRequest) -> SummarizeResponse:
    summary = summarize(request.text, llm_client, request.max_words)
    return SummarizeResponse(summary=summary, words=len(summary.split()))
Solution: Step 3

tests/test_api.py:

from fastapi.testclient import TestClient

from my_ai_project.api import app

client = TestClient(app)


def test_summarize_returns_a_short_summary() -> None:
    response = client.post(
        "/api/summarize",
        json={"text": "Error E101 means the sensor timed out after ten seconds.", "max_words": 5},
    )
    assert response.status_code == 200
    body = response.json()
    assert body["summary"] == "(fake) Error E101 means the"
    assert body["words"] == 5
Hint 2: Step 4

The 500 comes from a ValueError that summarize raises for blank text, and nothing catches it. Either catch it in the route and turn it into an HTTPException, or reject blank text earlier with a @field_validator like Day 11. (A validator gives a 422, so for a 400 catch it in the route.)

Solution: Step 4

Import HTTPException from fastapi and change the route body:

    try:
        summary = summarize(request.text, llm_client, request.max_words)
    except ValueError as err:
        raise HTTPException(status_code=400, detail=str(err)) from err

Add the second test to tests/test_api.py:

def test_blank_text_is_a_client_error() -> None:
    response = client.post("/api/summarize", json={"text": "   "})
    assert response.status_code == 400
    assert response.json() == {"detail": "text must not be empty"}

Run uv run pytest and expect 2 passed. In a browser or with curl, the blank request now returns 400 and {"detail":"text must not be empty"}.

7 · Check yourself 5 min

  1. In the test, why does nothing call the real model, and what would break if it did?
  2. The blank request gave a 500 before your fix. Whose fault is a 500, and whose fault is a 400?
  3. Which part of today came from which earlier day?
Answers
  1. The route uses the fake client, so the test is fast, free and the same every time. With a real model the test could be slow, cost money and give a different summary on each run.
  2. A 500 means the server failed: your code did something you did not plan for. A 400 (or 422) means the request was wrong and the client can fix it. Blank text is the client’s mistake, so it should be a 400.
  3. The fake client and summarize are from Day 5, the request and response models are from Day 9 and Day 11, the error handling is from Day 5 and Day 11. Only TestClient was new.
