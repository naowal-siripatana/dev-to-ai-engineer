DAY 175 · FINAL WORKSHOP · DAY 1

Final workshop, Day 1: integrate and demo

8 hhands-onfree
Today you will be able to integrate your projects into one repository a stranger can run, and demo it to a room.

1 · Before you start 10 min

Be clear about what this page is. The workshop is a live event: this page is the guide and the sheets for it, and the author did not run a workshop. What was run for real on one laptop, from a fresh clone of the capstone: the integrated repository, the preflight (7 checks, 16 seconds), the demo check, and the three bug fixes of Day 170. The Docker path, the GitHub pipeline and the hosted model were never run: say so, and show what you did run.

Today’s goal: integrate your three projects into one repository that a stranger can run, demo it to the room, and take the feedback. Today is not for new features: the freeze still holds.

Do three things before you open anything else: run your preflight (or the demo check); open your rehearsal sheet; and write your honest sentence on a card next to the laptop.

2 · The plan for the day 10 min

A day of about eight hours, in the order that works: integrate first (while you are fresh), polish, then practise, then demo. Adjust the times to your room.

3 · Integrate 90 min

What “integrated” means: a stranger gets everything from one link and one README. Work through the checklist. If your projects are in three repositories, copy the folders into one (the history of the three is not carried over: say so, or use a tool such as git subtree if you need it).

INTEGRATION CHECKLIST (what "integrated" means: a stranger gets everything from one link)
[ ] ONE repository with the layout:  python-service/  gateway/  web/chat-ui/  compose.yaml  README.md  scripts/  .github/workflows/
[ ] .gitignore keeps out:            .env  .venv/  node_modules/  dist/  bin/  obj/  __pycache__/  caches
[ ] .env.example documents every setting, with fake values
[ ] README: what it is and what is real, the diagram, run with Docker, run without Docker, settings, tests, what has not been run, known limits
[ ] one command to check everything:  bash scripts/preflight.sh
[ ] nothing secret in Git:            the secret finder, from the top of the repository
[ ] the history is readable:          git log --oneline  (short messages that say what changed)

Then the preflight, which runs the checks that you can run:

scripts/preflight.sh
#!/bin/bash
# One command before a demo or a push: every check that can run on this machine, and a clear list of what passed.
# The system (database, python service, gateway) must be running for the last step. Run it from the top of the repository.
set -u
cd "$(dirname "$0")/.."
fail=0
step() { printf '%-34s' "$1"; shift; if out=$("$@" 2>&1); then echo ok; else echo "FAILED"; echo "$out" | tail -5 | sed 's/^/    /'; fail=1; fi; }
step "diagram matches compose.yaml"     python3 scripts/check_diagram.py
step "no obvious secret in Git"         uv run --project python-service python python-service/find_secrets.py
step "python: types"                    bash -c 'cd python-service && uv run mypy src tests'
step "python: tests"                    bash -c 'cd python-service && uv run pytest -q'
step "gateway: tests"                   bash -c 'cd gateway && dotnet test AskGateway.Tests'
step "page: build"                      bash -c 'cd web/chat-ui && npm run build'
step "demo path (system must be up)"   python3 scripts/demo_check.py
[ $fail -eq 0 ] && echo "PREFLIGHT OK" || echo "PREFLIGHT FAILED"
exit $fail

4 · Polish and practise 120 min

Polish only what a check or a stranger finds. Give the repository to the person next to you with a timer and the link only, say nothing, and fix what they hit (as on Day 168). Practise the demo twice aloud with the timer: the second run without stopping. Use your demo check first, and your list of sentences for when it breaks (Day 172).

5 · The demo round 90 min

Each person shows the capstone in three minutes: the problem, how it fits (the diagram), two or three beats running, what is not real, and what next. The others write the feedback sheet while they watch, and do not interrupt. Keep the room kind and specific.

FEEDBACK SHEET for each person you watch (write while they demo, 3 lines are enough)
name / project:                  ...
what I understood in one sentence:  ...
the moment I was most interested:   ...
one thing I would ask them:         ...
one thing I would change:           ...
HOW TO GIVE FEEDBACK (and how to take it)
give:   say what you saw, not what they are ("I could not tell what the page does until minute two", not "it is confusing")
        one thing that worked, one question, one thing to change: in that order
take:   write it down, say thank you, do not defend. Decide later, in the triage.

6 · Feedback and triage 45 min

Read what you got. Sort every line into one of three boxes (as on Day 173): fix now (small, and it would hurt tomorrow), say it (a real limit: put the honest sentence in your talk and your README), or let go (taste, or a new feature: the ticket list). At most three fixes. Then run the preflight again and the demo once.

7 · Check yourself 5 min

  1. What does “integrated” mean for a capstone?
  2. Why does the second rehearsal run without stopping?
  3. How many fixes do you make after the feedback, and what do you do with the rest?
Answers
  1. A stranger gets everything from one link and one README, runs it, and can check it with one command.
  2. On stage you cannot stop: you practise recovering and saying your fallback line.
  3. At most three; the others become honest sentences in your talk and README, or go on the ticket list.
