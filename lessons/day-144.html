Docker Compose: the database and the Python service together

60-70 minhands-onfree
Today you will be able to start the database and the Python service together from one file, with the password kept out of Git.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. What is the difference between an image and a container?
  2. Why does a container that listens on 127.0.0.1 not answer a published port?
Answers
  1. The image is the read-only package, the container a running copy.
  2. Inside a container 127.0.0.1 is only that container. Listen on 0.0.0.0.

2 · Hook 2 min

On Monday you started one container by a long docker run line. Your system needs a database, the Python service, the gateway and a page. Do you type four long lines every morning, in the right order, and remember the passwords?

Guess first, then open

You write the lines once, in a file, and Docker Compose reads it: docker compose up. The file also says which part needs which, so the order is not in your head any more.

3 · The idea, in three small pieces 8 min

Be clear about what was run. The Docker engine on the author’s laptop did not respond, so no image was built and no container was started. What was run for real: docker compose config on the exact file below (the Docker command-line tool checks and prints the file without an engine), including the error you get for a missing password. How the services then talk to each other is standard Compose behaviour that was not run here. If a command below behaves differently for you, trust your screen, and tell us.

Piece 1: one file, many services

A compose.yaml lists services. Each service is one container made from an image (image:) or from a Dockerfile (build:). Compose puts all of them on one private network.

Piece 2: services find each other by name

On that network the name of a service is its address. The Python service does not call localhost to reach the database: it calls db. And the port is the one inside the container (5432), not the one you may publish on your laptop. A service with no ports: cannot be reached from your laptop at all, which is exactly right for a database.

Piece 3: settings and data live outside the container

The password does not go in the file. Compose reads a .env file next to compose.yaml and fills ${POSTGRES_PASSWORD}. The .env file stays out of Git (it goes in .gitignore); an .env.example with a fake value is what you commit. And a database inside a container would lose its data when the container is removed, so the data lives in a named volume (pgdata) that outlives the container.

If you know another typed language (C# as the example): ${POSTGRES_PASSWORD} is the same idea as a connection string from appsettings overridden by an environment variable (ConnectionStrings__Db), and a service name as a host name is like a name registered in a service registry.
Capstone: today two services (the database and the AI service); on Saturday four, and the one command.

4 · Worked example 5 min

Read it first. compose.yaml in the folder that holds python-service:

name: pumpguard

services:
  db:
    image: pgvector/pgvector:pg17
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-assistant}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in the file .env}
      POSTGRES_DB: ${POSTGRES_DB:-assistant}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./python-service/db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    # no 'ports': only the other services need the database, and they reach it by its name, db

  ai:
    build: ./python-service
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER:-assistant}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB:-assistant}
      LLM_MODE: ${LLM_MODE:-fake}
    ports:
      - "8000:8000"   # for today only, so that you can open it from your own machine
    depends_on:
      - db

volumes:
  pgdata:

Look for: the project name; ${POSTGRES_USER:-assistant} (a default if the variable is empty) against ${POSTGRES_PASSWORD:?...} (stop with this message if it is empty); @db:5432 in the address; a named volume and a bind of init.sql (which only runs the first time the data folder is empty). The .env file, with a fake value (the example file is committed, the real one is not):

POSTGRES_PASSWORD=change-me-before-you-share-anything
# LLM_MODE=real
# ANTHROPIC_API_KEY=
.env

Check the file before you start anything. This was run for real, with no engine:

You should see
docker compose config --services
db
ai

docker compose config -q
(no output, exit code 0)

And without a .env file, the same command refuses to continue and says what to do:

You should see

The commands you will use (the standard ones, output not shown, see the box in section 3):

docker compose up -d --build
docker compose ps
docker compose run --rm ai python ingest.py
curl http://localhost:8000/health
docker compose logs ai
docker compose down
# on your laptop:       postgresql://assistant:...@localhost:5433/assistant
# inside Compose:       postgresql://assistant:...@db:5432/assistant
#                                                   ^^ the service name, and the port INSIDE the container

5 · Try it 30 min

Work in the folder that contains python-service, on a branch: git switch -c compose. Docker Desktop must be running for steps 2 to 4. Step 1 needs only the Docker command-line tool, so you can do it even when the engine is off.

Step 1 Write and check

Add compose.yaml, .env (with your own throwaway password, and never a real one) and .env.example, and put .env in .gitignore. Run docker compose config --services and docker compose config -q. Then run git status: .env must not be listed.

Step 2 Start

Run docker compose up -d --build, then docker compose ps. Find both services. Fill the table once: docker compose run --rm ai python ingest.py. Call http://localhost:8000/health and ask one question at /docs.

Step 3 Break it on purpose

Two breaks, one at a time. First delete the password line from .env and run docker compose config: read the message. Then put it back and change @db: to @localhost: in the address, restart the service and look at docker compose logs ai. Predict first: what does “localhost” mean inside the AI container, and is a database there?

Step 4 Your turn

Does your data survive? Run docker compose down, then up -d again and count the chunks (the ingest prints a count; or ask a question). Predict first. Then find out what docker compose down -v does differently, and write one sentence on when you would want each. Commit: git add compose.yaml .env.example .gitignore and git commit -m "Add a Compose file for the database and the AI service".

6 · Stuck? anytime

  • required variable POSTGRES_PASSWORD is missing a value: there is no .env next to compose.yaml, or the line is empty. This is the check doing its job.
  • The service says the connection was refused: the database needs a few seconds to start, and depends_on without a condition only waits for the container to start, not to be ready. Tomorrow fixes that with a health check. For today, restart the service.
  • Port 8000 or 5433 is already in use: another program (or your Day 60 database) has it. Stop it, or publish a different port on the left of the colon.
  • You changed the password in .env but the database still wants the old one: the user and password are set only when the data folder is created. Remove the volume (down -v, which deletes the data) and start again.
Hint: Step 3

Inside a container, localhost is that container. The database is another container, with its own network name.

Solution: Step 3

The AI container looks for PostgreSQL on its own port 5432, finds nothing and fails to connect; the logs show a connection error to localhost. The service name db is the address that works on the Compose network.

Solution: Step 4

down removes the containers and the network but keeps the named volume, so the chunks are still there after up. down -v also removes the volumes: the next start is an empty database and init.sql runs again. Use -v when you want a clean start, never when the data matters.

7 · Check yourself 5 min

  1. How does the AI service find the database in Compose?
  2. Why is the password in .env and not in compose.yaml?
  3. What does down keep and what does down -v remove?
Answers
  1. By the service name, db, on the network Compose creates, with the port inside the container (5432).
  2. The Compose file is committed to Git and shared. The .env file stays on one machine and is ignored by Git, and an example file with a fake value shows what to fill in.
  3. down removes containers and the network and keeps the named volumes. down -v removes the volumes too, so the data is gone.
