DAY 145 · LEVEL 13: DEPLOYMENT · MIXED PRACTICE

Mixed practice: health checks and compose up

40 minhands-onfree
Today you will be able to write health checks and a start order in a Compose file, from a blank file.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. What does depends_on without a condition wait for?
  2. Why does the service reach the database as db and not localhost?
Answers
  1. Only for the other container to start, not to be ready.
  2. localhost is the container itself. The service name is the address on the Compose network.

2 · Today 2 min

Today you practise without the lesson open. Goal: one command, docker compose up -d --build, starts the database, fills it, and starts the AI service only when both are ready. You write the pieces from a blank file, then compare with the model below.

Be clear about what was run. No container was started for this lesson (the Docker engine on the author’s laptop did not respond). Checked for real: the files with docker compose config, two error messages, and the health command with exit codes 0 and 1. That a service really waits for healthy is standard Compose behaviour, and you will see it on your own machine.

3 · Plan first 5 min

Draw the order on paper before you write a line. Who must be ready before whom? Which part runs once and stops? Then open the sketch.

The order
db        healthy (pg_isready says yes)
ingest    starts when db is healthy, fills the table, exits 0
ai        starts when ingest has exited 0, then is healthy when /health answers
gateway   starts when ai is healthy
web       starts when gateway has started

4 · Do it from a blank file 25 min

On the branch compose, in compose.yaml. Write each piece before you open the model. Run docker compose config -q after each one: it needs no engine.

  1. A health check for the database. The program that asks PostgreSQL is pg_isready. It exits 0 when the server accepts connections. Give it an interval of 3 seconds and 15 tries.
  2. A one-off ingest service. The same image as the AI service, with the command python ingest.py, that is not restarted when it stops, and starts only when the database is healthy.
  3. The AI service waits for the ingest to finish with success. There is a condition for a service that runs and exits.
  4. The health check of the AI service itself. It belongs in the Dockerfile as HEALTHCHECK. A slim image has no curl: use the Python one-liner that exits 0 or 1.
  5. Run it. docker compose up -d --build, then docker compose ps: what states do you see, and in what order do they change?

Break it on purpose: misspell a condition (service_healty), and point depends_on at a service that does not exist. Run docker compose config each time and read the message.

5 · Compare with the model 10 min

Open these only after your own try. Piece 1, the database check (note the doubled dollar sign: Compose would otherwise fill the variable in itself, before the shell in the container sees it):

Piece 1
  db:
    image: pgvector/pgvector:pg17
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in the file .env}
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 3s
      timeout: 3s
      retries: 15
Pieces 2 and 3
  ingest:   # runs once, fills the table, and stops
    build: ./python-service
    command: ["python", "ingest.py"]
    restart: "no"
    depends_on:
      db:
        condition: service_healthy

  ai:
    build: ./python-service
    depends_on:
      ingest:
        condition: service_completed_successfully

What Compose resolves from it (run for real, with the engine off):

You should see
  ai:
    depends_on:
      ingest:
        condition: service_completed_successfully
        required: true
  ingest:
    depends_on:
      db:
        condition: service_healthy
        required: true
  (from docker compose config, which also fills in required: true)
Piece 4
HEALTHCHECK --interval=10s --timeout=3s --start-period=30s --retries=3 \
  CMD ["python", "-c", "import urllib.request, sys; sys.exit(0 if urllib.request.urlopen('http://localhost:8000/health', timeout=3).status == 200 else 1)"]

The command, against a local server that was up and then stopped (run for real, outside Docker):

You should see
service up: exit code 0
service down: exit code 1

The start-period gives a slow start (loading the model) time before failures count.

Piece 5
docker compose up -d --build
docker compose ps
docker compose logs ingest
docker compose logs ai

The output is not shown, because no container was started for this lesson. Expect db to be healthy first, ingest to end as Exited (0), and ai to move from starting to healthy. If yours differs, logs says why.

Break it

The two errors, run for real:

You should see
validating /compose.yaml: services.ingest.depends_on.db.condition value must be one of 'service_started', 'service_healthy', 'service_completed_successfully'
You should see
service "web" depends on undefined service "gatway": invalid compose project

Both stop at config, before anything is started. That is why you run it first.

6 · Check yourself 5 min

  1. What is the difference between service_started, service_healthy and service_completed_successfully?
  2. Why is the ingest a separate service and not part of the AI service?
  3. What does start-period in a health check do?
Answers
  1. Started: the container is running. Healthy: its health check passes. Completed successfully: it ran and exited with code 0.
  2. It runs once and stops, while the AI service runs for ever and may restart. Filling the table on every restart would be slow and wrong.
  3. Failures during that time do not count, so a service that needs a long time to start is not marked unhealthy.
