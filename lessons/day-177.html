DAY 177 · AFTER THE COURSE

After the course: your first three months

60 minhands-onfree
Today you will be able to plan your next three months with a rhythm you can keep, count what you never ran, and say when something counts as run.

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Why do you back every skill on your list with evidence?
  2. What is the one list in the README that makes the others believable?
Answers
  1. A level without evidence is a feeling: a file, a command or a number turns it into a claim.
  2. “What has not been run”: it says honestly where the real and the not-real meet.

2 · Hook 2 min

The workshop is over, the weekly plan has stopped, and nobody is waiting for your Sunday review. In ninety days, what will have happened to your project and your applications?

Guess first, then open

Without a plan, usually nothing: the project stays as it was on the last day, and the applications stop. With a small rhythm that you can keep when life is busy, ninety days is enough to run the things you never ran, and to answer a few dozen postings. Today you write that rhythm down.

3 · The idea, in three small pieces 8 min

Piece 1: a rhythm small enough to keep

The plan carried you for 25 weeks because someone decided each day for you. Now you decide. Keep it small: a few fixed slots a week (an application, a message to a person, an hour on the project) and one review a month. When a week goes wrong, shrink the plan to the smallest piece, do not drop it.

Piece 2: the not-run list is your backlog

Your README has a section “what has not been run”. It is also the most honest to-do list you own. Each month, take one item, run it for real, save the output, and move the line out of the list. A small counter shows the progress: four things never run, then three, then two. An item counts as run only by a clear rule, so that you cannot fool yourself.

Piece 3: apply before it is perfect, and keep the evidence fresh

A project that a stranger can run from a README, with an honest list of what is real, is ready to show now. Do not wait for the Docker run or one more feature: those are the next months’ work. And a project ages: once a month, re-run your checks and re-read your CV against your README, so that every claim stays true.

If you know another typed language (C# as the example): the not-run list is the technical debt register of the whole project, and the monthly review is the sprint retrospective you run alone. The counter is a burn-down chart with four items.
Capstone: the project is done for the course and open for the rest of your career: every item you run makes it more real.

4 · Worked example 5 min

Read it first. What was run: a tiny counter script on the capstone README, below. Everything else is a template: the plan, the rhythm and the examples are a guide, and nothing is claimed about jobs or results. The counter reads the section “What has not been run” (scripts/not_run.py):

"""Count the things the README says have NOT been run. The number should shrink: every item you run for real moves out of the list, with its output saved.
Usage: python scripts/not_run.py [README.md]     Exit code 0, or 1 when the README has no such section: a counter, not a gate."""
import re
import sys
from pathlib import Path

text = Path(sys.argv[1] if len(sys.argv) > 1 else "README.md").read_text(encoding="utf-8")
section = re.search(r"^## What has not been run\s*\n(.*?)(?=^## |\Z)", text, re.S | re.M)
if section is None:
    sys.exit("README.md has no section called 'What has not been run': add one, and be honest in it")
items = [line[2:].strip() for line in section.group(1).splitlines() if line.startswith("- ")]
print(f"{len(items)} thing(s) never run:")
for number, item in enumerate(items, start=1):
    print(f"  {number}. {item}")

The rule that decides when a line may move out of the list:

WHEN DOES AN ITEM COUNT AS "RUN"? (a rule, so that you cannot fool yourself)
1. you ran the real thing, on a real machine, from a clean start
2. you saved the command and its real output (a file in docs/, or pasted into the README)
3. you wrote down what surprised you or broke, and fixed it
4. only then you move the line out of "What has not been run", in the same commit as the evidence

An example plan for three months. Write your own, with your own goal and your own list:

MY NEXT THREE MONTHS (an example: write your own)
goal (one sentence you can check):    a stranger can run my project with ONE command, and the README says nothing false
every week:    3 to 5 applications (45 minutes each, in the log)    +    one person I write to about their work    +    one hour on the project
every month:   run ONE item from "what I never ran", and save the output
month 1 (April):   docker compose up --build on a machine with Docker; fix what breaks; paste the output       -> not-run count 4 to 3
month 2 (May):     push to GitHub and read the real run of the workflow; fix what is red; add the badge        -> 3 to 2
month 3 (June):    one real step toward users: ten people try it, or a real login; write what they did          -> and one more item run
first Sunday of each month:  the log, the project, the not-run list; change ONE thing
if I have not done this for two weeks: shrink it (one application and one hour), do not drop it

The weekly rhythm that fits inside a busy week, and when to apply instead of polishing:

THE WEEKLY RHYTHM (small enough to keep when life gets busy)
Mon   one application (45 min)
Tue   one message to a person about their work (15 min)
Wed   one hour on the project: the next item of the month
Thu   one application
Fri   write what happened in the log: sent, answered, what I learned (15 min)
Sun   look at the week: what to change, ONE thing
WHEN TO STOP POLISHING AND APPLY
the project runs from the README (a stranger tested it)          -> apply now, do not wait for the Docker run
the README says what is real and what is not                       -> apply now
you want to add a feature "to be ready"                            -> it is a ticket, not a blocker; apply, then build it
you got a reply with a question you cannot answer                  -> that question is your next week's work
KEEP YOUR EVIDENCE FRESH (every month, 20 minutes)
- re-run the preflight (bash scripts/preflight.sh): does everything still pass? (a library updates, a model changes)
- update the numbers you quote (tests, golden questions): are they still true?
- add one line to the README: what you ran this month, and the output
- re-read your CV and LinkedIn text against the README: every claim still showable?

5 · Try it 30 min

Work on paper or in a file in your repository (docs/next-three-months.md).

Step 1 Copy and run

Add scripts/not_run.py to your repository and run it. Does your README have the section? If not, write it now: every thing you set up but never ran (an image, a pipeline, a model, a second machine). How many items do you have?

Step 2 Change one thing

Predict: which one item will you run first, and what do you think will break? Write the guess down, then use it in a month to see how right you were.

Step 3 Break it on purpose

Try to fool yourself: pick an item and write the cheapest thing that would let you move it out of the list without really running it. Then read the rule above. Which of its four points does your shortcut skip?

Step 4 Your turn

Write your three months: one goal you can check, the weekly slots with times in your calendar, the item for each month, and the date of your first monthly review (the first Sunday of next month). Put the review in your calendar now. Commit: git add docs/next-three-months.md scripts/not_run.py and git commit -m "Plan the next three months".

6 · Stuck? anytime

  • The plan feels too big: halve it. One application, one message and one hour is a plan. A plan you keep beats a plan you admire.
  • You cannot run Docker yet: that is fine, and honest. Put it in the list, and pick an item you can run (the pipeline on GitHub, the local model, a trial with five people).
  • No replies to applications: look at the log, change one thing (the first sentence, the project you lead with), and keep the count going. Replies lag by weeks.
  • You feel you are not ready: apply for a few that are a stretch and a few that fit. The reply tells you more than your doubt does.
Hint: Step 3

The usual shortcut is “it should work”, or “I ran a similar thing”. Neither is the real thing on a clean machine with the output saved.

Solution: Step 3

The shortcut skips point 1 (the real thing, from a clean start) and point 2 (the saved output). That is why the rule has four points: a line moves out of the list only together with its evidence, in the same commit.

7 · Check yourself 5 min

  1. What does it mean that an item counts as “run”?
  2. Why do you apply before the not-run list is empty?
  3. What do you do when a week goes wrong?
Answers
  1. You ran the real thing on a real machine from a clean start, saved the command and its output, wrote down what broke, and moved the line out of the list in the same commit as the evidence.
  2. The project is ready to show when a stranger can run it from the README and the README is honest; the list is next month’s work, not a blocker.
  3. Shrink the plan to its smallest piece (one application and one hour) and keep going. Do not drop it.
