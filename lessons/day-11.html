2 · Hook 2 min

A client sends {"top_k": 99, "language": "fr"} with no question at all. How many things are wrong, and how many does your API tell the client about?

Guess first, then open

Three things are wrong: no question, top_k too big, a language you do not support. A good API reports all three at once, so the client fixes everything in one go. Today you let Pydantic do that, and you teach it one rule of your own.

3 · The idea, in three small pieces 8 min

Piece 1: the request model is the rulebook at the door

Each field in ChatRequest can carry rules: min_length and max_length for text, ge and le for numbers (“greater or equal”, “less or equal”), and Literal["en", "th"] for a short list of allowed values. A field with a default (top_k=3) is optional. A field without one is required.

Piece 2: write your own rule with a validator

Some rules do not fit in a number. “Not only spaces” is one. A @field_validator is a small function that receives the value, can clean it (strip()) and can reject it by raising ValueError. FastAPI turns that into a 422 for you.

Piece 3: the response model is the rulebook at the exit

response_model=ChatResponse says: “send back only these fields, in this shape”. If your function returns extra things (a debug note, an internal id, a secret), they are dropped before the client sees them. Think of it as a filter on the way out.

Part of a 422 errorWhat it tells you
locWhere: ["body", "top_k"] means the field top_k in the request body
msgWhat went wrong, in words
typeThe kind of problem: missing, less_than_equal, literal_error, int_parsing, value_error
inputThe value the client sent (when there is one)
If you know another typed language (C# as the example): the request model is a DTO with data annotations ([Range(1, 10)], [StringLength]), a validator is like IValidatableObject or a FluentValidation rule, and response_model is returning a response DTO instead of the database entity. In Java it is Bean Validation (@Min, @Size). One difference: in FastAPI the rules and the type live in the same place, and the /docs page shows them.
Capstone: the assistant will receive questions from real people. Strict request rules protect your model budget (no 50,000-word questions), and a strict response model protects your data (no internal fields leaking). Both are cheap to add now and painful to add later.

4 · Worked example 3 min

Read it first. Same app as Day 9, with richer models. Replace src/my_ai_project/api.py with this.

from typing import Any, Literal

from fastapi import FastAPI
from pydantic import BaseModel, Field, field_validator

app = FastAPI(title="my-ai-project")


class ChatRequest(BaseModel):
    question: str = Field(min_length=1, max_length=2000)
    top_k: int = Field(default=3, ge=1, le=10)
    language: Literal["en", "th"] = "en"

    @field_validator("question")
    @classmethod
    def not_blank(cls, value: str) -> str:
        value = value.strip()
        if not value:
            raise ValueError("question must not be blank")
        return value


class Source(BaseModel):
    doc_id: str
    title: str


class ChatResponse(BaseModel):
    answer: str
    sources: list[Source]


@app.get("/health")
def health() -> dict[str, str]:
    return {"status": "ok", "version": "0.1.0"}


@app.post("/api/chat", response_model=ChatResponse)
def chat(request: ChatRequest) -> dict[str, Any]:
    return {
        "answer": f"(fake) You asked: {request.question}",
        "sources": [{"doc_id": "1", "title": "Error codes"}],
        "internal_note": "never send this to a client",
    }

Start the server (uv run uvicorn my_ai_project.api:app --reload) and send a good question:

curl -i -X POST http://127.0.0.1:8000/api/chat -H "Content-Type: application/json" -d '{"question": "What is E101?"}'
You should see
HTTP/1.1 200 OK
content-type: application/json

{"answer":"(fake) You asked: What is E101?","sources":[{"doc_id":"1","title":"Error codes"}]}

Look at the answer: the function returned internal_note, but the client never sees it. The response model removed it. Now a blank question:

curl -i -X POST http://127.0.0.1:8000/api/chat -H "Content-Type: application/json" -d '{"question": "   "}'
You should see
HTTP/1.1 422 Unprocessable Entity

{"detail":[{"type":"value_error","loc":["body","question"],"msg":"Value error, question must not be blank","input":"   ", ...}]}

The -i flag shows the status line. The function chat returns a plain dictionary, and response_model checks and filters it. The -> dict[str, Any] keeps mypy happy.

Count the errors: there are three, one for each field. Read each loc and msg aloud. Then break it a second way: in api.py, delete , response_model=ChatResponse from the @app.post line, save, and send the good question again. What do you see? The internal_note leaks. Put the line back.

Two changes, no step-by-step:

  2. Add used_top_k (an integer) to ChatResponse, and return the top_k the request used.

Test it three times: with a tag ("tag": "errors"), without a tag, and with "tag": 123. The first two should give 200. The third should give 422, and you should be able to say why before you look at the message.

6 · Stuck? anytime

  • You sent a bad request but got 200: check that the rule is on the field in ChatRequest, and that you restarted the server (or used --reload).
  • The validator never runs: put @field_validator("question") above @classmethod, and make sure the name in the quotes is the name of the field.
  • “JSON decode error”: the body is not valid JSON. JSON needs double quotes around names and text, and no trailing comma. In a terminal, wrap the whole body in single quotes.
  • Your tag test gives 422 even without a tag: the field needs a default. Write tag: str | None = None, with the = None.
  • mypy says the return type is wrong: when you use response_model, annotate the function as -> dict[str, Any], and import Any from typing.
Hint for Step 4

The request field looks like the others, but with | None and a default of None. For the response, add the field to the model and add the key to the dictionary your function returns. The model alone is not enough: a required field that is missing from the dictionary gives a 500.

Solution for Step 4

In ChatRequest, add one line:

    tag: str | None = None

Then change the response model and the returned dictionary:

class ChatResponse(BaseModel):
    answer: str
    used_top_k: int
    sources: list[Source]
    return {
        "answer": f"(fake) You asked: {request.question}",
        "used_top_k": request.top_k,
        "sources": [{"doc_id": "1", "title": "Error codes"}],
        "internal_note": "never send this to a client",
    }

With "tag": 123 you get a 422 with "type":"string_type" and "msg":"Input should be a valid string", because Pydantic does not turn a number into text.

7 · Check yourself 5 min

  1. A client sends three bad fields in one request. How many errors come back, and which part of an error tells you which field it is?
  2. What is the difference between a 422 that comes from Field(le=10) and one that comes from a @field_validator?
  3. Why is it safer to return a plain dictionary through response_model than to send the dictionary as it is?
Answers
  1. Three errors, all in one 422. The loc list tells you the field, for example ["body", "top_k"].
  2. For the client there is no difference: both are a 422 with loc and msg. The first uses a built-in rule (the type is less_than_equal), the second uses a rule you wrote (the type is value_error).
  3. The response model keeps only the fields it lists. Extra fields, such as an internal note, are dropped, so a mistake in your function cannot leak them.
