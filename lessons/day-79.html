DAY 79 · LEVEL 6: RAG

Permission-aware retrieval and production RAG

60-70 minhands-onfree

1 · Warm-up 3 min

Answer from memory, then open the answers.

  1. Name three of the four reasons your pipeline turns an answer into a refusal.
  2. What does a citation prove, and what does it not prove?
Answers
  1. The best similarity is under the minimum; the writer finds no answer; the answer cites a source that was not retrieved; the answer cites no source.
  2. It proves the source exists and was retrieved. It does not prove that the source answers the question (the price question cited the warranty page).

2 · Hook 2 min

Your knowledge base has error pages with internal service notes. A customer types a question about an error. Your assistant answers from the service notes. How do you stop it, and where in the code?

Guess first, then open

Not with a sentence in the prompt (“do not tell customers”). A prompt is a request, and a model can be asked in clever ways to ignore it. The only safe place is before the model: the customer’s search must never return the staff pages. A model cannot leak what it never received.

3 · The idea, in three small pieces 8 min

Piece 1: write down who may see what

Start with a table, on paper, before any code. Who are the roles (customer, staff), and which pages may each one read? For your knowledge base the rule is simple: manuals and FAQs are for everyone; error pages hold service notes, so they are for staff. The table becomes one small dictionary in code.

Piece 2: filter in the query, everywhere you search

The filter goes into the SQL WHERE clause, so a forbidden row is never ranked, never returned and never sent to a model. Every other way of finding pages must obey the same rule: the keyword index of Day 74, and any cache you add later (a cached answer for staff must not be served to a customer: cache by question and role). Filtering after the answer is written is too late: the text is already in the model’s head.

Piece 3: fail closed, and take the role from a login

An unknown role must give an error, never “everything”. No role at all means the least powerful one. And the role must come from something the caller cannot choose: a login. Today a header stands in for it, only so you can try both roles; in Module 8 you replace it with real authentication. Notice also what the customer sees: “not found”, not “forbidden”. Saying “this exists but you may not read it” would already leak something.

If you know another typed language (C# as the example): this is row-level security done in the query, like a global query filter in EF Core (HasQueryFilter) that every query gets automatically. The lesson is the same: put the rule in the data access, not in each caller. And a header you read yourself is like trusting a cookie value: fine for a demo, never for production.
Capstone: the real ai-knowledge-assistant will have users, and Module 8 adds the login. Today you build the part that the login will plug into.

4 · Production RAG: the overview 5 min

This is a map, not a task. Five things separate a demo from a service. You do the first today, and the others when you need them:

concern                what goes wrong without it                 the idea in one line
permissions            a customer reads staff-only notes          filter by role inside the query, before ranking
incremental indexing   one changed page means a full re-embed     store a hash of each page, re-embed only what changed
tenant isolation       company A sees company B's pages           the same filter, with a tenant id on every row
retrieval caching      the same question is embedded again        cache by question and role, never by question alone
evaluation and logs    you cannot tell if a change made it worse  a fixed set of questions, and a log of what was retrieved

You will not build all of them in this course. What matters is that you know they exist, and that the first one (permissions) is the one you cannot add late: every route, index and cache must already pass the role down.

5 · Worked example 5 min

Read it first. The policy, in src/my_ai_project/access.py:

from typing import Literal

Role = Literal["customer", "staff"]

# Who may read which kind of page. Error pages hold service notes, so only staff may see them.
ALLOWED_KINDS: dict[str, tuple[str, ...]] = {
    "customer": ("manual", "faq"),
    "staff": ("manual", "faq", "error"),
}


def allowed_kinds(role: str) -> tuple[str, ...]:
    """The kinds of page a role may see. An unknown role is an error, never 'everything': fail closed."""
    try:
        return ALLOWED_KINDS[role]
    except KeyError:
        raise ValueError(f"unknown role {role!r}: use one of {', '.join(ALLOWED_KINDS)}") from None

The store search takes allowed_kinds and puts it in the SQL (in store.py; the kind filter of Day 67 still works):

    def search(self, query_vector: np.ndarray, top_k: int = 3, kind: str | None = None, allowed_kinds: Sequence[str] | None = None) -> list[Found]:
        if kind is not None and kind not in KINDS:
            raise ValueError(f"unknown kind {kind!r}: use one of {', '.join(KINDS)}")
        # The permission filter is part of the SQL: rows a user may not see are never ranked, never returned, never sent to a model.
        conditions: list[sql.Composable] = []
        filters: list[object] = []
        if kind is not None:
            conditions.append(sql.SQL("kind = %s"))
            filters.append(kind)
        if allowed_kinds is not None:
            conditions.append(sql.SQL("kind = ANY(%s)"))
            filters.append(list(allowed_kinds))
        where = sql.SQL("WHERE ") + sql.SQL(" AND ").join(conditions) + sql.SQL(" ") if conditions else sql.SQL("")
        query = sql.SQL(
            "SELECT doc_id, chunk_index, title, kind, text, 1 - (embedding <=> %s) AS similarity FROM {table} "
        ).format(table=self.table) + where + sql.SQL("ORDER BY embedding <=> %s LIMIT %s")
        params: tuple[object, ...] = (query_vector, *filters, query_vector, top_k)
        with self.connect() as conn:
            rows = conn.execute(query, params).fetchall()
        return [Found(d, i, t, k, x, round(float(s), 2)) for d, i, t, k, x, s in rows]

The role comes from a dependency (demo only), in deps.py:

def get_role(x_demo_role: Annotated[str, Header()] = "customer") -> str:
    """DEMO ONLY: the role comes from a header so that you can try both. A real service reads it from a login (Module 8),
    because a caller could write any header. With no header, the least powerful role is used."""
    if x_demo_role not in ALLOWED_KINDS:
        raise HTTPException(status_code=422, detail=f"unknown role {x_demo_role!r}: use one of {', '.join(ALLOWED_KINDS)}")
    return x_demo_role


RoleDep = Annotated[str, Depends(get_role)]

The routes use it:

# api.py: every route that reads the knowledge base takes the role, and passes the allowed kinds down
@app.post("/api/ask")
def ask(request: AskRequest, embedder: EmbedderDep, store: StoreDep, keywords: KeywordsDep, writer: WriterDep, role: RoleDep) -> AskResponse:
    result = answer_question(..., allowed_kinds=allowed_kinds(role))

# /api/search gets the same: retrieve(q, embedder, store, top_k=top_k, kind=kind, allowed_kinds=allowed_kinds(role))

A script that asks the same questions as both roles. permissions_demo.py:

import os

from my_ai_project.access import allowed_kinds
from my_ai_project.embedder import FastEmbedder
from my_ai_project.hybrid import KeywordIndex
from my_ai_project.rag import answer_question
from my_ai_project.simulated import SimulatedWriter
from my_ai_project.store import ChunkStore

store = ChunkStore(os.environ.get("DATABASE_URL", "postgresql://assistant:assistant@localhost:5433/assistant"))
embedder = FastEmbedder()
keywords = KeywordIndex(store.all_chunks())
writer = SimulatedWriter()   # NOT a real model

for question in ["What does error E104 mean?", "How often should I calibrate the sensor?"]:
    print(question)
    for role in ("customer", "staff"):
        result = answer_question(question, embedder, store, keywords, writer, allowed_kinds=allowed_kinds(role))
        sources = ", ".join(s.citation for s in result.sources) or "no source"
        print(f"  {role:<9}{result.text}  sources: {sources}")

7 · Stuck? anytime

  • mypy: the fake store does not match Searcher: add allowed_kinds: Sequence[str] | None = None to its search and filter by it.
  • A customer still sees an error page: one path ignores the role. Search for every call of search and check that each passes allowed_kinds.
  • Every question is refused for a customer: check the kinds in your policy. Kinds are lower case: manual, faq, error.
  • A 422 on every request: the header must be named x-demo-role and hold customer or staff.

Solution: Step 3

At least the tests of the keyword index and of the hybrid search fail: they ask for a customer and find an error page. Without the check in the keyword index, the exact word E104 would bring the staff page back to a customer through the keyword list, even though the SQL filter was right. Two search paths mean two places to enforce the rule.

Solution: Step 4 (the tenant)

On every row of chunks (a tenant_id column), in the same WHERE clause, in the keyword index, and in the cache key. It is the same filter as the role, with a different column.

8 · Check yourself 5 min

  1. Why is a prompt rule not enough to keep staff pages from customers?
  2. Why must the keyword index get the same filter?
  3. Why does a customer see “not found” and not “forbidden”?
Answers
  1. A prompt is a request, not a lock; the model has already received the text. The safe place is before the model: the search must not return the page.
  2. It is a second way to find pages. If only the SQL is filtered, an exact word can bring a forbidden page back through the keyword list.
  3. “Forbidden” would tell the user that the page exists. Refusing in the same way as for a missing page leaks nothing.
