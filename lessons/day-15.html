1 · Self-test 20 min

Close your notes. Answer each question in your own words, and write a confidence number next to it: 1 = guessing, 2 = fairly sure, 3 = certain. Then open the answers and mark each one right, partly right or wrong.

  1. Your test calls summarize() with a fake client. What does this give you that a real model would not? (Day 5)
  2. What is the difference between git add and git commit, and what does git push -u origin main do the first time? (Day 6, Day 14)
  3. A browser visit to /api/chat shows 405, a visit to /nope shows 404. What does each one mean? (Day 9)
  4. A client sends {"top_k": 99, "language": "fr"} with no question. How many errors come back, and which part of an error says where? (Day 11)
  5. What does response_model do, and why does it matter for secrets? (Day 11)
  6. Your route got blank text and the client saw a 500. Whose fault is a 500, and how did you turn it into a 400? (Day 12)
  7. The model replies not json to /api/extract. Which status should the client get, and why not 500? (Day 14)
  8. What three things make a project “done” for a stranger? (Day 14)
Answers
  1. Speed, no cost, and the same answer every time. A failing test then means your code is wrong, not that the model had a bad day.
  2. add puts changes in the box (staging), commit seals the box as a save point. The first git push -u origin main sends your commits to GitHub and remembers that main follows origin/main, so a plain git push works afterwards.
  3. 405: the address exists, but not for this kind of request (a browser visit is a GET, the route is POST). 404: there is no such address.
  4. Three errors in one 422: a missing question, top_k too big, a language that is not allowed. The loc list says where, for example ["body", "top_k"].
  5. It keeps only the fields of the model and drops the rest, so an extra field (an internal note, a secret) cannot leave your API by mistake.
  6. A 500 is your code failing in a way you did not plan for. You caught the ValueError in the route and raised an HTTPException with status 400.
  7. 502 Bad Gateway: the thing you called gave a bad answer. 500 would say your own code is broken, which is not true.
  8. Tests that pass, a README that explains how to run it, and the code on GitHub.

Read your numbers. If you were sure (3) and wrong, that is the most valuable thing you found this week. Circle those.

5 · Plan the M2 checkpoint and week 3 20 min

Next Saturday is the M2 checkpoint: your /api/chat calls a real model, the key is stored in an environment variable, and every call is logged. Two things must be ready before then.

  1. Choose a model provider and create an API key. Pick one you can afford, and set a spending limit if the provider allows it. It is a secret, like a password.
  2. Keep the key out of Git. Add .env to your .gitignore now, so you cannot commit it by mistake:
.env
.venv/

Never paste the key in code, in a README, in a chat or in a screenshot. If it ever lands in Git, treat the key as lost: delete it at the provider and make a new one.

Now write the plan for week 3 in your README or notebook, and put the sessions in your calendar with real times:

Week 3 outcome (one sentence): ...
Mon: Lesson 1   Tue: class   Wed: Lesson 2   Thu: mixed practice
Fri: teach-back   Sat: Project Lab (real LLM call)   Sun: review
Before Saturday: choose a model provider and create an API key.
If time runs out I drop first: Thu mixed practice, then Fri.

Suggested outcome for week 3: by Sunday my endpoints get their model from one place, I can load a CSV with pandas, and my project calls a real model with the key kept out of Git. Make it your own, in one sentence.

Tuesday is a class day, so there is no new lesson. Use the 45 minutes for your two questions before the class and a 5-line brain dump after it.
