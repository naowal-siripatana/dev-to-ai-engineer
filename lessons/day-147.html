2 · The goal 5 min

Done looks like: from a clean checkout, a person copies .env.example to .env, runs docker compose up -d --build, opens http://localhost:8080, asks a question in the page, and gets an answer with sources. Only one port is open to the outside. The password is in no committed file. The README says how to start it, what you ran and what you did not.

Be clear about what was run. The Docker engine on the author’s laptop did not respond, and the disk was too full to pull images. So no image was built, no container was started, and the page was never opened through Compose. What was checked for real: the whole Compose file with docker compose config (the Docker command-line tool reads and resolves it without an engine); each Dockerfile step for the gateway and the page by hand outside Docker; and the gateway taking its Python address from the environment. The nginx file could not be tested at all (no nginx on that machine). This lab is therefore a recipe that is checked as far as it can be, and your run is the first real one. If it fails, the log is the lesson: read it, fix it, and tell us what you found.

3 · Plan the work 10 min

Draw the four boxes and the arrows before you write a file. Browser to web (nginx, port 80), web to gateway (8080), gateway to ai (8000), ai to db (5432). Which arrow crosses to the outside? Only the first. Then the start order: the database first, then the ingest (once), then the AI service, then the gateway, then the page.

4 · Build 90 min

Job 1: the gateway image

The same two-stage idea as Day 142: the .NET SDK builds, a smaller ASP.NET runtime image runs. Restore comes first, so the packages are cached until the project file changes. gateway/Dockerfile:

# syntax=docker/dockerfile:1
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
# restore first: this layer is cached until the .csproj changes
COPY AskGateway/AskGateway.csproj AskGateway/
RUN dotnet restore AskGateway/AskGateway.csproj
COPY AskGateway/ AskGateway/
RUN dotnet publish AskGateway/AskGateway.csproj -c Release -o /out --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /out .
# the address of the Python service comes from the environment (PythonService__BaseUrl), set by Compose: no address is written in the image
ENV ASPNETCORE_URLS=http://+:8080
USER $APP_UID
EXPOSE 8080
ENTRYPOINT ["dotnet", "AskGateway.dll"]

Two things to notice. The Python address is not in the image: the code reads the setting PythonService:BaseUrl, and the environment variable PythonService__BaseUrl overrides it (double underscore for the colon). And the runtime image has no curl, so this service has no health check of its own; the page starts when the gateway has started. gateway/.dockerignore:

**/bin
**/obj
.git
AskGateway.Tests

Run for real, outside Docker, the same steps the Dockerfile runs, and then the published program with settings from the environment:

Job 2: the page image

Node builds the static files, nginx serves them. web/chat-ui/Dockerfile:

# syntax=docker/dockerfile:1
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

The nginx file does two things: it serves the page (any unknown path falls back to index.html), and it forwards /api/ to the gateway, so the browser only ever talks to one address. It also gives the request an id at the edge ($request_id in the X-Request-Id header), the id that Day 128 followed through the logs. web/chat-ui/nginx.conf:

server {
    listen 80;
    root /usr/share/nginx/html;

    # the page: any unknown path falls back to index.html (the page has its own #/ routes)
    location / {
        try_files $uri /index.html;
    }

    # the API: the browser only talks to this address; nginx forwards to the gateway and gives the request an id at the edge
    location /api/ {
        proxy_pass http://gateway:8080;
        proxy_set_header X-Request-Id $request_id;
        proxy_set_header Host $host;
    }
}

Not tested: this file was not run, because there was no nginx to run it. Read it carefully, and if the page loads but the question gets a 404 or 502, this is the first place to look. web/chat-ui/.dockerignore:

.git

Job 3: the Compose file

Five services: the database, the one-off ingest, the AI service, the gateway and the page. The ingest and the AI service share one image and one block of settings (a YAML anchor, &ai and <<: *ai), so they cannot drift apart. compose.yaml:

name: pumpguard

x-ai: &ai   # the same image for the service and for the one-off ingest job
  build: ./python-service
  image: pumpguard-ai
  environment:
    DATABASE_URL: postgresql://${POSTGRES_USER:-assistant}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB:-assistant}
    LLM_MODE: ${LLM_MODE:-fake}
    ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY:-}

services:
  db:
    image: pgvector/pgvector:pg17
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-assistant}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in the file .env}
      POSTGRES_DB: ${POSTGRES_DB:-assistant}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./python-service/db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 3s
      timeout: 3s
      retries: 15
    # no 'ports': nothing outside needs the database

  ingest:   # runs once, fills the table, and stops
    <<: *ai
    command: ["python", "ingest.py"]
    restart: "no"
    depends_on:
      db:
        condition: service_healthy

  ai:
    <<: *ai
    volumes:
      - auditlogs:/data
    depends_on:
      ingest:
        condition: service_completed_successfully
    restart: unless-stopped
    # the health check is in the image (HEALTHCHECK in the Dockerfile)

  gateway:
    build: ./gateway
    environment:
      PythonService__BaseUrl: http://ai:8000
    depends_on:
      ai:
        condition: service_healthy
    restart: unless-stopped

  web:
    build: ./web/chat-ui
    ports:
      - "8080:80"   # the only door to the outside
    depends_on:
      - gateway
    restart: unless-stopped

volumes:
  pgdata:
  auditlogs:

Resolved by the real docker compose config (the engine was not needed). The list of services, and the only published port:

6 · Stuck? anytime

  • The page loads but a question gets a 502: the gateway cannot reach the AI service, or nginx cannot reach the gateway. docker compose logs gateway names the address it tried.
  • The page loads but a question gets a 404: check the location /api/ block and the trailing slash of proxy_pass in nginx.conf: a slash after the host changes how the path is forwarded.
  • ai never becomes healthy: docker compose logs ai. A model that has to download, or a database address with the wrong password, shows there. The health check has a 30 second start period.
  • ingest exits with an error: the AI service will not start (that is the condition working). Read its log: usually the database address or password.
  • You changed .env and nothing changed: run docker compose up -d again so the containers are recreated; a database password is set only when the volume is created (use down -v for a clean start).
  • The build is slow every time: look at the order of the COPY lines and at the .dockerignore: if node_modules or .git are copied into the build, every build is slow.
Hint: a 502 through the page

Go one hop at a time. From the host you cannot reach the gateway (no published port), so use docker compose exec web wget -qO- http://gateway:8080/ to test the hop from the page container, then the same from the gateway to http://ai:8000/health. Each failed hop tells you which service to read the log of.

8 · Check yourself 5 min

  2. Why is the Python address an environment variable in the gateway?

Answers
  1. Everything else is reached by name on the private network. Fewer open doors means fewer ways in. The database and the AI service need no one outside.
