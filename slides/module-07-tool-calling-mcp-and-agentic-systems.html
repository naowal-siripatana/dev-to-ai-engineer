Core Concepts

The ideas worth actually understanding

Tool / function calling

The model asks your code to run a function (e.g. 'look up error code E204') and use the result — this is what turns a Q&A bot into something that can act.

MCP

A standard protocol for exposing tools/data to an LLM client — think of it like a well-defined API contract, but for AI clients instead of REST clients.

Agent loop

Plan → act (call a tool) → observe result → decide next step → repeat until done. It's a loop with a stopping condition, not magic.

Single vs. multi-agent

More agents is not automatically better — it's a trade-off between capability and debuggability/cost. Default to the simplest architecture that works.

From .NET To This

Bridging from what you already know

A tool-calling agent loop is structurally similar to a state machine or workflow engine you'd design in .NET (think: an orchestrator calling downstream services based on state) — the LLM is just the component deciding which state to go to next, non-deterministically.
Hands-On Checkpoint

What "done" looks like for this module

Give your assistant one real tool (e.g. 'query the mock incident database by error code') via function calling. Optionally, expose it as a minimal MCP server. Keep it to a single tool and a simple loop — no multi-agent orchestration yet.

Watch Out

Pitfalls & anti-patterns

  • Don't design a multi-agent system before a single agent with one tool is reliable — complexity here compounds fast.
  • Don't give a tool more permission than the task needs — this is the seed of Module 11's security discussion.
Key Takeaways

Before you move on

  • Tool calling is what turns retrieval into action.
  • MCP is a contract, not a framework — evaluate it as you would any API standard.
  • Default to single-agent, single-tool; earn the right to add complexity.
