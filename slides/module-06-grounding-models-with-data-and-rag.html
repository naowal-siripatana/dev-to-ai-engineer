Core Concepts

The ideas worth actually understanding

Chunking strategy

How you split documents (by size, by section, by semantic boundary) directly determines retrieval quality — the single highest-leverage decision in a RAG system.

pgvector

Vector search living inside PostgreSQL — you get semantic search without standing up a separate vector database, which matters for a solo/portfolio project's operational simplicity.

Hybrid search & reranking

Combine keyword and semantic search, then reorder results by actual relevance — the difference between a demo RAG and one that survives real questions.

Citation / grounding

Making the model point to which chunk supports each claim — this is what makes an answer trustworthy instead of just plausible.

From Backend Experience

Bridging from what you already know

pgvector means this whole module plugs into a database most backend developers already know — you add a new query capability (semantic similarity) to a tool you already know how to run, back up and reason about, instead of adopting unfamiliar infrastructure.

Watch Out

Pitfalls & anti-patterns

  • Don't reach for GraphRAG or fancy reranking before a simple top-k retrieval even works end-to-end.
  • Don't use real company data, even 'just to test' — mock data only.
Key Takeaways

Before you move on

  • Chunking strategy is the highest-leverage lever in a RAG system — spend your tuning time there first.
  • pgvector lets you skip standing up separate vector-DB infrastructure.
  • An answer without a citation is a guess with good grammar — always surface the source.
