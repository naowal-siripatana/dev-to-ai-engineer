Errors and Logging

Fail loudly, and leave a trail
Goal today: make a failed lookup leave a clear log line instead of silence.
Hook

Your AI call fails at 2 a.m.

Silence

You find nothing. You do not even know something broke.

A clear message

You find what failed, where, and why. You fix it in five minutes.

Errors

Raise a clear error, catch a specific one

class DocumentNotFoundError(Exception):
    """Raised when a document id is not in the store."""

def get_document(doc_id: str) -> str:
    if doc_id not in STORE:
        raise DocumentNotFoundError(f"no document with id {doc_id!r}")
    return STORE[doc_id]
The name says what happened. Catch DocumentNotFoundError, not everything.
Logging

Levels are volume knobs for your program's diary

DEBUG

Detail for you while building.

INFO

Normal events, like "found document 1".

WARNING

Something odd, but we recovered.

ERROR

Something failed.

print is for the user. logging is for you. Set the level once with logging.basicConfig(level=...).
Watch Out

Never swallow an error

  • except Exception: pass is like taking the battery out of a smoke alarm.
  • The real problem disappears and shows up later, in another line, with a confusing message (we will cause an UnboundLocalError on purpose).
  • Handle it (safe answer plus a log line), or let it travel up. Use logger.exception to keep the traceback.
From Another Language

Bridge

raise / except

C# throw and try / catch. Java is similar, but it has checked exceptions.

Levels

Same ideas as C# ILogger: LogDebug, LogInformation, LogWarning, LogError.

No checked exceptions

Nothing forces you to catch in Python. You have to choose to.

Specific is better

Catch the error you expect, like ValueError, not Exception.

Capstone Tie-In

Where this goes

Model calls will time out and hit rate limits. The service has to fail clearly, say what went wrong, and leave a log line for every call. FastAPI will use this habit for error responses.
