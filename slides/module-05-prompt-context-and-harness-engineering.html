Core Concepts

The ideas worth actually understanding

Context engineering vs. prompt engineering

Prompting is what you say to the model; context engineering is deciding what information (history, retrieved docs, tool results) even makes it into the prompt. The second one is where production systems actually live or die.

Context rot

Stuffing too much irrelevant history/context into the window degrades answer quality even when it technically 'fits' — directly relevant once you add RAG retrieval and conversation history.

Few-shot / structured prompting

Showing the model 2-3 examples of the exact output shape you want, instead of describing it — often more reliable than a longer instruction.

Harness engineering

The surrounding system (what tools are offered, what gets retried, what gets shown to the model) matters as much as the prompt text itself.

Watch Out

Pitfalls & anti-patterns

  • Don't just make the prompt longer when something goes wrong — check whether irrelevant context is crowding out the useful part first.
  • Don't hand-tune forever; once you have Module 8's eval set, let measurements (not vibes) drive prompt changes.
Key Takeaways

Before you move on

  • Context engineering (what you include) usually matters more than prompt wording (how you phrase it).
  • Context rot is real — more retrieved content is not automatically better.
  • A good failure-mode instruction ('say you don't know') is cheap insurance for a support tool.
