Core Concepts

The ideas worth actually understanding

Structured output / JSON Schema

Forcing the model to return data your Pydantic models can parse — this is what turns 'a chatbot' into 'an API you can build on'.

Streaming

Same idea as an HTTP chunked response or a SignalR stream — send tokens to the client as they're generated instead of waiting for the full answer.

Retry / timeout / rate limiting

The exact reliability patterns you'd apply to any flaky third-party API in a .NET service — just now the third party is an LLM provider.

Model routing

Sending cheap/simple requests to a small model and hard ones to a bigger model — a cost-control pattern, not an accuracy one.

From .NET To This

Bridging from what you already know

Everything here maps to patterns you already use for calling any unreliable external API from a .NET backend (Polly-style retry/circuit-breaker thinking). The new part is that failures here cost money per attempt and the 'response' is probabilistic, not just occasionally down.

Watch Out

Pitfalls & anti-patterns

  • Don't ship without a timeout on the LLM call — an unbounded wait is the most common cause of 'my AI feature hung'.
  • Don't over-invest in model routing this early; get one model working well before optimizing cost across several.
Key Takeaways

Before you move on

  • Treat the LLM provider like any flaky external dependency: timeout, retry, fall back.
  • Structured output is what makes an LLM response usable by the rest of your system.
  • Streaming is a UX win, not a correctness requirement — add it after the plain version works.
